# Orion Code v0.1.2 Goal 连续性与证据闭环计划

> 状态：Draft / Planning Baseline
>
> 目标版本：`@orion-agents/orion-code@0.1.2`
>
> 发布基线：`@orion-agents/orion-code@0.1.1`（必须先完成发布与发布后验证）
>
> 规划基线：2026-07-30 的 `codex/v0.1.1-release` 工作树
>
> 上位目标：[Orion Code 项目级目标](../goals/orion-code-项目级目标.md)
>
> 主题：让单 Session、单 Active Goal 真正跨回合恢复，并以逐项证据而不是模型判断关闭目标

## 1. 执行摘要

v0.1.1 负责收敛 UI 产品身份、命令契约、Goal 命令路由、数据安全和发布可信度。
v0.1.2 不重复这些工作，也不提前承诺完整的 v0.2 Goal Runtime。它要关闭的是当前 Goal
骨架中的端到端断点：

```text
用户目标
  → 原始目标与成功条件持久化
  → 结构化 Goal turn
  → 可恢复的计划与下一步
  → 工具/测试/文件/外部状态证据
  → requirement-by-requirement audit
  → complete / blocked / paused / limited
  → 可核验的最终交付摘要
```

当前实现已经有 Goal sidecar、状态机、预算字段、continuation 骨架、Goal tools 和 completion
audit，但这些能力还没有形成可信闭环：

- `update_goal` 当前只返回“请求已记录”的文本，没有把 terminal request 交给 turn outcome；
- `AgentTurnOutcome` 的实际构造没有携带 completion request、逐项证据或 verification summary；
- completion audit 只判断“任意 evidence ref + 非空摘要”，不能证明每项要求完成；
- `AgentTurnRequest` 已定义结构化 `goal_continuation`，实际调度仍重新提交提示字符串；
- Goal runtime events 已定义，但没有形成稳定的 controller → view model → renderer 链路；
- session resume 尚未证明会绑定、恢复并展示正确的 GoalCoordinator；
- usage accounting、no-progress 和 blocker 判断仍缺少真实 turn delta 与可审计信号。

因此 v0.1.2 的版本结果定义为：

1. 原始 objective、显式约束、成功条件、计划摘要和下一步可以跨回合、compact 与 resume 恢复；
2. continuation 使用结构化 runtime input，不再依赖伪装成用户输入的 marker 字符串；
3. `update_goal complete|blocked` 成为两阶段请求，只有 runtime audit 可以改变终态；
4. completion audit 逐项匹配新鲜证据，缺失、失败或过期证据时 Goal 保持 active；
5. TUI 清楚展示 Goal 状态、进度、预算、下一步和审计结果，技术版 terminal-ui 保持语义一致；
6. sidecar、恢复、预算和发布流程可向 v0.1.1 回退，且不静默损坏用户数据。

## 2. 版本边界

### 2.1 与 v0.1.1 的关系

v0.1.2 只有在 v0.1.1 完成以下发布门禁后才能进入发布阶段：

- TUI 已是明确的公众默认产品；
- terminal-ui 已收敛为技术 renderer；
- Ink 已废弃并有 v0.2.0 删除说明；
- `/target`、`/goal` 已通过 shared controller；
- command risk metadata、storage preview/confirm、context clear 和 structured shutdown 已稳定；
- build、lint、全量测试、PTY、tarball、实际 PATH 和 registry install 均有证据。

如果 v0.1.1 尚未发布，v0.1.2 可以做设计和隔离分支实验，但不得：

- 把 v0.1.1 未完成项重新包装成 v0.1.2；
- 直接从 dirty v0.1.1 工作树发布；
- 用 v0.1.2 的计划状态替代 v0.1.1 的 Go/No-Go；
- 在两个版本中重复修改同一命令/runtime 边界而不先确定归属。

### 2.2 与 v0.2 的关系

v0.1.2 是单 Session、单 Active Goal 的可靠性闭环，不是完整项目调度系统。

以下能力明确保留到 v0.2：

- 多 Goal 并发、目标队列、DAG 和跨 Session 调度；
- Goal、todo、subagent task 和 artifact 的完整关系图；
- 通用阶段编排器、远程 worker 和 unattended background daemon；
- Desktop、IDE、Web 或 App Server 客户端；
- 团队策略、云同步和远程审计；
- Ink、React、Yoga 的物理删除及相应破坏性 CLI 变更；
- Goal sidecar 的破坏性 schema 重写。

### 2.3 Patch 版本约束

v0.1.2 允许增强内部 Goal contract、runtime protocol 和 TUI 展示，但必须保持：

- `orion`、`/target`、`/goal`、现有配置和 session 基本用法兼容；
- v0.1.1 sidecar 可直接读取，不要求用户手工迁移；
- 不新增一批公众 slash commands；
- 不扩大默认权限，不自动执行发布、删除、付款或其他高风险外部操作；
- Print/JSON 仍为实验性自动化边界，不在本版本声明稳定协议。

## 3. 计划依据与优先级

### 3.1 依据

本计划按以下顺序约束实施：

1. [Orion Code 项目级目标](../goals/orion-code-项目级目标.md)；

5. 历史 OpenHorse Goal 代码与兼容行为。

历史实现只能提供迁移参考，不能覆盖当前项目级目标中的单一 runtime、安全默认值和证据门禁。

| 优先级 | 含义 | 发布规则 |

### 4.3 必须关闭的断点

#### 断点 A：终态请求没有进入 turn outcome

`update_goal` 当前没有把 `complete|blocked` 请求写入受当前 turn 约束的状态。即使模型调用工具，
coordinator 也不一定在 `finalizeTurn()` 中看到 `pendingTerminalRequest`。

风险：

- 工具声称成功但 Goal 永远保持 active；
- 后续若直接写状态，又可能绕过 completion/blocked audit；
- 并发或旧 turn 的请求可能污染新 revision。

#### 断点 B：证据只有字符串存在性，没有 requirement 语义

当前 audit 只要求至少一个 evidence ref 和非空摘要。一个无关测试、旧日志或模型自述即可满足
形式条件，违反“证据优先于判断”和逐项完成审计原则。

#### 断点 C：结构化 continuation 被降级为普通文本

coordinator 已生成 `AgentTurnRequest`，但实际 scheduler 提交
`[goal continuation #N]` 字符串。这样会丢失或模糊：

- `inputKind = goal_continuation`；
- `goalId/revision/continuationIndex`；
- `persistAsUserMessage = false`；
- `echoToTranscript = false`；
- 旧 generation 失效和取消语义。

#### 断点 D：恢复链未形成唯一 owner

GoalCoordinator 的创建、加载和 model tool 绑定尚未证明与 session lifecycle 同步。全局 tool
binding 还可能让错误 session 的工具读取或修改另一个 coordinator。

#### 断点 E：事件定义与实际产品体验脱节

`goal_updated`、`goal_cleared`、`goal_continuation`、`goal_audit_failed` 和 `goal_restored`
已有类型，但当前没有形成完整发送和消费路径。TUI 无法可靠解释：

- 当前是不是在持续目标模式；
- 为什么继续、暂停或停止；
- 哪项成功条件缺证据；
- 预算是否接近上限；
- resume 后恢复了哪个目标。

#### 断点 F：Accounting 与 no-progress 不足以支撑终止判断

若每轮重复累计 session 总用量，预算会提前耗尽；若只以 tool call 数判断进展，只读查询会被
误判为进展，而纯分析或文档结果可能被误判为无进展。blocked 判定也必须绑定同一 blocker
fingerprint 和连续 goal turn，不能只信任模型的一次声明。

## 5. 版本目标映射

| 项目级目标 | v0.1.2 交付 |
|---|---|
| G1 目标忠实度 | 持久化原始目标、成功条件、计划摘要和下一步；结构化 continuation；逐项完成审计 |
| G2 安全自主 | 终态两阶段提交；预算 fail-closed；外部/破坏性证据不能由模型文本伪造 |

## 6. P0 范围

### P0-A：持久化 Goal Contract 与 Plan Snapshot

在现有 session-scoped Goal 上增加最小可审计 contract：

```ts
interface GoalContract {
  originalObjective: string;
  objectiveRevision: number;
  constraints: GoalConstraint[];
  successCriteria: GoalCriterion[];
}

interface GoalCriterion {
  id: string;
  statement: string;
  source: 'user' | 'derived';
  status: 'pending' | 'passed' | 'failed' | 'stale';
  requiredEvidenceKinds: GoalEvidenceKind[];
  evidenceRefs: string[];
}

interface GoalPlanSnapshot {
  revision: number;
  phase: string;
  steps: GoalPlanStep[];
  nextAction?: string;
  updatedAt: number;
}
```

要求：

- `originalObjective` 创建后不可被普通 steering 静默改写；
- `/target edit` 明确产生 objective revision，保留变更原因和时间；
- `/target replace` 创建新 goalId，不复用旧 Goal 的 completion 状态；
- 用户显式给出的成功条件和限制标记为 `source=user`，Agent 不得删除或弱化；
- Agent 推导的成功条件标记为 `source=derived`，必须能回溯到计划 revision；
- 高风险、外部发布、删除或不可逆目标存在歧义时，先暂停并请求用户确认边界；
- plan snapshot 是可更新执行视图，不取代原始 objective；
- todo 可以投影到 plan，但 todo 完成不能自动等价于 criterion passed；
- compact 和 resume 必须恢复 contract、plan、next action 和 verification state。

兼容策略：

- v0.1.2 对现有 `SessionGoalV1` 只做可选字段扩展和读取时 normalization；
- 缺少新字段的 v0.1.1 sidecar 按原 objective 生成最小 pending contract；
- 不在 patch 版本强制改写历史 sidecar，不批量重写历史 session；
- v0.1.1 reader 应能忽略新增字段并继续读取核心 objective/status/accounting；
- 如果实现必须升级破坏性 schema，延期到 v0.2，不在 v0.1.2 隐式执行。

验收：

- v0.1.1 sidecar 可无交互加载；
- compact 前后的 objective、criteria id、plan revision 和 next action 一致；
- user steering 只补约束或修正当前步骤，不静默替换根目标；
- objective edit/replace 的 revision 与 goalId 语义明确；
- 读取失败、写入失败或 revision stale 时显示错误并停止 continuation。

### P0-B：结构化 Goal Turn 与 Session 恢复

runtime 必须直接消费 `AgentTurnRequest` 或等价结构，禁止把 continuation 降级为普通用户文本。

结构化链路至少保留：

```text
inputKind
sessionId
goalId
goalRevision
continuationIndex
persistAsUserMessage
echoToTranscript
generation
```

要求：

- shared controller 是 continuation scheduler 的唯一 owner；
- renderer 只能提交用户 input、控制请求和 permission response；
- 同一时间只有一个 active goal turn；
- pause、interrupt、replace、session switch 和 shutdown 使旧 generation 失效；
- stale goalId/revision 的 outcome、tool request 和 scheduler callback 必须被拒绝；
- goal continuation 不写成伪造的 user message，不污染持久 transcript；
- model tool coordinator 通过当前 runtime/session execution context 注入，不使用模块级可变全局；
- session 创建、切换、`/resume`、compact restore 和 shutdown 都有明确的 Goal bind/unbind；
- active Goal 在 process restart 后先恢复状态并展示，不在无可见提示时自动执行；
- unclean shutdown 恢复为 `paused/recovery_required` 或等价安全状态；
- 用户显式 `/target resume` 后才重新进入自动 continuation；
- 正常 turn 结束后，scheduler 只在 Goal active、budget 可用、无 pending permission、
  无 terminal request 且 generation 未变化时继续。

验收：

- 20+ turn fixture 中每个 continuation 的 goalId/revision/index 连续且唯一；
- continuation 不出现在 user transcript 或持久 user message 中；
- `/resume` 绑定被恢复 session 的 Goal，不读取上一个 session 的 coordinator；
- process restart 后不发生静默工具调用；
- pause/replace/shutdown 后排队 callback 不会重新启动旧目标；
- TUI 和 terminal-ui 对同一结构化 Goal turn 产生等价 runtime event 顺序。

### P0-C：证据账本与逐项 Completion Audit

引入由 runtime 管理的证据记录，模型只能引用候选证据，不能凭文本自封通过：

```ts
interface GoalEvidenceRecord {
  id: string;
  goalId: string;
  goalRevision: number;
  turnId: string;
  kind: 'test' | 'build' | 'lint' | 'file' | 'runtime' | 'external' | 'user';
  subject: string;
  result: 'passed' | 'failed' | 'inconclusive';
  sourceRef: string;
  capturedAt: number;
  workspaceFingerprint?: string;
  expiresAt?: number;
  redacted: boolean;
}
```

证据规则：

- 模型自然语言、自我评价、计划文本和“应该已完成”不能作为 passed evidence；
- command/tool 的真实 result、exit code、文件 hash、测试报告、runtime probe、外部 API 状态或
  用户明确确认可以形成 evidence；
- failed 和 inconclusive evidence 必须保留，不能被同一轮摘要静默丢弃；
- 工作树在证据后发生相关修改时，受影响的 build/test/file evidence 标为 stale；
- 外部 PR、CI、registry、发布或服务状态必须有当前查询时间，过期后不能关闭 criterion；
- evidence 中的 secret、token、env value 和敏感路径按现有 redaction policy 清理；
- evidence ref 必须能回到 session event、artifact、命令摘要或外部资源标识；
- completion audit 不重新执行任意命令，只审计已捕获证据；缺证据时返回下一步验证建议。

`update_goal complete` 必须执行两阶段流程：

1. model tool 记录绑定当前 turn、goalId 和 revision 的 terminal request；
2. turn 持久化完成后，coordinator 对每个 success criterion 运行 audit；
3. 全部 required criterion 有新鲜 passed evidence，且无相关 failed evidence，才转为 complete；
4. audit 失败时 Goal 保持 active，写入 remaining requirements 并发送 `goal_audit_failed`；
5. runtime 根据 remaining requirements 更新 next action，再决定是否 continuation。

`update_goal blocked` 必须：

- 记录结构化 blocker category、resource、reason 和 fingerprint；
- 同一 blocker 在至少 3 个连续 goal turn 中重复出现；
- 这 3 个 turn 均无法产生实质进展；
- 明确需要用户输入、权限或外部状态变化；
- 未达到条件时 Goal 保持 active 或 paused，不伪装成 blocked。

验收：

- 一个无关的 passing test 不能关闭多个未验证 criterion；
- 旧 workspace fingerprint 的 test evidence 不能关闭当前代码 criterion；
- `update_goal complete` 的 tool success 只表示“请求已接收”，不表示 Goal 已完成；
- audit failure 后状态仍为 active，并列出 criterion id、缺失证据和建议动作；
- 全部 criterion 通过时记录 completion audit、completedAt、final summary 和 evidence refs；
- 同一 blocker 未连续出现 3 次时不能进入 blocked。

### P0-D：准确 Accounting、预算与 Continuation Stop Policy

要求：

- 每个 Goal turn 只累计本 turn delta，不重复累加 session lifetime usage；
- prompt、completion、retry、fallback 和 subagent token 的计入口径明确；
- token budget 只在用户显式设置时存在，不能由模型自行创建或扩大；
- 发起下一次 provider 请求前检查剩余预算；
- provider usage 缺失时标记 accounting incomplete，不把未知值当 0 后继续无限运行；
- budget 达限转为 `budget_limited`，保存精确 stop reason 和可恢复方式；
- usage/auth/network/rate-limit/runtime error 分层，不统一包装为 blocked；
- no-progress 由 workspace change、criterion/evidence/plan 变化和有效外部状态变化组合判断；
- 只读 tool call 数量本身不等于进展；
- 没有 tool call 也不自动等于无进展；
- 连续无进展达到阈值时安全暂停，并向用户解释最近三轮发生了什么；
- completion、blocked、paused、usage_limited 和 budget_limited 都阻止继续调度。

验收：

- 3 个已知 token delta 的 turn 得到精确总和；
- retry/fallback 不会漏记或重复记账；
- 达到预算后零新增 provider call；
- permission pending、用户 interrupt、session switch 和 shutdown 后零幽灵 continuation；
- no-progress fixture 不因只读查询被重置；
- stop reason 在 restart/resume 后保持一致。

### P0-E：Goal Events、TUI 主体验与 Renderer Parity

shared runtime 是以下事件的唯一事实源：

- `goal_restored`
- `goal_updated`
- `goal_plan_updated`
- `goal_continuation`
- `goal_evidence_recorded`
- `goal_audit_failed`
- `goal_completed`
- `goal_cleared`

TUI 最小产品体验：

- 启动或 resume 后显示当前 Goal objective、status、plan phase 和 next action；
- 运行中显示 turn index、预算使用和 continuation 原因；
- audit 失败显示缺失 criterion 和最短验证路径；
- paused/blocked/limited 显示恢复条件；
- complete 显示逐项通过摘要和证据入口；
- Goal 状态更新不制造伪 user message，不重复刷 transcript；
- Goal panel 不抢占输入 ownership，不破坏 scrollback、paste、CJK、resize 和 Ctrl+C；
- 窄终端降级为一行状态，不截断输入区域。

renderer 边界：

- TUI 是所有新增 Goal 交互的产品验收主界面；
- terminal-ui 只做文本化事件 parity、诊断和必要回退；
- Print/Text 对交互性 Goal continuation 返回确定性状态，不无限后台跟随；
- Print/JSON 输出结构化 Goal event，并继续标记 experimental；
- Ink 不新增 Goal UI，只验证废弃入口不会绕过 shared runtime 或安全退出。

验收：

- 同一 fixture 在 TUI、terminal-ui 和 Print adapter 中产生相同业务事件序列；
- renderer 切换不改变 Goal status、plan revision、evidence 或 accounting；
- TUI resume 后展示恢复目标，不需要用户猜测是否已加载；
- 80、120、154 列下 Goal 状态不破坏输入和工具输出顺序；
- terminal-ui 不出现独立 coordinator、audit 或 continuation loop。

### P0-F：发布可信度

v0.1.2 发布前必须：

- 从已发布并验证的 v0.1.1 对应开发分支创建 v0.1.2 分支；
- 明确 dirty-worktree ownership，不混入 v0.1.1 或视觉实验的无关改动；
- 版本、CLI、Banner、帮助、中英文 README、release note 和 npm metadata 一致；
- build、lint、全量 Jest、Goal E2E、renderer parity 和真实 PTY 分别留证；
- 完成 v0.1.1 sidecar 兼容读取、restart/resume 和 corrupt recovery；
- `npm pack --dry-run` 审核文件清单；
- 用生成 tarball 在干净 prefix 安装并验证；
- 在用户实际 zsh/PATH 验证 `command -v orion`、`orion --version` 和默认 TUI；
- PR、CI、人工 review、merge、tag、npm publish 和 registry install 状态分别记录。

## 7. P1 范围

### P1-A：计划与证据可解释性

- `/target` 状态摘要显示 pending/passed/stale criterion 数量；
- `/target status` 或现有详情视图可查看当前 phase、next action 和最近 evidence；
- completion summary 区分自动验证、外部查询和用户确认；
- audit failure 提示可执行的下一步，不只输出内部 error code；
- plan update 和 criterion update 记录 source 与 revision；
- warning 和重复 audit 结果在 UI 中去重。

不因此新增多组 Goal slash commands；优先扩展现有 `/target` 详情和 TUI inspector。

### P1-B：诊断与恢复

- `/doctor` 检查 orphan/corrupt/stale Goal sidecar，但默认只读；
- storage repair 只对可证明安全的 Goal metadata 提供 preview；
- stale CAS、session mismatch、corrupt sidecar 和 incompatible fields 使用不同错误；
- 提供用户可执行的恢复建议，不自动删除原始 sidecar；
- debug/trace 中保留 goalId 短标识、revision、turnId 和 stop reason；
- 所有日志继续经过 secret redaction。

### P1-C：长会话稳定性

- 20+ turn、至少一次 compact、一次 process restart、一次 session resume；
- 中途包含用户 steering、permission deny、失败测试、修复、重新验证；
- 目标、成功条件、next action 和 evidence 不因摘要压缩而漂移；
- transcript 不出现重复 continuation marker；
- 最终完成摘要可从 sidecar/session evidence 重建。

## 8. 明确非目标

v0.1.2 不做：

- 新的多目标管理命令或目标调度 UI；
- 自动把所有聊天请求升级为 persistent Goal；
- 让模型自行扩大预算、权限或高风险操作范围；
- 自动发布 npm、合并 PR、删除分支或清理用户数据；
- 把 tool call 数、todo 完成或模型自述当作 completion evidence；
- 为 terminal-ui 做与 TUI 平行的产品级视觉迭代；
- 为 Ink 增加任何新 Goal 能力；
- 稳定 Print/JSON 公共协议；
- 重构全部 TaskManager、Subagent 或 Artifact 系统；
- Desktop、Web、IDE、云同步或团队策略；
- 借 Goal 改造顺带增加 Provider、模型或 slash command 数量。


- v0.1.1 应忽略 v0.1.2 additive fields 并读取核心 Goal；
- 如果某实现无法满足向后读取，必须在发布前改为 side-by-side 存储或延期到 v0.2；

## 15. Go / No-Go

### Go

- v0.1.1 已发布并完成发布后验证；
- 原始 objective、显式约束和 success criteria 可跨 compact/restart/resume 恢复；

- failed/stale/missing evidence 时 Goal 保持 active；
- accounting 和 budget preflight 精确，达限后零新增 provider call；

### No-Go

- v0.1.1 尚未发布或其 P0 未关闭；
- continuation 仍提交 marker 字符串或伪 user message；
- 任一 renderer 拥有私有 GoalCoordinator、audit 或 scheduler；
- `update_goal` 声称成功但 terminal request 未进入 turn outcome；
- completion 只检查 evidence 数量或模型摘要；
- 旧、失败、无关或 stale evidence 可以关闭 criterion；
- session switch 后 Goal tool 仍指向旧 coordinator；
- usage 不完整时继续无限自动运行；
- sidecar 写入/CAS 失败被吞掉；
- restart 后在用户不可见时自动执行工具；
- TUI Goal 展示破坏 input ownership、scrollback、CJK、paste 或 Ctrl+C；
- v0.1.1 sidecar 被隐式破坏性重写；
- 只报告 Jest 总量，没有长会话、PTY、tarball 和 registry 证据。

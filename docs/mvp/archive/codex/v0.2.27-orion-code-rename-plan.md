# Orion Code v0.2.27 全面重命名与发布迁移计划

> **状态**: draft
> **版本**: v0.2.27
> **日期**: 2026-07-23
> **作者**: Codex
> **目标读者**: 负责架构、实现、测试、CR、迁移和发布的 Coding Agent
> **版本主题**: 产品名改为 Orion Code，npm 包改为 `orion-code`，主启动命令改为 `orion`

## 1. Summary

v0.2.27 是一次完整的产品身份切换，不是只修改 CLI banner。版本目标是把当前
OpenHorse 的公开品牌、npm 包、命令、配置命名空间、持久化路径、公共 SDK、协议身份、
文档、GitHub 仓库和 Desktop 联动统一为 Orion Code。

最终身份固定为：

| 维度 | v0.2.27 目标值 |
|---|---|
| 产品显示名 | `Orion Code` |
| 产品 ID | `orion-code` |
| npm 包 | `orion-code` |
| 主命令 | `orion` |
| GitHub 仓库 | `Linux2010/orion-code` |
| 全局配置目录 | `~/.orion-code/` |
| 全局配置文件 | `~/.orion-code/orion.json` |
| 全局 dotenv | `~/.orion-code.env` |
| 项目配置目录 | `.orion-code/` |
| 环境变量前缀 | `ORION_CODE_` |
| 用户规则文件 | `ORION.md` |
| 本地用户规则文件 | `ORION.local.md` |
| MCP client name | `orion-code` |
| Desktop 产品名 | `Orion Code Desktop` |

核心决策：

1. **正常运行路径硬切新品牌**：不保留 `openhorse` binary、旧环境变量 fallback、
   `~/.openhorse` 自动读取或旧公共类型 alias。
2. **数据迁移与运行时兼容分离**：提供显式的一次性
   `orion migrate openhorse`，但启动、查询、Resume 和工具运行不扫描旧目录。
3. **历史日志不重写**：Session JSONL、trace 和历史 assistant 内容保持原字节，保证可审计；
   只在 reader 中识别必要的旧 Context marker。
4. **集中产品身份**：新增单一 `ProductIdentity`，禁止 package、UI、MCP、路径和 prompt
   继续各自硬编码品牌字符串。
5. **公开 API 同步硬切**：`OpenHorseConfig`、`OpenHorseRuntime`、`OpenHorseTool` 等
   public types 改为 `OrionCode*`；新包不导出旧别名。
6. **主命令必须是 `orion`**：已确认生态存在同名命令，发布前必须完成冲突测试和用户提示。
7. **跨仓库一致性**：CLI 仓库和 `openhorse-desktop` 的活跃产品面必须在公开宣布前完成同一品牌切换。
8. **先发布新包，再弃用旧包**：验证 `orion-code@0.2.27` 后 deprecate `openhorse`，不 unpublish。

## 2. 结论与可行性评估

### 2.1 总体结论

技术结论：**GO WITH CONDITIONS**。

代码和发布链路可以完成重命名，但名称本身存在明显生态冲突：

- `orion-code` npm 包在 2026-07-23 执行 `npm view orion-code` 返回 404；
- `Linux2010/orion-code` 当前不存在；
- npm 已有 `orion@20.0.0`，并安装同名 `orion` binary；
- Homebrew 搜索结果存在 `orion`；
- npm 和 GitHub 已存在多个以 Orion 命名的 Coding Agent 或多 Agent 项目；
- 当前机器未安装 `orion` 命令，也没有 `~/.orion` 或 `~/.orion-code` 目录。

因此：

- `orion-code` 包名当前是候选可用，不代表已被永久保留；
- `orion` 命令可以按用户要求使用，但必须接受与其他工具冲突的现实；
- 品牌和商标唯一性尚未获得法律结论，本计划不能替代人工商标核验；
- 发布前 Gate 0 不通过时，不能先改完代码再临时换第三个名字。

### 2.2 Gate 0：名称确认

开始大规模代码替换前必须完成：

```bash
npm view orion-code name version --json
npm view orion bin version description --json
gh repo view Linux2010/orion-code
gh search repos 'orion-code in:name' --limit 20
brew search orion
```

判定：

- `orion-code` 被他人发布：停止实施，重新确认 npm 名称；
- `Linux2010/orion-code` 已被非本项目占用：停止仓库重命名；
- 用户不接受 `orion` binary 冲突：重新确认命令名；
- 品牌审查不通过：停止公开发布，但可保留技术分支等待新名称。

不得通过发布空壳恶意占名，也不得假设一次 404 查询能永久保留 npm 名称。

### 2.3 外部平台依据

- [npm package.json `bin` 规范](https://docs.npmjs.com/files/package.json/)：npm 根据
  `bin` map 把命令链接到全局或项目 bin 目录，因此 `orion` 冲突属于真实安装面问题。
- [npm package deprecation](https://docs.npmjs.com/deprecating-and-undeprecating-packages-or-package-versions/)：
  npm 推荐 deprecate 而不是 unpublish，弃用信息会在安装时展示。
- [GitHub repository rename](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)：
  仓库重命名后 Web 和 Git remote 通常会重定向，但本地 clone 仍应更新 remote；旧仓库名不能被重新创建，
  否则会破坏 redirect。

## 4. 目标命名契约

### 4.1 单一命名矩阵

实现中禁止自行派生名称，统一使用：

```ts
export interface ProductIdentity {
  productId: 'orion-code';
  displayName: 'Orion Code';
  cliName: 'orion';
  npmPackage: 'orion-code';
  repository: 'Linux2010/orion-code';
  configDirName: '.orion-code';
  configFileName: 'orion.json';
  envFileName: '.orion-code.env';
  envPrefix: 'ORION_CODE_';
  userInstructionsFile: 'ORION.md';
  localInstructionsFile: 'ORION.local.md';
  projectConfigDirName: '.orion-code';
  mcpClientName: 'orion-code';
}
```

建议新增：

```text
src/product/identity.ts
src/product/paths.ts
src/product/environment.ts
```

业务模块只能引用这些常量或 path API，不得散落 `Orion Code`、`orion-code`、`.orion-code`
字符串。

### 4.2 为什么配置目录使用 `~/.orion-code`

虽然命令是 `orion`，全局和项目配置目录选择 `.orion-code`：

- `orion` 是高冲突通用词；
- npm 已存在同名 package/binary；
- `.orion` 可能与编辑器、服务器、游戏或其他 Agent 共用；
- `.orion-code` 与 npm 产品身份一致，降低误读和数据目录碰撞。

因此不采用 `~/.orion`，也不让运行时同时搜索两个新目录。

### 4.3 环境变量命名

使用 `ORION_CODE_*`，不使用过于通用的 `ORION_*`。

### 6.1 `package.json`

目标：

```json
{
  "name": "orion-code",
  "version": "0.2.27",
  "description": "Orion Code - goal-driven coding agent for the terminal.",
  "bin": {
    "orion": "bin/orion"
  },

```

要求：

- 使用 package manager 正常更新 lockfile；
- package 与 lockfile root name/version 必须一致；
- `files` 包含 `bin/orion`，不包含 `bin/openhorse`；
- tarball 名为 `orion-code-0.2.27.tgz`；
- version 的运行时来源只能有一个；
- `orion --version`、banner、doctor、npm metadata 输出同一版本。

### 6.2 bin 文件

执行：

```text
git mv bin/openhorse bin/orion
```

bin loader 调整：

- `~/.openhorse.env` 改为 `~/.orion-code.env`；
- 注释、错误和 debug identity 改为 Orion Code；
- 保留 `#!/usr/bin/env node`；
- dist/src fallback 逻辑保持行为不变；
- 不加载旧 dotenv；
- 不创建 `openhorse` symlink。

### 6.3 命令冲突策略

已知 `orion@20.0.0` 也导出 `orion`。安装文档必须包含：

```bash
command -v orion
type -a orion
readlink "$(command -v orion)"
```

若命令已被占用：

- 安装不得静默覆盖不属于 `orion-code` 的 binary；
- 用户明确卸载冲突包或调整 PATH 后再安装；
- `orion doctor --installation` 必须能证明当前命令来自 `orion-code`；
- CI 构造 fake `orion` binary 验证冲突提示；
- README 明确 npm package 与 command 不同名。

主体验仍是：

```bash
npm install -g orion-code
orion
```

### 6.4 CLI 文案

所有命令示例改为：

```bash
orion
orion doctor
orion diff
orion commit
orion --ui terminal
orion --ui tui
orion --ui ink
orion -p "review the current git diff"
echo "summarize this project" | orion --print
```

Help 第一行和 banner 使用 `Orion Code`；命令 token 使用 `orion`，不要输出 `orion-code`
作为主命令。

## 8. 一次性数据迁移

### 8.1 命令边界

新增：

```bash
orion migrate openhorse --dry-run
orion migrate openhorse
orion migrate openhorse --include-env
orion migrate openhorse --include-project-files
```

该命令必须在 LLM/config 初始化前可执行。即使 `~/.orion-code/orion.json` 不存在，也能运行
migration help 和 dry-run。

正常启动 `orion`：

- 不检测 `~/.openhorse`；
- 不自动提示迁移；
- 不读取旧 config；
- 不合并旧数据。

迁移是显式运维动作，不是兼容 fallback。

### 8.2 迁移数据契约

```ts
export interface BrandMigrationManifestV1 {
  version: 1;
```

### 8.3 文件迁移规则

默认行为是 **copy + verify + atomic publish**，不 move，不删除 source：

| 来源 | 目标 | 处理 |
|---|---|---|
| `~/.openhorse/openhorse.json` | `~/.orion-code/orion.json` | 结构验证后重命名复制 |
| `~/.openhorse/OPENHORSE.md` | `~/.orion-code/ORION.md` | 重命名复制 |
| `settings.json` | `settings.json` | 原字节复制 |
| `usage.json` | `usage.json` | 原字节复制 |
| `history.jsonl` | `history.jsonl` | 原字节复制 |
| `mcp.json` | `mcp.json` | 原字节复制，保持 `0o600` |
| `vector.db` | `vector.db` | SQLite integrity check 后复制 |
| `projects/**` | `projects/**` | 原结构复制并逐文件校验 |
| `skills/**` | `skills/**` | 原结构复制 |
| `cost/**` | `cost/**` | 原结构复制 |
| `cache/**` | `cache/**` | 可复制；失败可重建，不影响核心成功 |
| `backups/**` | `backups/openhorse/**` | 保留来源说明 |
| `migration-logs/**` | `migration-logs/openhorse/**` | 保留审计记录 |

旧 JSONL、trace、compact、goal、harness 和 Session metadata 不做品牌字符串替换。

### 8.4 原子流程

```text
1. acquire target migration lock
2. inventory source without reading secret content into logs
3. validate source config is v0.2.26 schema
4. create sibling staging directory
5. copy files with original safe modes
6. apply only approved filename/config-key transformations
7. parse every JSON/JSONL artifact
8. run SQLite integrity_check
9. compare file count, byte count, per-file SHA-256 and tree hash
10. atomically rename staging to ~/.orion-code
11. write final manifest
12. leave ~/.openhorse unchanged
```

如果 target 已存在：

- 默认失败；
- 不隐式 merge；
- `--force` 也不能覆盖非空 target；
- 后续如需要 merge，单独设计并测试，不放进 v0.2.27 P0。

### 8.5 dotenv 迁移

`~/.openhorse.env` 位于 config home 外，默认 dry-run 只报告。

`--include-env`：

- 使用 dotenv parser，不做正则全文替换；
- key 按完整映射从 `OPENHORSE_*` 改为 `ORION_CODE_*`；
- value 原样保留；
- 写入 `~/.orion-code.env`，mode `0o600`；
- 目标存在时失败；
- 日志只记录 key name，不记录 value；
- generic Provider env 不改名。

### 8.6 项目文件迁移

默认不修改 Git 工作区。`--include-project-files` 必须显式开启，并按项目逐个处理：

```text
.openhorse/              -> .orion-code/
.openhorse.yaml          -> .orion-code.yaml
.openhorse.yml           -> .orion-code.yml
.openhorse.json          -> .orion-code.json
openhorse.yaml           -> orion-code.yaml
openhorse.yml            -> orion-code.yml
openhorse.json           -> orion.json
OPENHORSE.md             -> ORION.md
OPENHORSE.local.md       -> ORION.local.md
```

规则：

- 先 `git status --porcelain`，dirty project 默认只报告；
- target 已存在则记录 conflict，不覆盖；
- YAML/JSON 使用 parser 修改根 namespace；
- 变更前输出清单和 backup；
- 不自动 commit；
- 完成后输出每个项目的 diff summary。

### 8.7 历史 marker

新内容使用：

```text
[Orion Code Context State v3]
[Orion Code Verification Gate]
[Orion Code loop hint]
```

迁移后的旧 Session 可能包含：

```text
[OpenHorse Context State v2]
[OpenHorse Verification Gate]
[OpenHorse loop hint]
```

Reader 必须在专用 `legacy-markers.ts` 中只读识别旧 marker。禁止在新输出、prompt、UI 或
新 Session 中生成旧 marker。Brand audit 对该文件和 migration fixtures 建立精确 allowlist。

## 23. 风险与控制

### 风险 A：`orion` 命令冲突

控制：Gate 0、安装前 `command -v/type -a/readlink`、fake collision CI、doctor identity 和清晰文档。

### 风险 B：npm 名称在开发期间被占用

控制：每个 release checkpoint 重新查询；准备 scoped fallback 仅供决策，不在代码中预埋第二品牌。

### 风险 C：配置目录切换造成“数据丢失”

控制：显式 copy/verify migration、source 保留、real-data Gate 和两条 Session Resume。

### 风险 D：无差别替换损坏历史/协议

控制：parser/AST/structured migration、历史 allowlist、禁止重写 JSONL、协议版本 bump。

### 风险 E：public API 半改名

控制：tarball consumer compile，旧 symbols absence test，Desktop/shared SDK review。

### 风险 F：Desktop 分裂品牌

控制：跨仓库 checklist 和公开公告 Gate；preload/appId/protocol 一起切换。

### 风险 G：仓库 rename 破坏链接/自动化

控制：GitHub settings audit、remote update、old URL redirect test、不复用旧 repo 名。

### 风险 H：旧包过早弃用

控制：新包 clean install、Provider turn、migration 和 Resume 成功后才 deprecate。

### 风险 I：品牌法律风险

控制：发布前人工商标和命名审查；本文只证明技术可行性，不证明法律可用性。

## 24. 回滚方案

### 24.1 npm 回滚

- `orion-code` 保留已发布版本；
- 将 `latest` 指回已验证的 Orion Code 版本；
- 暂缓或撤销 `openhorse` deprecation message；
- 不 unpublish；
- 公告明确问题和恢复时间。

### 24.2 数据回滚

- `~/.openhorse` 从未删除，可继续由旧 CLI 使用；
- 删除或隔离失败的 `~/.orion-code` 前先保留 migration manifest；
- 不从 target 反向覆盖 source；
- project files migration 使用 backup 恢复；
- rollback 过程不修改 Session JSONL。

### 24.3 GitHub 回滚

通常不建议反复 rename。若代码发布失败，保持 `orion-code` 仓库名并修复版本；只有品牌决策整体撤销时
才考虑仓库回退，并重新验证 redirect、package metadata 和所有 clone。

### 24.4 Desktop 回滚

- 保留旧 app build；
- appId 变化前备份 userData；
- protocol mismatch fail-fast；
- 不让新 renderer 连接旧 app-server 后静默运行。

## 27. Coding Agent 执行指引

承担实现的 Coding Agent 必须按以下方式工作：

1. 从最新 v0.2.26 完成基线重新审计，不能依赖本文行号机械替换。
2. 先落 `ProductIdentity` 和 brand audit，再替换各模块，防止新硬编码继续出现。
3. 禁止使用无边界的全仓库 replace；按 package、runtime、data、UI、docs 分批修改。
4. 修改持久化路径前先完成 migration tests，不能先让旧数据不可见。
5. migration 只 copy/verify，不删除 source，不改写历史 JSONL。
6. public API 变更使用 tarball consumer 证明，不只运行仓库内 Jest。
7. 每个 Slice 完成后运行 focused tests、build、brand audit 和 `git diff --check`。
8. UI Slice 必须跑真实 PTY，不能只审查字符串。
9. Desktop 使用独立 PR/commit，但必须纳入同一发布 checklist。
10. GitHub rename 和 npm deprecate 属于不可轻率回滚的外部操作，只在 Gate 通过后执行。
11. 发布证据记录具体 commit、tarball hash、npm metadata、migration manifest 和 smoke 命令。
12. 任何数据、package、command 或品牌 Gate 证据不足时，保持 **NO-GO**。

# Orion Code v0.1.1 命令可靠性与交互优化计划

> 状态：Draft  
> 基线：v0.1.0 / 2026-07-28 当前工作树  
> 目标版本：v0.1.1  
> 主题：统一 slash command 语义、修复默认 TUI 路由、收敛旧命令、补齐安全与验收门槛

## 1. 执行摘要

v0.1.1 不应继续增加一批新的 `/` 命令。当前更重要的问题是：同一命令体系承载了 42 个
共享命令，其中 39 个默认可见、3 个隐藏兼容；TUI 又额外维护 2 个本地命令。默认面板没有
充分区分稳定内建命令、条件命令、Agent 工作流快捷方式和迁移入口。

本次审计确认三个 P0：

1. 默认 TUI 中的 `/target` 和 `/goal` 没有复用传统 terminal renderer 的结构化
   `goal_control` 路由，因而缺少一致的 `budget`、确认式 `clear`、自动启动和多轮续跑语义。
2. `/storage cleanup` 与 `/storage repair` 会修改本地数据，但当前无需 `--yes` 确认；
   `cleanup` 默认可递归删除被识别为旧版、临时或空项目的存储目录。
3. `/clear-history` 只重置当前内存中的模型上下文，不删除或截断持久化 session；命令名称和
   “Cleared conversation history” 输出会让用户误以为历史已经永久清除。

建议把 v0.1.1 定义为稳定化版本：

- 修复所有 renderer 的命令路由一致性；
- 为命令增加能力、风险、可用条件和弃用元数据；
- 默认面板只突出用户能立即理解和可靠使用的命令；
- 对旧命令给出清晰迁移提示；
- 用共享契约测试、聚焦 PTY 测试和真实安装 smoke test 关闭发布门槛。

## 2. 审计范围与方法

本次结论来自以下当前实现：

- `src/commands/index.ts`：共享命令注册表和处理器；
- `src/commands/target-command.ts`：目标命令结构化解析；
- `src/runtime/agent-runtime-controller.ts` 与 `src/runtime/chat-controller.ts`：共享运行时路由；
- `src/terminal-ui/launch.ts`：传统 terminal renderer 的目标命令特例；
- `src/tui-ui/launch.ts` 与 `src/tui-ui/runner.ts`：默认 TUI 路由和 TUI 本地命令；
- `tests/`：现有命令、session、runtime、TUI 和 PTY 测试。

审计标签：

| 标签 | 含义 |
|---|---|
| 稳定 | 处理器与当前产品语义一致，可保留在默认面板 |
| 条件可用 | 依赖 Git、LLM、embedding、MCP、历史状态或特定 renderer |
| 工作流快捷方式 | 实际转换为普通 Agent 输入，不是确定性内建操作 |
| 有缺陷 | 能进入处理器，但语义、路由、安全或持久化行为不完整 |
| 兼容/过时 | 来自旧 Task/Agent 架构或只用于一次性迁移 |
| 内部命令 | renderer 自身维护，不应伪装成跨 renderer 的公共命令 |

这里的“稳定”不等于测试覆盖已经充分。缺少命令级契约测试的项目仍列入 v0.1.1 验收范围。

当前聚焦回归基线为 6 个 suite、105 个 test 全部通过，覆盖 goal parser、status/model、
session command、storage maintenance、runtime UI parity 和 TUI runner。该结果证明已有局部
能力未发生回归，但不能关闭本计划识别出的跨 renderer 路由、安全确认和持久化语义缺口。

## 3. 当前命令盘点

### 3.1 工作流与目标

| 命令 | 当前判断 | 主要问题 | v0.1.1 处理 |
|---|---|---|---|
| `/target` | **有缺陷 / P0** | 默认 TUI 走共享注册表中的独立 `GoalCoordinator`，未接入 controller 的自动续跑链路；与 terminal renderer 的结构化解析不一致 | 将解析和执行移动到共享 controller；所有 renderer 使用同一状态机 |
| `/goal` | **兼容别名 + 同上缺陷** | 与 `/target` 重复；当前仍有用户和历史数据依赖 | 保留为 `/target` 别名，帮助中标注 compatibility alias，不单列为主命令 |
| `/diff` | 稳定、Git 条件可用 | 非 Git 目录会失败，这是正常可用条件 | 在面板中显示 “requires Git” |
| `/commit` | 稳定、Git 条件可用 | 名称容易被误解为直接提交；实际只生成只读 commit plan | 改描述为 “Preview commit plan”；v0.2 再评估命名 |
| `/review` | 工作流快捷方式 | 只是把 `/review …` 重新交给 Agent，不是确定性审查器 | 保留，标记 `Agent workflow` |
| `/security`、`/audit` | 工作流快捷方式 | 同上，结果取决于模型、工具和上下文 | 保留一个主名称，别名不占面板行 |
| `/test-gen`、`/tests` | 工作流快捷方式 | 同上；`tests` 容易被理解为执行测试 | 主名称建议改为 `/test-gen`，明确 “generate/improve tests”，不声称执行测试 |
| `/todos`、`/todo` | 基本可用 | 展示的是 Store 中 Agent todo，不是 target 进度，也不是旧 TaskManager | 描述改为 “Agent plan todos”；增加空状态解释 |

### 3.2 Session 与上下文

| 命令 | 当前判断 | 主要问题 | v0.1.1 处理 |
|---|---|---|---|
| `/resume` | 稳定 | TUI/terminal picker 已有测试；依赖可恢复 session | 保留为一级命令 |
| `/sessions` | 稳定 | `--all` 与当前项目作用域需要更明显 | 面板显示作用域；补搜索与空状态契约测试 |
| `/session-rename` | 稳定 | 名称较长，但语义明确 | 保留；短别名只用于输入补全 |
| `/compact` | 稳定、条件可用 | 空历史或低于阈值时不执行；依赖 LLM 时摘要质量不同 | 输出中说明 local/LLM summary 来源 |
| `/clear-history`、`/reset` | **有缺陷 / P0** | 只清 Store 和 tool state，不清持久化 session；`reset` 含义过宽；无确认 | 改为 `/context clear --yes` 或明确 “clear model context only”；保留旧名一个版本并警告 |
| `/harness` | 基本可用 | 偏高级诊断，不适合默认一级面板 | 移到 Advanced/Context 分组 |
| `/memory` | 条件可用 | `reindex` 依赖 embedding provider；实现使用 `process.cwd()` 而非命令上下文 `ctx.cwd` | 修正项目路径；面板动态显示 unavailable 原因 |
| `/skills` | 基本可用 | 只展示已加载 skill | 保留 |
| `/skill` | 稳定的 Agent 工作流 | 只对一个 chat turn 激活，属于聊天路由而非内建副作用 | 描述中明确 “for one turn” |

### 3.3 工具、模型与系统

| 命令 | 当前判断 | 主要问题 | v0.1.1 处理 |
|---|---|---|---|
| `/tools`、`/tool` | 基本可用 | 只展示前 28 个，且静态/MCP 可用性信息有限 | 增加总数、来源、连接状态和过滤提示 |
| `/edit-preview` | 条件可用、偏内部 | 必须刚执行过 `edit_file`；依赖全局 last-edit state，旧记录可能没有 session/turn 标签 | 从默认面板移到 Advanced；逐步改为 artifact/turn 引用 |
| `/mcp` | 条件可用 | 无配置时只是状态页；不能在命令内连接、重连或解释失败 | v0.1.1 先增加原因与 `/doctor` 跳转 |
| `/safety` | 基本可用 | 是状态展示，不执行 security review；与 `/security` 容易混淆 | 重命名描述为 “tool safety policy status” |
| `/model` | 稳定、切换时依赖 LLM | 当前运行时切换有效，但不代表写入永久配置 | 输出中明确 “current session/runtime only” |
| `/mode` | 基本可用 | 名称容易与 UI mode 混淆；实际是工具许可策略 | 面板显示 `Permission mode`，保留命令名 |
| `/config` | 基本可用 | 与 `/status`、`/doctor` 有部分重复 | 只保留配置来源与生效值，诊断交给 `/doctor` |
| `/help` | **信息不完整** | 只读取共享 registry，不包含 TUI 的 `/tool-output`、`/redraw`；也不显示条件、风险或弃用状态 | 从统一命令元数据生成 renderer-aware help |
| `/status` | 稳定 | 信息较多但已有 renderer 诊断 | 保留；控制为一屏摘要 |
| `/clear` | 默认交互路径可用，但实现分叉 | `AgentChatController` 会安全清 transcript；共享 registry 仍保留原始 `process.stdout.write('\\x1Bc')` 实现，直接调用时可破坏 TUI surface | 删除双实现，统一发出 `clear_view` runtime event |
| `/exit` | 稳定，但实现分叉 | controller 会拦截；旧处理器直接 `process.exit(0)` | 统一为结构化 shutdown request |

## 4. 建议的 v0.1.1 命令信息架构

默认 `/` 面板只显示高频入口：

```text
Workflow   /target  /diff  /commit  /review  /security  /test-gen
Session    /resume  /sessions  /compact
Context    /skills  /skill  /todos
Runtime    /model  /mode  /tools
System     /status  /doctor  /help  /clear  /exit
```

Advanced 面板或 `/help --all` 显示：

```text
/session-rename  /context-clear  /harness  /memory  /mcp  /safety
/storage  /usage  /loop-stats  /trace  /last-tool  /artifacts
/checkpoint  /migrate  /edit-preview  /tool-output  /redraw
```

兼容别名应参与补全，但不重复占用面板行。面板项需要显示：

- `builtin`、`agent workflow` 或 `renderer local`；
- 当前是否可用以及不可用原因；
- `read-only`、`writes state`、`destructive` 风险；
- `deprecated` 与替代命令；
- renderer scope。

## 5. 实施计划

### Phase 0 — 建立命令契约

扩展 `SlashCommand` 元数据：

```ts
interface SlashCommand {
  execution: 'builtin' | 'agent-workflow' | 'renderer-local';
  rendererScope?: Array<'tui' | 'terminal' | 'print'>;
  risk: 'read-only' | 'state-write' | 'destructive';
  availability?: (ctx: CommandContext) => Availability;
  deprecated?: { since: string; replacement?: string; removeIn?: string };
}
```

验收：

- registry 是 help、palette、completion 和文档清单的唯一来源；
- alias 不重复展示；
- unavailable 命令可见但不可直接执行，并解释原因；
- destructive 命令必须经过共享确认协议。

### Phase 1 — 修复 P0 路由与数据安全

1. 在 `AgentRuntimeController` 或共享 command router 中统一解析 `/target` 与 `/goal`；
2. 删除 `src/terminal-ui/launch.ts` 的 renderer 私有目标路由；
3. TUI、terminal、print 共用一个 `GoalCoordinator`、一个 session scope 和同一输出事件；
4. 补齐 `budget`、`replace`、`clear --yes` 和 active-turn 控制；
5. `/storage repair|cleanup` 默认 preview，执行必须 `--yes`；
6. 将 `/clear-history` 拆成明确的 “clear current model context” 与后续可选的持久化删除；
7. `/clear`、`/exit` 改为结构化 runtime event，业务处理器不直接操作 stdout 或退出进程。

验收：

- 在 TUI 与 terminal 中创建 target 后都会立即启动并能继续多轮；
- `/target budget 50000` 不会被创建成名为 “budget 50000” 的目标；
- `/target clear` 只预览/提示，`/target clear --yes` 才清除；
- 没有确认时 storage 命令不得写入或删除；
- `/clear-history` 的输出与实际持久化范围完全一致。

### Phase 2 — 收敛过时与重复命令

1. `/goal`、`/cost` 保留为兼容别名，但不单列面板；
2. `/task`、`/run`、`/chat` 执行时打印弃用警告；
3. `/agents` 从默认面板移除，直到能展示真实 subagent/runtime task；
4. `/migrate` 移至 Advanced，并声明保留期限；
5. 将 `/usage` 与 `/cost` 收敛成 `/usage [session|lifetime]`；
6. 将 `/review`、`/security`、`/test-gen` 明确标记为 Agent workflow。

验收：

- 旧命令不会静默表现为当前主执行链；
- 每个弃用入口都有替代命令、起始版本和计划删除版本；
- README、`/help`、palette 不再把旧命令列为主能力。

### Phase 3 — 测试、文档与可观测性

新增共享命令契约测试，逐条验证：

- 名称和 alias 唯一；
- help、palette、completion 一致；
- renderer scope 正确；
- availability 与实际依赖一致；
- read-only 命令不写磁盘；
- destructive 命令无 `--yes` 不产生副作用；
- 命令返回失败时 `CommandResult.success === false`；
- TUI/terminal/print 对共享命令产生等价 runtime event。

文档：

- 从 registry 生成命令参考或至少用测试校验静态表；
- 更新 README，只保留稳定、高频入口；
- 更新 `docs/mvp/v0.1.0.md` 的历史状态，避免把兼容/工作流命令写成同一种能力；
- 新增 v0.1.1 release note，列出弃用期和迁移方式。

## 6. 其他优化

### 6.1 TUI 对话节奏

保留当前“用户输入前后各留一行、与 Agent 输出分隔”的方向，但把它作为 transcript layout
契约测试，而不是依赖零散换行。需要验证：

- 连续 user/assistant 消息；
- user 后紧跟 tool activity；
- resume 后恢复的历史；
- 窄终端换行；
- 空消息、错误和中断状态。

### 6.2 启动 Banner

v0.1.1 只做稳定化，不再改变已确认的 banner 几何。要求：

- 保留当前星系图标和 OC 像素布局；
- 固定 cell 宽度，防止 CJK、ANSI 颜色和窄终端导致错位；
- terminal image protocol 必须能力探测后才发送控制序列；
- macOS Terminal 不支持 Kitty 图像时必须无乱码地回退到像素文本；
- banner 改动必须跑真实 PTY，不能只依赖字符串快照。

### 6.3 条件能力反馈

把“命令不可用”变成可操作信息：

- 非 Git 项目：提示切换项目或初始化 Git；
- embedding 未配置：给出当前 provider 状态和配置入口；
- MCP 未连接：展示 server 错误和 `/doctor` 建议；
- 没有 edit/tool/artifact/session：显示产生该状态的最短操作路径；
- LLM 未初始化：说明只读命令仍可用，模型相关操作不可用。

### 6.4 输出与错误规范

- 禁止命令处理器直接 `process.stdout.write`、`process.exit`；
- 所有输出走 renderer-neutral event；
- 用户错误、运行时错误、条件不可用和用户取消使用不同 error code；
- 禁止出现内部旧品牌和旧架构文案；
- 成功/失败必须与返回的 `CommandResult.success` 一致。

## 7. 测试与发布门槛

### 7.1 自动化门槛

- `npm run build`
- `npm run lint`
- `npm test -- --runInBand`
- 新增 command registry contract tests
- 新增 target renderer parity tests
- 新增 storage destructive-action tests
- 新增 clear/context persistence tests

### 7.2 聚焦 PTY 门槛

分别执行并记录：

- 默认 `orion`（TUI）启动、`/help`、`/target`、多轮 continuation、`/clear`、退出；
- `orion --ui terminal` 的同一命令序列；
- 80、120、154 列宽度；
- macOS Terminal 的无图像协议回退；
- banner、CJK 输入、粘贴、resume、tool output、Ctrl+C 双击退出。

启动 marker 或 banner 文案发生变化时，必须单独更新并运行对应 PTY 断言；不能用 build/lint
通过替代真实终端验收。

### 7.3 发布门槛

- `package.json`、CLI `--version`、banner 均为 `0.1.1`；
- `npm pack --dry-run` 只包含预期文件；
- 用生成的 tarball 本地安装；
- 在用户实际 zsh/PATH 中运行 `which orion`、`orion --version` 和 TUI smoke；
- 保存 TUI/terminal 截图或 PTY 日志作为发布证据；
- 所有 P0 关闭后才允许发布。

## 8. Go / No-Go

### Go

- 默认 TUI 与 terminal 的 target 行为一致；
- 所有 destructive command 都有 preview 和确认；
- 默认面板没有旧 TaskManager 入口；
- 条件命令能说明不可用原因；
- 全量测试、聚焦 PTY、tarball 安装和实际 PATH 验证通过。

### No-Go

- `/target` 仍由 renderer 私有分支实现；
- `/storage cleanup` 可在无确认时删除数据；
- `/clear-history` 仍声称永久清除但可被 `/resume` 恢复；
- Kitty/iTerm 控制序列会在不支持的终端输出为长字符串；
- 只报告 build/lint 通过，没有真实 TUI/PTY 证据。

## 9. 建议排期

| 优先级 | 工作 | 预计 |
|---|---|---|
| P0 | command contract、target 路由统一、storage/clear 安全 | 2–3 天 |
| P1 | palette/help 元数据、弃用与重复命令收敛 | 1–2 天 |
| P1 | renderer parity、command contract、持久化测试 | 2 天 |
| P1 | TUI spacing/banner 聚焦回归与真实 PTY | 1 天 |
| Release | 文档、pack、实际 PATH 安装验证 | 0.5–1 天 |

建议总周期：6–9 个工程日。若 v0.1.1 必须更快发布，最小可发布范围仍必须包含三个 P0、
target renderer parity tests 和 storage destructive-action tests；命令命名空间重构可延后到
v0.2。

# v0.2.14 UI 终极体验修正计划

## 审计补充：本轮 review 发现的高优先问题（2026-07-08）

以下问题是基于最新代码审计给出的“可执行修订清单”，不改变架构，仅完善 runtime + 交互一致性：

1. 跳过工具事件缺少真实元数据（P1）
   - 当前 `finalizePendingAsSkipped` 在取消链路里可能写出 `name=callId/args={}`，会影响 `/trace`、审计和定位。
   - 修改建议：保留运行时 `runningToolEntries` 的工具名与参数，`toolFinished` 使用真实 `name/args`，只把 `state` 标记为 `skipped`。
   - 文件：`src/runtime/chat-controller.ts`、`src/runtime/ui-events.ts`、`src/runtime/ui-view-model.ts`。

2. risky 检测与告警文案不一致（P1）
   - `createPreToolCheckpoint` 会写入 `risky_multi_file_checkpoint`，但状态文案当前可能在 checkpoint 真实落盘失败或未成功时仍误导“已创建”。
   - 修改建议：基于 `createCheckpoint` 返回值与 trace 事件，先判定 `created`，再决定是否显示 rollback 文案；未创建时显示“尝试执行但未记录快照（原因...）”并保留重试建议。
   - 文件：`src/core/checkpoint.ts`、`src/runtime/chat-controller.ts`。

3. 安全分类未闭环（P1）
   - `classifyCommandSafety` 已实现，但当前执行链路主要仅用于展示，不参与高风险执行策略。
   - 修改建议：保留低风险策略（仅观测/提示），并明确在 `verification`/permission 文本中带出风险决策来源，后续再接入阻断阈值。
   - 文件：`src/services/verification-profile.ts`、`src/runtime/ui-view-model.ts`、`src/runtime/chat-controller.ts`。

4. 风险门控与 completion claim 仍需一致（P2）
   - `verificationRisky` 已记录到 trace，但 `/harness`/`/trace` 输出里要统一展示，以便用户判断“该次变更是否可能不完整”。
   - 文件：`src/services/session-storage.ts`、`src/runtime/ui-view-model.ts`、相关命令输出格式化逻辑（`/trace` / `/harness`）。

5. 长命令/长参数可追溯路径（P2）
   - 对执行命令/参数截断仍依赖状态栏/助手区推断，需统一 `/last-tool` + artifact 引用作为唯一全量入口。
   - 文件：`src/runtime/ui-events.ts`、`src/runtime/ui-view-model.ts`、命令输出命令集成文档。

`docs/targets/ui-ultimate-experience.md` 和 `docs/codex/v0.2.14-targets-remaining-work.md` 当前都未达到“收口完成”。

- `v0.2.14-targets-remaining-work.md` 明确仍在 P0–P3 列出未完成项。

## P0（本迭代必须完成）

### 1. 完成“风险命令/多文件编辑”安全闭环
- 目标：将 `classifyCommandSafety` 和 `isRiskyEdit` 真正接入 `runChat` 执行路径。
- 内容：
  - 多文件修改触发自动 checkpoint + 明确风险提示；
  - 高风险命令/高变更量操作在无确认前不直接进入 completion gate；
  - 在 tool 运行前可选择提示/确认（与现有 permission 流程统一）。
- 验收：
  - 高风险命令进入 `tool_calls` 前有决策分支；
  - 未确认不会直接进入“验证通过”状态；
  - 对应单测覆盖风险判定与门控行为。

### 2. 打通多文件 checkpoint 策略
- 目标：将 `shouldCreateMultiFileCheckpoint` 纳入 `createPreToolCheckpoint` 分支。
- 内容：
  - 在单轮多文件变更阈值（默认 5）触发 checkpoint；
  - 明确 trace 里记录 `checkpoint` 的触发策略和文件清单；
  - `/checkpoint` 查看与恢复行为与会话回滚一致。
- 验收：
  - 变更 5+ 文件时产生 checkpoint 且可恢复；
  - 对应单测覆盖阈值边界。

### 3. 终端长输出 + 活动输入稳态收口
- 目标：`Run long output while typing` 场景下输入位置不抖动、历史不污染。
- 内容：
  - 增补 `terminal-ui-pty` 自动化场景，固定覆盖：
    - 缩放触发重排；
    - assistant streaming 中键入修正；
    - tool output 与命令提示不重叠。
  - 统一把 overlay 输出和 status 输出与 transcript 分离。
- 验收：
  - 无新增行噪声；
  - 光标/输入框稳定。

## P1（下一优先）

### 4. “完整命令可追溯”能力增强
- 目标：执行大参数/大命令仍可查看完整信息。
- 内容：
  - 命令摘要超过显示上限时，必须给出 `/last-tool` 或 `/artifacts show <id> --full` 的稳定入口；
  - 终端、tui、ink 三 renderer 呈现一致。
- 验收：
  - 端到端用例确认 `last-tool` 与 `artifacts` 内容可复现。

### 5. completion/restart 统一语义
- 目标：当 `finishReason` 为 `completion_gate / budget_exceeded / interrupted` 时，UI 与 session 语义一致。
- 内容：
  - 统一 `resume` 后 `继续` 指令的目标继承检查；
  - 让 status/trace 中的 continuation 提示可复用。
- 验收：
  - 中断后再次输入不产生乱序的旧 transcript。

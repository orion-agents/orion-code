## 二、核心断路：runner 未切换到新管线

### 问题描述

`src/tui-ui/runner.ts` 仍然使用旧的 `renderTuiUiFrame` + `TuiTerminalWriter` 管线，没有切换到 `InlineTerminalSurface` + `renderTuiLiveFrame`。

### 影响范围

这一断路同时阻塞了以下切片的生产效果：

- **切片 3（Rich Transcript）**：`TranscriptLayoutCache` 是死代码——没人 import，缓存逻辑无法生效
- **切片 4（Inline Surface）**：`InlineTerminalSurface` 类完整，但 runner 不消费它的 commit/renderLive 方法，commit 边界协议无法执行
- **切片 5（Status/Timeline）**：activity/timeline 数据层到位，但 layout 无 timeline 区域渲染，`renderTuiLiveFrame` 未被调用
- **切片 6（Scheduler）**：`TuiRenderScheduler` 存在但生产路径默认禁用（`noScheduler` 默认 `true`），TranscriptLayoutCache 成为死代码，surface 做 full live-region repaint 而非 changed-row diff

### 具体证据

| 断路项 | 文件 | 代码位置 |
|--------|------|----------|
| runner 用旧 writer | `src/tui-ui/runner.ts` | 调用 `renderTuiUiFrame` 而非 `renderTuiLiveFrame` |
| TranscriptLayoutCache 死代码 | `src/tui-ui/transcript-cache.ts` | 全文件无生产路径 import |
| scheduler 默认禁用 | `src/tui-ui/render-scheduler.ts` | `noScheduler` flag 默认 `true` |
| surface 未接入 | `src/tui-ui/inline-surface.ts` | `InlineTerminalSurface` 类完整但 runner 不持有 surface 实例 |
| timeline 未渲染 | `src/tui-ui/layout.ts` | 无 `renderTuiLiveFrame` 调用或 timeline 区域 |

### 修复建议

1. runner 持有 `InlineTerminalSurface` 实例
2. dispatch 改为 reducer → effect plan → surface queue + scheduler pipeline
3. layout 切为 `renderTuiLiveFrame`（只接收 live entries + activity + overlay + status + composer）
4. 删除 `renderTuiUiFrame` compatibility wrapper（或保留但标记 deprecated）
5. 删除 `scrollTranscript` action 和 PageUp/PageDown 绑定

## 五、根因分析

### 5.1 集成断路的根因

`runner.ts` 是 TUI 的核心编排层，负责将 reducer state → layout → frame → surface 输出串联。plan 明确要求在第 4–7 步逐步替换 runner 的内部管线：

1. reducer 增加 commit boundary
2. runner 接 post-reducer effects 和 serialized surface queue
3. layout 切成 live-only input
4. launch 切 primary screen lifecycle
5. scheduler 接入 coalescing

但实际执行时，各切片的模块代码是独立提交的，没有做 runner 的管线切换这一集成步骤。结果就是所有新模块都是"可插拔但未插入"的状态。

### 5.2 Composer 未接入的根因

plan 的切片 1 要求迁移顺序是：

1. 新建 shared 文件 → 保持零行为变化
2. Ink 改 compatibility re-export
3. TUI state/runner 改 shared reducer
4. parser 区分 CR/LF/Alt+Enter
5. layout 接 prompt viewport

实际只完成了第 1–2 步（模块到位、Ink re-export），第 3 步（TUI 接入）未做。这导致后续的 Alt+Enter、多行导航、History 都无法实现。

### 5.3 模块交付完整但集成空缺的模式

这个模式在多个切片中重复出现：

- **切片 3**：parser/layout/cache 模块 ✅ → runner 接入 ❌
- **切片 4**：surface 类 ✅ → runner 持有 surface ❌
- **切片 5**：activity state ✅ → timeline layout ❌
- **切片 6**：scheduler 模块 ✅ → 生产启用 ❌

本质是"每切片交付了模块代码，但没有交付模块到 runner 的集成"。

## 九、结论

v0.2.21 的模块交付证明了架构设计的可行性——rich-text、styled frame、inline-surface、scheduler、composer 作为独立模块都能正确工作。但缺少了最关键的一步：**将这些模块串联到 runner 的生产管线中**。

v0.2.22 的首要任务是完成这个串联。管线切换完成后，切片 3–6 的效果（缓存、增量重排、timeline 渲染、性能优化）将自动生效，无需额外模块开发。

第二大任务是 Composer 接入，让 TUI prompt 拥有与 Ink 等价的多行交互能力。

完成这两项后，v0.2.22 才能达到 v0.2.21 plan 定义的全部发布验收标准。

# v0.2.11 Agent Loop Rate-Limit Optimization

## Goal

Reduce avoidable base-model pressure without changing OpenHorse's core runtime
architecture. The stable path remains:

`LLM request -> tool calls -> scheduled tool execution -> tool results -> next LLM request`.

This iteration focuses on reducing retries that immediately fail, avoiding noisy
prompt growth, and improving fallback behavior when providers throttle requests.

## Changes

- Treat generic provider throttling text as retryable:
  - `rate limit`
  - `too many requests`
  - `api-limit` / `api limit`
  - `request limit`
  - `429`
  - `temporarily throttled`
- Keep quota and credit failures non-retryable:
  - `NotEnoughCvError`
  - `insufficient_quota`
  - `quota exceeded`
  - `credit exhausted`
- Apply a stronger rate-limit backoff than normal transient errors, while still
  respecting `retry-after` when the provider returns it.
- Trigger fallback model after repeated 429/rate-limit/busy failures, not only
  provider 529 overload errors.
- Stop injecting an extra `[System] Tool ... failed` user message after failed
  tool results. The structured tool result already contains the failure, and
  the strategy tracker still injects a suggestion when repeated attempts are
  exhausted.

## Expected Impact

- Fewer failed turns caused by temporary provider throttling.
- Less prompt noise after tool failures, which reduces token use and helps the
  next model request stay focused.
- Faster recovery when a configured fallback model is available.

## Non-Goals

- No new agent runtime protocol.
- No local heuristic agent that replaces the LLM planner.
- No batching of unsafe write/edit/push commands.
- No UI renderer changes.

## Verification

- `tests/llm.test.ts`: provider busy, generic rate-limit retry, quota no-retry,
  abortable retry backoff.
- `tests/llm-fallback.test.ts`: fallback after 529 and 429 throttling.
- `tests/query.test.ts`: failed tool results do not inject extra user noise.

# OpenHorse v0.2.26 多模型配置与 `/model` 运行时切换计划

> 版本：v0.2.26
>
> 文档状态：Draft / Implementation Ready
>
> 调研日期：2026-07-22
>
> 前置基线：v0.2.23、v0.2.24、v0.2.25 完成并合入后实施
>
> 目标读者：承担架构、开发、测试、CR 和发布验证的 Coding Agent
>
> 版本主题：一个 `openhorse.json` 配置多个 Provider 和模型；`/model` 安全切换完整模型档案；用户配置的 Context 高于目录和动态发现；采样温度由 Agent 内核决定

## 1. Summary

v0.2.26 将 OpenHorse 当前的“单 endpoint + 单 API key + 默认/备用 model 字符串”升级为正式的 **Provider + Model Profile Registry**。

推荐方案不是给现有配置增加一个 model 字符串数组，而是把每个可切换模型定义成稳定的模型档案。档案同时绑定：

- 用户使用的 selector；
- Provider 配置；
- 发给 API 的真实 model ID；
- Context Window；
- Max Output Tokens；
- 显示名称和 aliases；
- 能力及采样兼容信息。

核心决策：

1. **`providers` 与 `models` 分层**：Provider 管 endpoint/auth/protocol；Model Profile 管 selector/model/context。
2. **配置模型才是“可用模型”**：内置 catalog 只提供元数据回退，不能再让 `/model list` 把未配置、未验证的模型宣称为 available。
3. **Context 字段级优先级**：`openhorse.json models.<id>.contextWindow` > Provider `/models` 动态发现 > 内置 catalog 精确匹配 > 模糊匹配 > 保守默认值。
4. **`/model` 原子切换完整档案**：同时切换 API client、endpoint、credential reference、model ID、context budget、fallback 和 diagnostics；不能只执行 `setModel(string)`。
5. **Session 连续性**：切换结果持久化到 Session/Project；`/resume` 恢复模型档案，而不是仅恢复消息。
6. **不开放 temperature 配置**：Coding Agent 的确定性请求固定为 `temperature: 0`；不支持 temperature 的推理模型完全省略该字段。
7. **Renderer 无业务决策权**：Terminal UI、TUI、Ink、Print 只消费统一的 model registry 和 `model_changed` 事件。
8. **配置采用破坏性升级**：v0.2.26 不加载旧四字段模型配置；用户必须直接把
   `openhorse.json` 修改为 `providers + models` 新结构。

## 2. 用户问题与版本目标

### 2.1 当前用户问题

当前 `~/.openhorse/openhorse.json` 只能表达：

```json
{
  "apiKey": "sk-xxx",
  "apiBaseUrl": "https://example.com/v1",
  "defaultModel": "model-a",
  "fallbackModel": "model-b"
}
```

这导致以下问题：

- 不能为不同模型配置不同 endpoint/API key；
- `/model` 只改 `LLMService.config.model`，不能切换 Provider client；
- `/model list` 来自内置静态 catalog，显示的模型不等于用户实际可用模型；
- `ProjectConfig.lastModel` 已定义但没有形成启动和恢复闭环；
- Session metadata 虽有 `model`，`/resume` 后没有恢复 LLM 当前模型；
- 自定义模型缺少 catalog 条目时会落到保守 Context 默认值；
- Provider 动态发现可能覆盖或掩盖用户明确知道的 Context；
- Compact、安全输入预算、Harness 和状态栏可能对同一模型使用不同来源的元数据；
- 固定发送 `temperature: 0.1` 不符合 Coding Agent 的确定性目标，也可能被部分推理模型拒绝。

### 2.2 v0.2.26 目标

做到：

```text
openhorse.json
  ├─ providers: endpoint / auth / protocol
  └─ models: selector / provider / API model / context / output
                  ↓
             ModelRegistry
                  ↓
      /model、启动、resume 使用同一解析器
                  ↓
       LLM + Compact + Session 原子切换
                  ↓
 Terminal / TUI / Ink / Print 一致展示结果
```

### 2.3 核心验收陈述

1. 用户配置两个模型后，`/model list` 只把已启用、可解析的档案显示为 configured models。
2. `/model deepseek` 能从 Provider A 切换到 Provider B，下一次 HTTP 请求使用 Provider B 的 endpoint、key 和真实 model ID。
3. 用户配置 `contextWindow: 1000000` 时，`/model info`、状态栏、Harness、安全预算和 Compact 都使用 1M，不被 catalog 或 `/models` 发现值覆盖。
4. 切换到更小 Context 的模型时，在发请求前重新计算安全预算；必要时由 Agent Core 执行 preflight compact。
5. 切换模型后重启并 `/resume`，恢复同一个 Model Profile；档案缺失时明确告警并使用可解释的 fallback。
6. Coding Agent 请求对兼容模型发送 `temperature: 0`；对不支持 temperature 的模型不发送该字段。
7. 旧版四字段模型配置会被明确拒绝，并输出可直接照做的迁移提示；运行时不承担兼容和自动迁移逻辑。

## 3. 当前实现审计

### 3.1 已有能力

- `GlobalConfig` 已有 `apiKey`、`apiBaseUrl`、`defaultModel`、`fallbackModel`。
- `model-catalog.ts` 已有模型别名和静态目录。
- `model-context.ts` 已有 Context、Max Output、Provider、动态发现和安全输入预算计算。
- `/model` 已支持 info、list、alias 和运行时切换 model 字符串。
- `AutoCompact.setModel()` 会在模型变化时清空 Provider token estimate calibration。
- Session metadata 已有实际 `model` 字段。
- Project 配置类型已有 `lastModel` 字段。
- Terminal、TUI、Ink 已有共享 model picker 数据结构基础。

### 3.2 已确认缺口

#### 缺口 A：配置模型与 Provider 没有实体关系

当前只创建一个 `OpenAI` client。模型切换后仍复用原 endpoint 和 API key，因此跨 Provider 模型切换在架构上不可成立。

#### 缺口 B：静态 catalog 混合了“可用性”和“元数据”

`/model list` 直接遍历静态 `MODEL_CATALOG`。这只能证明 OpenHorse 知道这些名字，不能证明当前 endpoint、账号或权限能使用这些模型。

#### 缺口 C：Context 来源优先级不满足用户意图

当前有效顺序近似为：

```text
provider discovered > builtin exact > fuzzy > default
```

缺少显式 config 层。用户无法覆盖不准确或过期的 catalog/discovery 值。

#### 缺口 D：模型切换不是事务

当前 `/model` 依次执行：

```text
llm.setModel(model string)
compact.setModel(model string)
store.currentModel = model string
```

没有 Provider client 切换、配置校验、失败回滚、Session 持久化、Project lastModel 持久化或共享 runtime 事件。

#### 缺口 E：Resume 不恢复模型运行态

`/resume` 恢复 transcript、history、compact checkpoint 和 harness，但没有以 Session 的 model 更新 LLM、Store 和 Compact。UI 显示的 Session 模型与下一次实际请求模型可能不一致。

#### 缺口 F：配置错误会静默退回默认值

全局配置解析失败时返回默认配置。JSON 错误、字段拼写、alias 冲突或 context 非法可能表现成“配置不生效”，缺少结构化诊断。

#### 缺口 G：temperature 策略与注释不一致

代码注释描述代码/分析/创意多个温度，但实际请求固定为 `0.1`。这既不是明确的任务策略，也没有处理“不支持 temperature”的模型。

## 4. 外部产品调研与可复用结论

### 4.1 Codex

[Codex Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference)
将模型选择、模型上下文、自动 Compact 阈值、Provider 配置和外部模型目录定义为独立配置项。

Codex 配置将以下概念分开：

- 当前 `model`；
- `model_context_window`；
- `model_auto_compact_token_limit`；
- `model_provider`；
- `model_providers.<id>` 的 endpoint、env key 和 headers；
- 外部 model catalog。

可复用结论：模型 selector、Provider transport、Context metadata 和 Compact threshold 应是不同层级，最终由一个 resolver 合并，而不是散落在 UI 和 LLMService。

### 4.2 OpenCode

[OpenCode Providers](https://opencode.ai/docs/providers) 和
[OpenCode Models](https://opencode.ai/docs/models) 将 Provider、Model、Context/Output limit、
`provider/model` selector 和模型选择顺序分别建模。

OpenCode 使用 provider map 和 provider 内 model map，模型可配置 `limit.context`、`limit.output`，并使用 `provider_id/model_id` 作为稳定选择方式。其模型选择考虑命令行、配置和最近使用模型。

可复用结论：

- 模型选择必须有稳定 selector，不能把展示 alias、API model ID 和 Provider ID 混为一个字符串；
- Context 与 Output 应配置在模型层；
- “已配置模型”和 Provider 自动发现模型应能区分；
- 最近使用模型适合持久化到 project state，不应覆盖全局 default。

### 4.3 Claude Code

[Claude Code CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-usage)
支持通过 `--model` 传入 alias 或完整 model name 选择当前 Session 模型。

Claude Code CLI 支持以 alias 或完整 model name 选择当前 Session 模型。

可复用结论：用户输入应支持简短 alias，但 Session 必须持久化解析后的稳定标识，避免 alias 将来变更后恢复到不同模型。

### 4.4 OpenHorse 采用的组合方案

OpenHorse 采用：

```text
Codex 的 Provider/Context 分层
+
OpenCode 的 Provider/Model registry 与稳定 selector
+
Claude Code 的轻量 alias 交互
+
OpenHorse 现有 Compact、Session、Renderer 统一事件体系
```

## 6. 配置 Schema

### 6.1 推荐完整配置

```json
{
  "defaultModel": "deepseek-pro",
  "fallbackModel": "glm-coding",
  "providers": {
    "astron": {
      "apiBaseUrl": "https://maas-coding-api.example.com/v2",
      "apiKeyEnv": "ASTRON_API_KEY",
      "protocol": "openai-chat-completions"
    },
    "local": {
      "apiBaseUrl": "http://localhost:11434/v1",
      "apiKeyEnv": "OLLAMA_API_KEY",
      "protocol": "openai-chat-completions"
    }
  },
  "models": {
    "deepseek-pro": {
      "provider": "astron",
      "model": "xopdeepseekv4pro",
      "label": "DeepSeek V4 Pro",
      "aliases": ["deepseek", "ds"],
      "contextWindow": 1000000,
      "maxOutputTokens": 16384,
      "enabled": true
    },
    "glm-coding": {
      "provider": "astron",
      "model": "xopglm51",
      "label": "GLM 5.1 Coding",
      "aliases": ["glm"],
      "contextWindow": 204800,
      "maxOutputTokens": 16384
    },
    "qwen-local": {
      "provider": "local",
      "model": "qwen2.5-coder:latest",
      "contextWindow": 32768,
      "maxOutputTokens": 8192
    }
  },
  "toolConfirmation": "allow"
}
```

### 6.2 TypeScript 数据契约

```ts
export type ModelProtocol = 'openai-chat-completions';

export interface ModelProviderConfig {
  apiBaseUrl?: string;
  apiKeyEnv?: string;
  apiKey?: string; // Direct value is allowed; apiKeyEnv is preferred.
  protocol?: ModelProtocol;
  headers?: Record<string, string>;
}

export interface ModelProfileConfig {
  provider: string;
  model: string;
  label?: string;
  aliases?: string[];
  contextWindow?: number;
  maxOutputTokens?: number;
  enabled?: boolean;
  capabilities?: {
    supportsTools?: boolean;
    supportsTemperature?: boolean;
  };
}

export interface GlobalConfig {
  defaultModel: string;
  fallbackModel?: string;
  providers: Record<string, ModelProviderConfig>;
  models: Record<string, ModelProfileConfig>;
  // Existing unrelated fields remain unchanged.
}
```

### 6.3 标识语义

| 名称 | 示例 | 语义 |
|---|---|---|
| `providerId` | `astron` | 用户配置的 Provider 稳定 ID |
| `profileId` | `deepseek-pro` | 用户和 Session 使用的稳定 selector |
| `modelId` | `xopdeepseekv4pro` | 发给 Provider API 的真实 model 字符串 |
| `alias` | `ds` | 仅用于输入便利，不作为持久化主键 |

禁止把这四者继续存放在同一个含义不明的 `model` 字段中。

### 6.4 凭证规则

1. `apiKeyEnv` 优先于同 Provider 的 `apiKey`。
2. Provider 内的 `apiKey` 允许直接配置，但推荐 `apiKeyEnv`；两者都不得在日志、trace、错误或 config summary 中输出。
3. 环境变量缺失时，Profile 标记为 unavailable；启动可继续，但选择该模型必须失败并给出变量名。
4. Provider headers 中疑似 secret 的键值使用统一 redaction。
5. Session 和 checkpoint 只保存 `providerId/profileId/modelId`，不保存 key、endpoint headers。

### 6.5 配置校验

启动时构建结构化 `ConfigDiagnostic[]`，至少校验：

- `providers`、`models` 必须存在、为 object 且至少包含一项；
- 根级 `apiKey`、`apiBaseUrl` 视为已删除字段并报迁移错误；
- Provider ID 和 Profile ID 非空且大小写归一后唯一；
- `provider` 必须存在；
- `model` 必须非空；
- aliases 不能与 Profile ID、其他 alias 冲突；
- `contextWindow` 必须为正整数；
- `maxOutputTokens` 必须为正整数且小于 `contextWindow`；
- `defaultModel`、`fallbackModel` 必须能解析到 enabled Profile；
- protocol 必须在支持集合内；
- 用户提供 `temperature` 时输出 unsupported configuration error 并停止启动，绝不传入请求。

致命错误必须阻止 LLM 初始化；非致命错误允许启动并通过 `/doctor` 展示。不能再把整个文件解析错误静默变成默认配置。

## 7. 配置迁移与 Session 兼容

### 7.1 `openhorse.json` 破坏性升级

v0.2.26 只接受 `providers + models` 新 Schema，不实现旧配置合成器、混合模式或兼容分支。

旧配置：

```json
{
  "apiKey": "sk-xxx",
  "apiBaseUrl": "https://example.com/v1",
  "defaultModel": "model-a",
  "fallbackModel": "model-b"
}
```

必须由用户手动改为：

```json
{
  "defaultModel": "primary",
  "fallbackModel": "fallback",
  "providers": {
    "main": {
      "apiBaseUrl": "https://example.com/v1",
      "apiKeyEnv": "OPENHORSE_MAIN_API_KEY",
      "protocol": "openai-chat-completions"
    }
  },
  "models": {
    "primary": {
      "provider": "main",
      "model": "model-a",
      "contextWindow": 128000,
      "maxOutputTokens": 8192
    },
    "fallback": {
      "provider": "main",
      "model": "model-b",
      "contextWindow": 128000,
      "maxOutputTokens": 8192
    }
  }
}
```

当检测到根级 `apiKey`、`apiBaseUrl`，或缺失 `providers/models` 时：

- 启动失败，不创建隐式 Provider/Profile；
- 错误明确指出旧字段和目标 Schema；
- 指向 `docs/openhorse.example.json` 与配置参考；
- 不修改用户文件；
- 不允许 `/model <raw-model-id>` 绕过 Registry；
- 不产生 deprecation-only warning 后继续运行。

### 7.2 严格 Registry 规则

- `providers` 和 `models` 都必须存在、为 object 且至少包含一项；
- `defaultModel/fallbackModel` 只表示 Profile selector；
- selector 不得按唯一 model ID 猜测配置意图；alias 必须显式声明；
- `/model` 只接受 Registry 中的 Profile ID、显式 alias 或唯一 `provider/model`；
- `/doctor` 只报告 `registryMode: configured`，不维护旧模式分支；
- 环境变量只通过 Provider 的 `apiKeyEnv` 引用，不再覆盖已经删除的根级模型字段。

### 7.3 Session 兼容

Session metadata 新增可选字段，不删除旧字段：

```ts
interface SessionMeta {
  model: string; // 保留：用户选中 Profile 的 provider model ID
  modelProfileId?: string; // 用户选中且应在 resume 恢复的 Profile
  modelProviderId?: string; // 用户选中 Profile 的 Provider
  lastResponseModelProfileId?: string; // 可选：最后一次响应实际使用的 fallback Profile
  modelConfigFingerprint?: string;
}
```

旧 Session 只有 `model` 时按以下顺序恢复：

1. 唯一 Profile 的 `modelId` 精确匹配；
2. Profile ID/alias 精确匹配；
3. 找不到时恢复历史，但警告模型已不可用，并使用当前启动 selector。

不能因为旧模型已删除而拒绝恢复 Session transcript。

## 8. 核心架构

### 8.1 组件关系

```text
GlobalConfig loader
       │
       ├─ validation diagnostics
       ▼
ModelRegistryBuilder ───── Provider discovery cache
       │                         │
       └──────── merge metadata ┘
                   │
                   ▼
          ResolvedModelRegistry
                   │
       ┌───────────┼───────────────┐
       ▼           ▼               ▼
 ModelCoordinator  ContextResolver  /doctor + /model list
       │           │
       │           ├─ safe budget
       │           ├─ compact
       │           └─ harness
       ▼
 LLM Provider Client Pool
       │
       ├─ Session/Project persistence
       └─ Runtime model_changed event
```

### 8.2 `ResolvedModelProfile`

```ts
export interface ResolvedModelProfile {
  profileId: string;
  providerId: string;
  modelId: string;
  label: string;
  aliases: string[];
  enabled: boolean;
  available: boolean;
  unavailableReason?: string;
  protocol: ModelProtocol;
  apiBaseUrl?: string;
  credentialRef?: { type: 'env' | 'inline' | 'none'; name?: string };
  headers: Record<string, string>;
  contextWindow: number;
  maxOutputTokens?: number;
  capabilities: {
    supportsTools: boolean;
    supportsTemperature: boolean;
  };
  sources: {
    contextWindow: ModelMetadataSource;
    maxOutputTokens: ModelMetadataSource;
    provider: 'config';
    capabilities: ModelMetadataSource;
  };
}

export type ModelMetadataSource =
  | 'config'
  | 'provider_discovered'
  | 'builtin_exact'
  | 'builtin_fuzzy'
  | 'default';
```

运行时对象可以持有解析后的 credential value，但任何可序列化、日志或 UI 对象只能持有 `credentialRef`。

### 8.3 `ModelRegistry`

建议新增 `src/services/model-registry.ts`，提供：

```ts
interface ModelRegistry {
  listConfigured(): ResolvedModelProfile[];
  listDiscovered(): DiscoveredModelProfile[];
  resolve(selector: string): ModelResolutionResult;
  get(profileId: string): ResolvedModelProfile | undefined;
  getDefault(): ResolvedModelProfile;
  getFallback(): ResolvedModelProfile | undefined;
  getDiagnostics(): ConfigDiagnostic[];
  getFingerprint(): string;
}
```

要求：

- Registry 在一次启动周期内不可变；
- aliases 在构建阶段建立 normalized index；
- 列表排序确定：default、configured order、Profile ID；
- fingerprint 排除 secret value，只包含会影响模型解析的字段；
- 不使用跨 Runtime 的可变全局 singleton；
- 测试可以注入 registry 和 discovery adapter。

### 8.4 Context 字段级合并

每个字段独立解析，不能因为 catalog 命中就整对象覆盖：

```ts
contextWindow =
  profile.contextWindow
  ?? discovered.contextWindow
  ?? builtinExact.contextWindow
  ?? builtinFuzzy.contextWindow
  ?? DEFAULT_CONTEXT_WINDOW;

maxOutputTokens =
  profile.maxOutputTokens
  ?? discovered.maxOutputTokens
  ?? builtinExact.maxOutputTokens
  ?? builtinFuzzy.maxOutputTokens;
```

最终优先级：

```text
显式用户 config
    > 当前配置 Provider 的动态发现
    > builtin catalog 精确 model ID
    > builtin catalog 模糊/alias 匹配
    > 保守默认值
```

这比仅规定“config 高于 catalog”更严格：用户配置也高于 discovery，因为用户可能在 Provider `/models` 返回错误或过期数据时进行纠正。

`ModelContextResolution` 增加 `profileId`、`providerId`、`fieldSources`，保留现有 `source` 作为兼容摘要字段。

### 8.5 Provider discovery

- 每个 Provider 最多启动一个后台 discovery 请求；
- 同 endpoint/auth fingerprint 的 Provider 可共享结果；
- discovery 失败不阻塞启动；
- 设置短期内存缓存和超时；
- discovery 只补全未显式配置字段；
- discovered 模型默认不进入 configured list；
- `/model list --all` 可在 P1 中展示 discovered candidates；
- discovery 的 raw response 不写入 Session，不记录 secret headers。

## 9. 模型选择优先级

配置字段合并优先级与“当前 Session 选择哪个模型”是两件事，必须分别定义。

### 9.1 初始模型选择

```text
CLI --model/-m
  > 当前命令显式 /model 选择
  > /resume Session.modelProfileId
  > ProjectConfig.lastModelProfileId
  > GlobalConfig.defaultModel
  > 第一个 enabled + available Profile
```

说明：

- 增加 `--model <profile|alias>` / `-m`，真正实现 CLI 最高优先级；
- CLI override 仅影响本次进程，不改全局 default；
- `/model` 更新当前 Session 和 project last model，不改全局 default；
- `/resume` 是显式用户动作，恢复 Session 模型高于 project last model；
- 若 CLI 带 `--model` 后再 `/resume`，默认以 Session 模型为准，并输出恢复提示；未来可增加 `--keep-model`，不属于 P0。

### 9.2 Fallback 选择

`fallbackModel` 同样解析为 Profile。Fallback 必须允许跨 Provider，但切换必须复用 v0.2.25 的 request resilience policy：

- 只在策略允许时 fallback；
- 每个逻辑请求记录 from/to profile；
- fallback 是请求级选择，不永久修改用户选中的 Profile、Project last model 或全局 default；
- Session 的 `modelProfileId` 保存用户选中的 Profile，实际完成 turn 的 fallback Profile 只写入
  `lastResponseModelProfileId`、usage 和 trace；
- 下一 turn 默认重新从用户选中的 Profile 开始；若 v0.2.25 熔断器要求暂时继续 fallback，必须由显式 policy 决定，不能由 `LLMService` 隐式 mutable state 决定。

## 11. 原子模型切换事务

### 11.1 新增 `ModelCoordinator`

建议新增 Runtime 独享的 `src/runtime/model-coordinator.ts`：

```ts
interface ModelCoordinator {
  current(): ResolvedModelProfile;
  switchModel(selector: string, options: SwitchModelOptions): Promise<ModelSwitchResult>;
  restoreModel(session: SessionMeta): Promise<ModelRestoreResult>;
}
```

### 11.2 切换步骤

```text
1. resolve selector
2. validate available + credential + protocol
3. require runtime idle / acquire model-switch mutex
4. prepare Provider client
5. calculate new ContextUsageSnapshot
6. if current history exceeds new safe budget, prepare preflight compact
7. prepare an atomic Session metadata write when a Session exists
8. commit Session metadata as the durable switch record
9. synchronously swap LLM active profile + Compact model + Store snapshot
10. best-effort persist Project lastModelProfileId preference
11. emit model_changed
```

### 11.3 失败与回滚

- 1 至 7 任一步失败：保持原模型，不更新 Store/Session/Project；
- Provider client 初始化失败：销毁临时 client；
- preflight compact 失败：默认拒绝切换并说明当前历史无法安全放入目标模型；
- Session metadata 原子写失败：切换不提交；
- Session metadata 已提交后，步骤 9 必须是不可失败的同步引用交换；若实现中仍可能抛错，必须先引入
  switch journal/recovery，不能留下持久化目标与运行时模型不一致；
- Project last model 是启动偏好缓存，写入失败不回滚已提交的 Session/runtime 切换，但必须告警并在结果中标记
  `projectPreferencePersisted: false`；
- 成功事件只能在全部核心状态提交后发送；
- 不允许 UI 先显示“changed”再异步失败。

### 11.4 Provider client pool

将 `LLMService` 从“一个 client + 可变 model 字符串”重构为：

```ts
class LLMService {
  constructor(
    private readonly clientPool: ProviderClientPool,
    initialProfile: ResolvedModelProfile,
  ) {}

  setActiveProfile(profile: ResolvedModelProfile): void;
  getActiveProfile(): ResolvedModelProfile;
}
```

Client Pool：

- 以 `providerId + non-secret config fingerprint` 为 key；
- credential value 不参与可见日志；
- v0.2.25 必须关闭 SDK 隐式 retry，Pool 不能重新引入双层重试；
- 请求开始时捕获 immutable profile snapshot，避免 mid-stream 切换导致同一请求混用两套配置；
- 同一逻辑请求的 retry/fallback 必须显式选择 Profile。

## 12. Compact 与 Context 安全

### 12.1 全链路使用同一个 Profile

以下路径必须改为接收 `ResolvedModelProfile` 或 registry-backed resolver，不能只传裸 model ID：

- `query()` assembled prompt 估算；
- `AutoCompact`；
- `CompactCoordinator`；
- Harness assembler；
- status/context display；
- Session compact checkpoint；
- Provider estimate correction；
- max output reserve。

### 12.2 切换到更小 Context

模型切换前计算：

```ts
safeInputBudget = Math.max(
  1,
  contextWindow - outputReserve - safetyMargin,
);
```

如果当前 assembled history 达到目标 Profile 安全预算的 95%：

- Agent Core 执行 preflight compact；
- UI 仅显示 `compacting_before_model_switch`；
- compact checkpoint 记录目标 `modelProfileId` 和 Context snapshot；
- compact 成功后再提交模型切换；
- compact 后仍超限则拒绝切换。

### 12.3 Provider 校准

Provider prompt-token correction 至少按 `providerId + modelId` 分区。模型或 Provider 变化时不能复用旧模型 correction；切换后以目标档案重新建立校准。

## 13. Temperature 与采样策略

### 13.1 产品决策

v0.2.26 **不允许用户在 `openhorse.json`、CLI 或 `/model` 配置 temperature**。

理由：

- OpenHorse 是 Coding Agent，不是通用创意写作 UI；
- 代码生成、工具参数、补丁、测试、review、compact 和 goal continuation 更需要确定性；
- 用户配置会让同一模型档案在不同机器上产生难以复现的行为；
- 部分 reasoning model 固定或拒绝 temperature；
- 在没有 eval 证明前，不应按“代码 0.1 / 分析 0.3 / 创意 0.7”猜测任务类型。

### 13.2 内核策略

新增 `src/services/sampling-policy.ts`：

```ts
type AgentRequestKind =
  | 'agent_turn'
  | 'compact_summary'
  | 'goal_continuation'
  | 'subagent'
  | 'stream_recovery';

function resolveSamplingParams(
  profile: ResolvedModelProfile,
  _kind: AgentRequestKind,
): { temperature?: number } {
  return profile.capabilities.supportsTemperature
    ? { temperature: 0 }
    : {};
}
```

P0 所有 request kind 使用相同确定性策略：

- 支持 temperature：发送 `0`；
- 不支持或未知为不支持：省略；
- 禁止继续固定发送 `0.1`；
- 请求 trace 可记录 `samplingPolicy: deterministic_zero|temperature_omitted`，不记录用户秘密。

### 13.3 能力来源

`supportsTemperature` 优先级：

```text
config capabilities override
  > builtin exact capability metadata
  > protocol/model family adapter
  > conservative default
```

保守默认建议：OpenAI-compatible 普通 chat model 为 `true`；已知 reasoning family 为 `false`。配置仅用于能力声明，不允许直接提供 temperature 数值。

### 13.4 未来扩展门槛

只有建立任务级 eval，证明某类非代码任务在较高 temperature 下质量提升且不降低工具正确率后，后续版本才可增加内部 policy。此扩展仍不等于开放用户配置。

## 14. Session、Project 与 Resume

### 14.1 持久化字段

- `SessionMeta.modelProfileId`：稳定 Profile ID；
- `SessionMeta.modelProviderId`：诊断辅助；
- `SessionMeta.model`：用户选中 Profile 的 API model ID，兼容旧消费者；
- `SessionMeta.lastResponseModelProfileId`：最后响应实际使用的 fallback Profile，仅用于诊断，Resume 不以此覆盖用户选择；
- `SessionMeta.modelConfigFingerprint`：非 secret registry fingerprint；
- `ProjectConfig.lastModelProfileId`：替代含义不明确的 `lastModel`；旧字段不再读取。

Compact checkpoint 同步新增可选 `modelProfileId`、`modelProviderId`，旧 checkpoint 继续可读。

### 14.2 `/resume` 顺序

```text
1. load Session + checkpoint + transcript
2. resolve saved modelProfileId
3. validate current registry availability
4. ModelCoordinator.restoreModel()
5. restore model history and compact state
6. update Store and renderer
7. emit session_restored with model metadata
```

模型恢复必须发生在下一次 turn 前。

### 14.3 档案变化处理

如果 Session fingerprint 与当前 registry 不同：

- Profile 仍存在：使用当前配置，输出 endpoint/context may have changed 的简短 warning；
- Profile 已删除：恢复 transcript，使用当前 default，明确显示 requested/restored profile；
- Context 变小：执行与手动切换相同的 preflight compact；
- credential 缺失：不发请求，保留恢复后的 transcript，并引导设置对应 env。

- client 创建失败不提交；

### 19.6 Session/Resume 测试

- `/model` 更新 Session、Project 和 Store；
- resume 恢复 Profile/client/context；
- old Session 以 model ID 唯一匹配 Profile；
- Profile 删除时 transcript 仍恢复；
- fingerprint 变化给出 warning；
- Context 缩小触发 preflight compact；
- key 缺失时不发送下一请求；
- checkpoint 和 Session 的模型元数据一致。

### 19.7 Renderer parity 测试

- 四种 Renderer 收到相同 Profile list 数据；
- Terminal 输出完整列表；
- TUI/Ink picker 选择结果提交相同 selector；

### 19.8 真实 smoke

至少执行：

1. 同 endpoint 两个真实 model ID 切换；
2. 两个 Provider Profile 跨 endpoint 切换；
3. 明确配置一个与 catalog 冲突的 Context；
4. 切换后发一个 tool-bearing coding turn；
5. 退出并 `/resume`，再次发请求；
6. 检查 trace 中 endpoint/model/profile 正确且无 key。

真实 smoke 必须受用户凭证和配额条件约束，失败时区分 OpenHorse 问题与 Provider/quota 问题。

## 20. Delivery Gates

### Gate A：配置正确性

## 22. 风险与控制

### 风险 A：把多模型做成巨大的 LLMService 重写

控制：先建立 Registry 和 Profile snapshot，再以 Client Pool 渐进替换；每个 Slice 保持可测试。

### 风险 B：动态发现覆盖用户配置

控制：字段级 resolver 固化 `config > discovery > builtin > default`，用冲突值测试证明。

### 风险 C：切小模型时 Context overflow

控制：切换事务提交前进行目标模型安全预算和 preflight compact。

### 风险 D：Resume 恢复消息但模型不一致

控制：模型恢复纳入 `restoreSession` 顺序和集成测试，检查实际 mock endpoint。

### 风险 E：Provider key 泄漏

控制：运行时 secret 与可序列化 Profile 分离；fingerprint 排除 secret value；CR 搜索 trace/session fixtures。

### 风险 F：破坏性配置升级导致启动失败

控制：发布说明和配置参考提供完整 before/after 示例；启动错误精确指出旧字段，且不提供隐式兼容或 raw model 绕过路径。

### 风险 G：temperature=0 被 Provider 拒绝

控制：能力驱动的 0/omit policy；reasoning families 默认 omit；真实 Provider smoke 验证。

## 23. 完成定义

v0.2.26 只有同时满足以下条件才算完成：

1. 一个 `openhorse.json` 能配置多个 Provider 和多个模型档案。
2. `/model` 可以按 Profile/alias 列出和切换，跨 Provider 请求经自动化验证。
3. 用户 Context 配置高于 discovery 和 catalog，并在全部预算/Compact/Harness 路径一致生效。
4. 切换是可回滚事务，不产生 LLM、Store、Session 和 UI 状态分裂。
5. Session/Project 持久化模型选择，`/resume` 恢复实际运行态。
6. 新配置 Schema 为必需；旧配置明确失败，旧 Session 仍可恢复且不发生破坏性改写。
7. temperature 不对用户开放，Coding Agent 使用统一的 0/omit 策略。
8. Terminal、TUI、Ink、Print 通过 parity 和 PTY 验收。
9. build、lint、full test、pack dry-run、diff check 和真实 smoke 有可复核记录。
10. 配置、日志、Session、trace 和 UI 中没有 secret 泄漏。

未满足任一 P0 Gate 时，版本结论为 **NO-GO**，不能仅凭 build 或 focused tests 通过进入发布流程。

# v0.2.10 Batched Tool Calls 优化方案

## 背景

当前 OpenHorse 已支持单次模型响应返回多个 `tool_calls`，并且 `tool-scheduler` 可以并发执行并发安全工具。但实际运行中，模型经常一次只调用一个命令，导致流程变成：

1. 调用基模决定执行一个工具。
2. 本地执行工具。
3. 再调用基模读取结果。
4. 再决定下一个工具。

这会显著增加基模请求次数，在长任务和工具密集任务里更容易触发限流。

## 目标

- 优先让模型在一次推理里返回多个独立只读工具调用。
- 本地批量并发执行安全工具，并按原始顺序回传结果。
- 写操作、需要确认的工具、存在任务漂移风险的工具继续串行执行。
- 不改变现有工具协议和 session schema，保持兼容。

## 现状

- `src/framework/tool-scheduler.ts` 已有 `prepareToolCalls`、`executeToolCalls`、`inspectSchedule`。
- `glob`、`grep`、`list_files`、`web_search`、`web_fetch` 等工具已标记 `isConcurrencySafe`。
- `read_file` 目前只标记 `isReadOnly`，缺少并发安全标记。
- `exec_command` 能判断只读命令，但未把只读命令标记为可并发。
- system prompt 没有明确要求模型批量发起只读工具调用。

## 设计

### 三层优化边界

本轮不是单点“并发工具”优化，而是按三层收敛 coding-agent 的模型往返成本：

1. **上下文层：Harness + auto compact 降噪**
   - 通过模型 context window 感知、predictive compact、`/harness explain` 指标，避免把无关历史、长工具输出和重复短反馈持续塞入 prompt。
   - 目标是减少每次请求的 prompt 噪音和上下文溢出概率。
2. **模型工具层：Prompt + scheduler 批量 tool calls**
   - system prompt 明确要求模型一次提出多个独立只读工具调用。
   - `tool-scheduler` 对并发安全工具按窗口执行，默认 `maxParallelToolCalls = 6`，写操作/确认操作继续串行。
3. **本地 fallback 层：`batch_read` 只读探索批处理**
   - 当模型或 provider 习惯一次只发一个 tool call 时，模型可调用 `batch_read`，一次提交最多 8 个只读探索步骤。
   - `batch_read` 只允许 `git_status`、`list_files`、`glob`、`grep`、`read_file`，每步仍走现有 `executeTool` 路径并输出保序摘要，避免绕过权限/工具协议。

这三层分别减少“prompt 过大”“模型多轮决策”“单工具往返”三类成本，最终目标是降低 provider 限流概率，并让 agent 在工具密集任务中持续推进。

### 1. Prompt 策略

在 system prompt 的 tools 段加入批量工具策略：

- 探索、诊断、阅读代码时，先批量调用独立只读工具。
- 同一次响应里可同时调用 `git_status`、`list_files`、`glob`、`grep`、`read_file`、LSP hover/references、只读 `exec_command`。
- 若 provider 或模型只倾向一次发一个工具，可用 `batch_read` 合并最多 8 个只读探索步骤。
- 不要把写文件、编辑、push、需要确认的命令放进批量组。
- 工具结果回来后再综合判断下一步，避免每查一个文件都重新请求模型。

### 2. Scheduler 并发上限

保留现有并发组能力，但新增 `maxParallelToolCalls`，默认 6，防止一次性启动过多本地命令或网络请求。

执行规则：

- 连续的并发安全工具按窗口分批执行。
- 每批内并发执行，批与批之间串行。
- 非并发安全工具会 flush 当前并发批次，然后单独执行。

### 3. 工具标记

- `read_file` 标记为 `isConcurrencySafe: true`。
- `exec_command` 在 `isReadOnlyCommand(command)` 为 true 时标记为并发安全。
- 未来可把 LSP read-only 工具逐步标记为并发安全。

### 4. 可观测性

- 保留 query event 中的 `batchCount/batchIndex`。
- UI 将 `Turn N...` 换成更明确的 `Thinking...` / `Reading tool results...` / `Running N tools...`，避免用户误以为每个本地工具执行都重新请求了基模。
- 后续 `/doctor` 可报告并发安全工具数量。

### 5. 协作执行流

后续同类任务采用三智能体协作：

- 主 agent：调度范围、拆分任务、集成变更、最终验证。
- plan 子智能体：先给设计方向、风险、优先级，不直接改代码。
- coding 子智能体：负责限定文件范围内的实现，不回滚他人改动。
- review 子智能体：在主 agent 集成后做代码审查，重点看回归风险、测试缺口和架构边界。

## 验证

- `prompt.test.ts`：system prompt 包含批量只读工具策略。
- `tool-scheduler.test.ts`：并发上限生效，超过上限时分批执行。
- `tools.test.ts`：`read_file` 与只读 `exec_command` 标记为可并发。
- `query.test.ts`：已有多工具并发回归继续通过。

## 成功标准

1. 模型在 repo 探索场景更倾向一次返回多个 read-only tool calls。
2. 同批只读工具本地并发执行，减少模型往返次数。
3. 写操作、确认操作、风险操作不被并发执行。
4. 完整测试通过，不破坏 session/tool_calls 存储兼容。

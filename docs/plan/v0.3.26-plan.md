## 1. #274 (Bug) — SQL comment edits disappear from the structured Git diff

**Reported symptom**: deleting a source line beginning with `-- ` produces a
unified-diff body line beginning with `--- `; the parser mistakes it for an old-file
header, closes the active hunk, and treats the remaining body as document metadata.
A two-line `query.sql` edit yields an empty hunk, zero additions/deletions and
`completeness: limited` where the raw diff has 2 additions and 2 deletions.

**Source-confirmed root cause** — `src/web/git-diff-document.ts`,
`parseGitDiffDocument()`: the `isMetaLine()` header check runs against every line,
including lines inside an active hunk body. A deletion row whose text starts with
`-- ` (`--- old comment`) matches `line.startsWith('--- ')`, so the parser closes the
hunk and pushes the row to document `meta`; every following row then lands before
the first hunk and is also pushed to `meta`.

**Fix**: classify by the body marker first. While a hunk is active, a line whose
first character is `+`, `-`, ` ` (or which is empty, the empty-context case) is a
body row; `isMetaLine()` is consulted only for lines that carry no body marker —
which is exactly the set of genuine document-level lines, because a real file
boundary is always announced by `diff --git` (a line with no leading marker can
never be a body row: context rows start with a space, additions with `+`,
deletions with `-`). Unrecognized markerless lines keep their existing in-hunk
`meta` line kind. Hunk completeness then accounts for the deletion rows, so
`completeness` reports `complete`.

**Tests** (`tests/web-git-versions.test.ts`): the issue's exact fixture —
`query.sql` changing `-- old comment` / `SELECT 1;` to `-- new comment` / `SELECT 2;`
→ 2 additions, 2 deletions, one complete hunk, empty document meta. Companion
cases: an added line starting with `++ `, a context line starting with `-- `, and a
multi-file page still splitting at `diff --git`.

## 2. #275 (Bug) — Structured diff pagination drops continuation rows inside a large hunk

**Reported symptom**: a hunk spanning the 240-line page boundary loses its
continuation rows: later pages put diff body rows into `meta`, return no hunks, and
the last page reports `completeness: complete`. A 300-line replacement yields 234
deletions and zero additions as structured rows across all pages, while the raw
pages still contain the missing 366 change rows.

**Source-confirmed root cause** — `parseGitDiffDocument()` parses every page
independently and only opens a hunk on a `@@` header line. A continuation page
starts mid-hunk (no header), so every row lands in `meta`. The page cursor
(`encodeCursor`/`encodeCommitDiffCursor`) carries only an offset — no hunk state —
so the parser cannot resume.

**Fix** (per the issue's suggested direction — retain parser state in the
continuation contract):
- `GitDiffDocumentV2` gains `pendingHunk: GitDiffHunkResumeV1 | null` — the hunk
  still open when a page ends (only when the page has more lines). The resume state
  carries `header`, `index`, and the running `oldCursor`/`newCursor` so resumed rows
  keep correct line numbers and the hunk keeps its stable
  `${index}:${oldStart}:${newStart}` identity across pages.
- `parseGitDiffDocument()` accepts an optional `resume` input: when a page's first
  line is not a `@@` header and a resume state is supplied, the hunk opens from it.
- Both cursor encoders gain the optional resume state (HMAC'd `diff` cursor and the
  base64url commit/compare cursor); decoders validate it when present, so cursors
  minted before this change decode unchanged. All three `diffDocument()`-family
  call sites pass the resume state into the parser and re-mint the next cursor with
  the parsed `pendingHunk`.
- Completeness stays truthful: a hunk is `complete` when its cursors reach the
  header's promised counts, now including resumed pages.

**Tests** (`tests/web-git-versions.test.ts` / `tests/web-git-history.test.ts`):
the issue's scenario — replace all 300 lines of a file, follow every cursor of
`diffDocument()`, assert the union of rows covers 300 additions and 300 deletions
with contiguous line numbers and `completeness: complete` on the last page; plus a
small-file unpaged case and a page boundary that falls exactly at a hunk end.

## 3. #276 (Bug) — Permanent Session deletion leaves v2 Thread records behind

**Reported symptom**: deleting a cutover Session removes its legacy metadata and
catalog entry but leaves the v2 authoritative records on disk: cutover entry, event
log, head, projection, import receipt and transcript pages. `deleteSession()`
returns `true` and the Web dialog promises permanent deletion.

**Source-confirmed root cause** — `src/services/session-storage.ts`,
`deleteSession()`: the path list covers only legacy files (meta, messages, harness,
compact, trace, goal) plus the catalog entry. The v2 layout —
`getProjectThreadsV2IndexPath` (cutover index mapping sessionId → threadId) and the
per-thread files under `getProjectThreadsV2Dir` (`<threadId>.events.v1.jsonl`,
`.projection.v1.json`, `.head.v1.json`, `.compact-state.v1.json`,
`.compact-checkpoints.v1/`, `.session-index.v1.json`, `.transcript-pages.v1/`, and
the import receipt) — is never consulted. `ThreadEventStore` has no removal API.

**Fix**: `deleteSession()` removes the v2 records for the deleted Session: read the
cutover index entry for the session id, delete the thread's files and directories
(events, projection, head, compact state, compact checkpoints, session-index
manifest, transcript pages, import receipt), and remove the cutover index entry
under the index file lock with the same atomic-write discipline the materializer
uses (generation bumped; an emptied index keeps its file with an empty session map
so readers stay on the atomic authority). Unrelated Sessions' threads are
untouched; a missing entry makes the v2 step a no-op.

**Tests** (`tests/session-storage.test.ts` or the cutover regression file):
materialize a Session (the issue's fixture), delete it while idle, assert the
cutover entry, event log, head, projection, import receipt and transcript pages are
gone while an unrelated Session's v2 records remain intact.

## 4. #277 (Bug) — Exiting a cutover Session rewrites its summary from the old JSONL

**Reported symptom**: after a legacy Session is cut over and receives a new turn,
`/exit` rewrites its listing summary from the frozen legacy JSONL — message count
and history size move backwards even though the authoritative Thread history is
intact. Reopening the Session repairs the metadata from v2.

**Source-confirmed root cause** — `src/commands/core-command-handlers.ts`
`handleExit()` and the shutdown path in `src/runtime/product-bootstrap.ts` both call
`readSessionMessages(sessionId)` (the legacy JSONL, frozen at cutover) and then
`updateSessionSummary(sessionId, messages)`, which re-derives
`messageCount`/`historySizeBytes` from those legacy messages and writes them into
the session meta. The reopen path repairs them via `loadThreadSessionViewV1` —
already imported by session-storage — which is why reopening fixes the display.

**Fix**: `updateSessionSummary()` becomes v2-aware. Inside the session lock it
first loads the authoritative Thread view; when the Session is cut over, the
summary's `messageCount`, `historySizeBytes` and `updatedAt` come from that view
(the legacy summary path is skipped), so an exit can no longer regress a cutover
Session. Both callers are fixed by this single change; the legacy path is
unchanged for non-cutover Sessions.

**Tests** (`tests/session-composer-control.test.ts`-adjacent session-storage tests
or a focused regression): cut over a Session, append a v2 turn, call
`updateSessionSummary()` the way `handleExit` does, and assert the meta keeps the
v2 message count and history size; a legacy Session still summarizes from its
JSONL.

## Test matrix & gates

Per commit: targeted Jest suites. Before push: full Jest, lint, `tsc --noEmit` (root
+ web), build, `release:check`. CI: critical journey ×3, three-consecutive-runs
3×105, Node 22/24/26 matrices. Known environment-flaky suites (PTY smoke, settings
watcher under parallel load) are judged per the four-state evidence convention.

## Risks

1. **#274 classification change** touches every structured-diff read. Mitigated by
   the marker-first rule (boundary announcements are markerless by construction)
   and multi-file page tests.
2. **#275 cursor extension** changes a signed contract. The resume field is
   optional and validated when present; cursors without it decode as before, and
   the HMAC scope binding is unchanged.
3. **#276 deletes durable files.** Deletion only touches threads named by the
   cutover index entry of the deleted Session, under the existing session lock plus
   the index lock; unrelated Sessions are explicitly asserted intact.

## Non-goals

No protocol breaking changes (both cursor extensions are additive and optional); no
new diff features; no change to the archive/delete listing semantics beyond the v2
cleanup; no Agent capability changes.

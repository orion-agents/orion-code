# v0.3.12 Web Workbench：验收复盘与收口计划（v2）

- 目标版本：`v0.3.12`（修正性收口，不另行升版本）。
- 审查基线：`codex/v0.3.12`，`33f87fb8208874f975a04108d93989daf03fe399`，工作树干净。
- 审查日期：2026-09-06。
- 范围：核验上一版计划中承诺的 Right Workspace、五类面板、Context V2 与真实 E2E；本文件是后续开发清单，不代表已发布。

## 1. 结论

**v0.3.12 目前不符合可发布预期，应按 P0 收口后再进入发布门禁。**

已确认的正向结果：项目可以构建；右侧 rail、五个既有面板、`file_range` 的版本绑定解析、Review 验证分页 Host 端点、Git mutation 与工作区搜索的底层测试均有实现或测试资产。

但用户最核心的“右边栏可像 Codex 一样大幅侵占对话空间”没有接入实际 App 主路径：`App.tsx` 仍调用 v2 的 `computeWorkbenchColumns`，而该模型把工作面板硬限制在 720px。新建的宽屏几何和 per-workspace v3 偏好仅被其单测引用，运行时没有消费。真实浏览器会话 E2E 也在 readiness 断言处失败，尚不能作为端到端通过证据。

## 3. 根因与收口原则

### 3.1 根因

1. 新代码以“纯函数/底层服务”形式加入，但没有替换 `App` 的旧 layout state 和旧 API 调用链，形成平行实现。
2. 相关单测验证的是新模块本身，未验证它是否被生产入口调用；因此出现“48 tests 全绿、真实需求仍不可见”。
3. 真实 E2E 的 readiness locator 绑定了易变展示文案，UI 文案调整后把会话流测试完全短路。
4. 先前 S2–S4 的 Host 能力没有形成 UI → action → Host → revision refresh 的闭环，导致“服务存在”被误当成“用户可用”。

### 3.2 约束

- 只以一个运行时 layout schema、一个列计算函数、一个右栏宽度定义为准；详情宽度不含 48px rail。
- 宽度、会话切换、资源刷新均不得触发 `activateContext`、Runtime 重连或额外 PTY 创建。
- Git 保持明确安全边界：只允许 stage、unstage、commit；不增加 push/pull/fetch/reset/discard/checkout/merge/rebase。
- v0.3.12 的原计划文件必须随实现分支提交；当前实施 worktree 未包含该计划文档，v2 合入时一并补齐文档追踪。

## 4. 修正实施切片

### S0 — 先恢复真实验证（P0）

1. 将 `waitForWorkbenchReady` 改为稳定语义：等待可操作的 Host-connected status（建议 `data-testid="runtime-connection-state"` 或语义 role/状态枚举），不匹配具体中文展示文案。
2. 重新跑 `WEB33-P0-15`，使其确实走到：创建会话 → 输入 prompt → 提交 → SSE assistant article → composer 恢复可发送。
3. 在失败时保留 trace、error-context、截图与 Host evidence manifest；通过时记录实际 source SHA、tarball digest、浏览器版本与无 console/page/5xx 异常。

**完成标准：** 该真实会话 E2E 在打包安装的 `0.3.12` artifact 上通过，不能仅把断言删掉或以 mock 请求替代。

### S1 — 让 Wide Right Workspace 成为唯一生产路径（P0）

1. 在 `App.tsx` 以 `computeWideDesktopColumns` / `computeRightWorkspaceGeometry` 替换 `computeWorkbenchColumns` 的桌面求解；保留小屏 drawer 的既定 a11y 行为，但不要让旧 v2 分支再决定桌面宽度。
2. 用 v3 preference adapter 解析、迁移、保存：按当前 `workspaceId` 读取 `detailWidthPx`、active panel、task subview；迁移成功后写 v3，损坏值安全回退。
3. 让 resize handle 接收宽详情最小/最大值和 snap 点；移除 720px 上限，拖动实时更新 CSS variable，pointerup 才持久化，双击回到 560px。
4. 修正“左栏先让位”：当已请求详情宽度在左栏 dock 下达不到可用上限/960 snap，而把左栏收为 48px rail 后可以达到时，应让左栏收 rail；不能只在对话已经小于 320px 后才让位。
5. 修正几何边界：`snapDetailWidth()` 在无候选点时不能返回大于 `maxWidth` 的值；为 `maxWidth < 360`、1024 临界、drawer/rail/恢复展开态补纯函数测试。
6. 统一工作面板“总列宽”和“详情宽”的命名，避免 rail 被重复加/减；删除不再使用的 v2 生产状态路径后再清理兼容代码。

**完成标准：**

- 1440px：详情拖到至少 960px，左栏必要时自动收 rail，对话始终 >= 320px；
- 1920px：详情可达可用宽度的 >= 70%（受 80% cap 与 320px 对话下限共同约束）；
- 1280/1024/768/480/375/320px：无横向溢出，dock/rail/drawer 行为与焦点恢复正确；
- 宽度在同 workspace 刷新后保留，切换 workspace 不串值。

### S2 — 统一仓库事实与渐进 Review（P0）

1. 将 `WorkspaceRepositorySnapshotStore` 放入 Workbench provider 或专用 hook，Git、Review、Files decorations 均以 `{workspaceId, repositoryRevision}` snapshot 为入口；不要在各面板单独 `gitStatus()`。
2. 让 Git mutation、terminal resource invalidation、手动刷新失效同一个 workspace slot；coalesce 同时刷新，使用 AbortController/generation 防止旧响应覆盖。
3. Review 首屏只渲染 repository summary；验证证据经 `/review/verification` 独立分页，并显示 loading/stale/error/retry。Web API、action 与 `ReviewPanel` 必须全部接上。
4. 在 UI 显示 revision changed/stale，更新期间保留旧内容而非整页闪空。

**完成标准：** 临时 Git 仓库包含 staged/unstaged/untracked/conflict 时，Git、Review、Files 装饰计数与 revision 一致；刷新不产生三次并发 status；Review 摘要先于验证证据可用。

### S3 — 把五类面板补成可用工作流（P1）

1. **Review：** staged/unstaged/untracked/conflict 过滤、文件前后导航、hunk 折叠与反馈；选择 hunk 生成版本绑定 Context chip。
2. **Files：** 接入 Host workspace search（名称/可选内容、cursor、ignore/sensitive/out-of-root 限制）；小于 520px 改列表 → 预览 drill-in；提供“文件/行范围加入 Context”。
3. **Git：** 显示受限 stage/unstage/commit 操作；所有 mutation 传 workspace/context/repository revision、requestId、用户手势；commit 前二次确认；409 后刷新并要求再次确认。
4. **Terminal：** `/terminals` 或 summary 提供真实状态并驱动 rail badge；补 tab 重命名、搜索、用户显式输出选区 Context；切换面板后不重建既有 PTY。
5. **Agent：** 使用 v3 `taskSubview`，将四个子页收敛为紧凑切换，不丢 Goal、活动、能力、诊断。

### S4 — Context V2 闭环（P1）

1. 协议扩展 `diff_hunk`、`review_summary`、`terminal_selection`、`tool_artifact`；每种类型定义 opaque ID、revision/digest、大小上限、脱敏与 stale 语义。
2. 详情面“加入 Context”只添加可移除 chip；提交/排队时由 Host 重新解析，并在过期、越权、二进制、超预算时给出可恢复提示。
3. 对 terminal 只允许用户显式选择的有限文本，不能把完整 scrollback 注入会话或持久化收据。

### S5 — 视觉、无障碍、性能（P0）

1. 移除 `PROJECT WORKSPACE` 眉题和重复边框；右栏 header 统一为 icon、面板名、scope/count、刷新/更多/收起；rail active 使用文字化状态、窄指示条和可访问 tooltip。
2. 每个面板显式实现 loading skeleton、empty、content、stale、error/retry、unavailable；禁止在请求时清空上一份可读内容。
3. 检查深浅主题、classic/blocksmith、reduced motion、键盘 rail、Esc、drawer focus return、separator Arrow/Home/End。
4. 将关键 viewport 的 screenshot baseline 加入 E2E；对动态时间/ID 固定 fixture 或屏蔽，避免视觉测试抖动。

## 6. 执行顺序与提交边界

1. 先完成 S0，避免测试“假失败/假通过”；随后 S1，一次性换掉旧桌面路径。
2. S2 必须在 S3 之前，先确定 Git/Review/Files 的同一仓库事实。
3. S3 与 S4 可并行拆分，但每个 Context 类型需端到端闭环后再新增下一个。
4. S5 与每个切片同行：不将视觉/a11y 堆到最后一次大改。

推荐提交边界：

- `test(web): repair runtime-ready e2e contract`
- `refactor(web): make wide right workspace the production layout`
- `fix(web): share repository snapshot across work panels`
- `feat(web): complete guarded workspace panel workflows`
- `feat(web): add version-bound context v2 references`
- `test(web): cover wide workspace release matrix`

## 7. 完成定义

只有同时满足以下条件，v0.3.12 才可称为完成：宽右栏真实可拖到目标尺寸；v3 偏好和 snapshot store 真正被生产入口使用；五类面板的承诺能力可从 UI 发起并安全完成；Context V2 的每种已声明引用可经 Host 验证；真实 artifact E2E、a11y、视觉矩阵及常规门禁全部通过。PR、合并、npm 发布仍需要单独授权。

| --- | --- | --- |

## 2. 会话「编辑/标记」修复与升级

### 2.1 现状盘点（代码事实）

- rename 链路**完整闭合**：会话行 edit 图标（`ProjectNavigator.tsx:442-451`）→ `onRenameSession` → App `RenameDialog`（`Dialogs.tsx:191`，仅改名、maxLength 120）→ `actions.renameSession`（`useWorkbench.ts:1053`，成功后 `upsertSessionSummary` + dispatch 刷新 rail）→ host `workbench-controller.ts:1153`（校验：会话须属于**当前 workspace**，否则 409；trim/空/超长 400）→ `session-storage.renameSession`。
- **无标签（tag）能力**：`WebSessionSummaryV1`（`protocol.ts:481`）无 tags 字段；核心层无会话 tag 存储。协议里唯一的 `tags`（`protocol.ts:380`）是**工具描述符**元数据，与会话无关。
- 候选缺陷（需在真实 host 上复现确认）：
  - rename 入口仅 `project.active` 项目渲染（441 行），且 `operationLocked`（`pendingAction`）时 disabled —— 有任务在跑时按钮灰，可能被感知为「无法编辑」。
  - `RenameDialog` 失败路径 `catch {}` 静默（提交失败仅靠全局 notice，弹窗不关）；若 `requireContextGuard` 抛错，表现为「点保存无反应」。
  - 图标是行尾 13px 小按钮，hover 命中区域小（可点目标不足），存在点击被 `project-session-main` 遮挡的风险。

### 2.2 预期行为

1. 对**当前项目**下任一可见会话，随时可重命名；名称即时反映到树（已有）。
2. 会话可设置 **0..N 个标签**（轻量分类，如「进行中 / 归档待续 / 临时」）；标签显示在会话行 secondary 行或小徽章，可增删。
3. 操作入口统一为行尾「更多」（⋮）菜单：重命名 / 管理标签 / 归档 / 删除（删除见 §3，同菜单）。

### 2.3 交互方式（建议）

- 会话行 hover 显示「更多」按钮（`session-more`），点击弹出轻菜单（定位在行内，避免与 rail 的 `contextmenu` 冲突）。
- 菜单项：**重命名… / 标签… / 归档 / 删除…**；归档/删除危险操作二次确认（§3）。
- 重命名：复用现有 `RenameDialog`（升级为可同时编辑「名称 + 标签」的单表单，标签用输入 + Enter/chips，或独立小对话框）。
- 键盘：菜单箭头导航 + Esc 关闭 + 焦点归还行（参照既有 dialog 模式）。

### 2.4 实现建议

- **先修可用性缺陷（P0，低风险）**：
  - 菜单化入口：新组件 `SessionRowMenu`，替换 edit 图标（`ProjectNavigator.tsx:441-451`）。
  - `RenameDialog` 失败不再静默：catch 里显示行内错误（`field-error`）而非关闭。
  - 检查并消除小命中区域（按钮 ≥24×24 可点区）。
- **标签能力（P0.5，新增契约）**：范围决策——本轮只做**前端本地会话标签**还是**持久化到会话记录**？
  - 建议：持久化。会话记录 JSON 增加可选 `tags?: string[]`；`WebSessionSummaryV1` 增 `readonly tags?: readonly string[]`；host 增 `setSessionTags(sessionId, tags)`（复用 rename 的 workspace 校验与 404 语义）；列表/搜索可按 tag 过滤（v0.3.7 内做显示 + 增删，过滤留 v0.3.8）。
  - 兼容：旧会话无 tags 字段 → 按空数组处理，协议向后兼容（字段可选）。

### 2.5 验收

- 真实 host：对当前项目会话改名成功且树即时更新；改名后刷新仍在（持久化）。
- 标签增删即时反映 + 刷新持久；无 tag 旧会话不报错。
- 所有会话管理操作菜单可键盘完成；axe 无 serious/critical。
- 修复候选缺陷的回归：pendingAction 转场后菜单可再次打开；改名失败有行内错误提示。

## 3. 会话归档与删除

### 3.1 现状盘点（代码事实）

- 前端：无 archive/delete action（`useWorkbench.ts` 仅有 `removeWorkspace`/`removeQueued`）。
- host：`workbench-controller` 无归档/删除会话方法；`server.ts` 无对应路由。
- 核心：`session-storage.ts` 提供 `listSessions`/`findSession`/`renameSession`/`countSessionsByProject` 等，**无 remove/archive**；`storage-maintenance` 已有项目级清理（vector rows、孤儿 key 清理）可复用删除路径。

### 3.2 语义设计（建议）

| 操作 | 定义 | 存储处理 |
| --- | --- | --- |
| **归档** | 移出「项目」默认列表，保留全部数据，可在归档区查看/还原 | 会话记录加 `archivedAt?: string`；`listProjectSessions`/`countSessionsByProject` 默认过滤归档；新 `listArchivedProjectSessions` + `restoreSession` |
| **删除** | 物理删除会话（不可恢复，强确认） | `session-storage` 新 `removeSession`：删记录文件/目录 + memory/vector 行（复用 maintenance 清理）+ 移除 registry/runtime（若在跑则先中断并拒绝删除运行中会话） |

边界与约束：
- **运行中会话禁止删除/归档**（`sessionRuntimeById` phase ≠ cold 时菜单项禁用并提示「会话运行中」）。
- **跨 workspace 会话**：host 会话 API 全部按当前 workspace 上下文校验（现有 rename 409 语义）→ 归档/删除同样限定**当前项目**可见会话；UI 上其他项目的会话不提供操作入口（与现状一致，避免误导）。
- 归档区入口：项目树底部「已归档 N」折叠区（点击展开可还原），或单独过滤视图。

### 3.3 交互方式

- 「更多」菜单 → **归档**：立即执行（可撤销），Toast 提示「已归档」+ 若 3s 内可「撤销」；归档后行从树消失。
- **删除…**：二次确认对话框（`DialogFrame`），文案含会话名与不可恢复警告；确认按钮 danger 样式；成功后 Toast。pendingAction 期间禁用。
- 运行中/转场中状态：菜单项禁用 + 说明 tooltip/脚注。

### 3.4 实现建议（分层，后端先行）

1. `session-storage.ts`：`archiveSession(sessionId)` / `restoreSession(sessionId)` / `removeSession(sessionId)`（+ `listArchivedProjectSessions`）——注意 session JSON 是 append-only 事实文件的投影，归档/删除需同步清理关联（artifacts、goal sidecar、checkpoints、vector 行），删除前由 maintenance 侧函数统一执行。
2. host 协议：`WebCommandTypeV1`/RPC 增 3 方法 + `server.ts` 路由 + controller（含 workspace guard、404/409/412 语义、运行中校验）。
3. 前端：`useWorkbench` action（`runOperation` 包装）+ reducer（删除后移除 sessions/投影/队列条目 + notice）；reducer 层测试补 `archive/remove` 契约。
4. UI：菜单项 + 确认框 + 归档区。
5. 危险操作护栏：删除确认框内展示会话消息数与更新时间；**不做任何自动清理**（遵守本项目 scope discipline）。

### 3.5 验收

- 归档后默认树消失、归档区可见、还原恢复原位；刷新持久。
- 删除后列表/计数/搜索均不再出现；对应向量行清理日志有记录。
- 运行中会话操作项禁用；跨项目会话无入口。
- jest（reducer/storage 契约）+ web-ui 渲染测试补对应用例；CI e2e 一条归档/删除主流程。

## 4. 新增项目 / 工作区选择流程重构

### 4.1 现状盘点（代码事实）

- 入口：项目工具栏「+」（`ProjectNavigator.tsx:243-252`，aria-label「选择其他工作区」）→ App `WorkspaceDialog`。
- `WorkspaceDialog`（`Dialogs.tsx:69-189`）已具备：已知工作区列表（当前/不可用 pill、可用高亮、分页加载更多）+ 手动路径输入 + 提交后错误提示。**功能完整但存在体验缺口**：
  1. 无**目录浏览**（浏览器原生限制，需路径输入；macOS 用户期望 Finder 选择器）。
  2. 提交前无校验（空/重复/非目录要等 host 拒绝，400 语义靠错误文案，无本地预检与 loading 态）。
  3. 「已知工作区」与「新目录」混在一个对话框，初次用户不清楚「新增项目」与「切换工作区」的关系。
  4. 无最近打开目录建议、无成功跳转反馈（成功后直接关窗，用户需自己看到树变化）。

### 4.2 预期行为

1. 「新增项目 / 打开项目」= 选择/添加一个**本地目录**作为工作区；若该目录已注册则直接切换（幂等），未注册则注册并切换。
2. 两步心智：**常用目录（最近/已注册）→ 新目录**；目录输入即时校验（存在性、是否已注册、是否属于已知父级规则），给出可操作提示。
3. 任何失败在输入框下方行内展示（已有 pattern），提交期间按钮 loading 防重。

### 4.3 交互方式（建议）

- 保留单个 DialogFrame（不引入向导多步），重排为三个区块：
  1. **建议目录**（最近打开的 3-5 个 + 当前，点击即开）——数据源：host 维护 `recentWorkspaces`（现有 workspaces 已按注册顺序；可加最近使用时间戳）。
  2. **所有已知工作区**（可折叠「其他工作区…」分组 + 加载更多）——保留现有列表与 pill。
  3. **打开其他目录**：输入 + 「浏览…」。
- **浏览…**：macOS 浏览器无法直接弹 Finder；两个方案：
  - A（推荐，零依赖）：`<input type="file" webkitdirectory>` 隐藏控件触发系统目录选择，取其路径文本回填（webkit 系浏览器可用；Chromium 支持，符合本项目 Chromium 系约束）——仅回填路径并聚焦，用户确认「打开」。
  - B：粘贴路径 + 「在 Finder 中显示」辅助，弱于 A。
- 校验：提交前 `path` 存在性（前端无法 stat）→ 仍以 host 为准，但增加 debounce 预检端点 `probeWorkspace(path)`（只读 stat：是否目录、是否 git 根/可识别项目、是否已注册）——可选 P2。
- 提交成功：DialogFrame 关闭前短暂「已打开 <basename>」Toast；失败行内错误保留输入。

### 4.4 实现建议

- 纯前端优先（P1）：重排 WorkspaceDialog DOM + 建议区（数据用 `state.workspaces` 前 N 个即可，不做新端点）+ webkitdirectory 浏览回填。
- 可选后端（P2）：`probeWorkspace` 只读 stat 端点 + `recentWorkspaces`（host 侧记录切换时间）。
- 文案：对话框标题与触发按钮统一为「打开项目 / 新增项目」语义；「+」aria-label 同步。

### 4.5 验收

- 打开已注册目录：直接切换不重复注册；打开新目录：注册并成为当前项目，树刷新出该项目。
- 「浏览…」在 Chromium 下可选择目录并回填。
- 非法路径/重复打开错误行内展示，输入不清空；pendingAction 时提交按钮禁用。
- axe 无 serious/critical；e2e 补一条「浏览回填 + 打开新目录」主流程。

## 1. Executive Summary

v0.3.22 完成了执行可靠性（ToolGateway 请求身份、持久化故障注入、发行门禁）与评测基座
（coding-task-eval + 12 个机器验证 fixture）。v0.3.23 的目标是让 Orion Code 从「执行可靠」
进阶为「理解准确、修改优质、自主验证」：

- **方向 A（P0）Live Coding Eval**：把 `runCodingTaskEvalV1()` 的 live 模式从「直接抛错」
  接通为真实模型 × 真实 Agent Loop × 隔离 Workspace 的闭环——它是另外两个方向所有改进的
  测量基础。
- **方向 B（P1）Repo Intelligence**：在既有 file-context / project-instructions /
  session-memory / `lsp_get_diagnostics` 之上建轻量符号索引与任务相关召回，不做全量搜索引擎、
  不引入向量库。
- **方向 C（P1）Autonomous Verification & Repair**：把两个**孤儿模块**
  （`services/auto-fix/`、`services/verification-profile.ts`）中独特的有界修复与命令安全
  分类能力并入**已接线**的 HarnessKernel 完成审计栈，形成变更感知验证 → 结构化归因 →
  有界修复 → 完成审计的闭环，不新建第二套修复 Agent。

投入比例（源码成熟度修订后）：Repo Intelligence 40% / Verification & Repair 35% /
Live Coding Eval 25%（与原始建议一致；Live Eval 虽占比最小但为 P0 前置）。

### 3.2 关键结构性发现（决定本版方案的三个事实）

1. **存在两套验证/修复栈，一套接线一套孤儿。** `services/auto-fix/` 与
   `services/verification-profile.ts` 是独立完整实现（含 `maxAttempts` 语义、命令风险分类、
   完成门禁提示），但没有任何生产消费者；与此同时 HarnessKernel 已有另一套完成审计
   （verification kinds + trusted evidence + waivers）。**v0.3.23 不允许出现第三套**——方向 C
   的正确动作是把孤儿栈中独有的能力（有界修复循环、命令安全分类、结构化失败解析）**并入**
   HarnessKernel 完成审计，并删除或降级孤儿文件，消除重复。
2. **Live Eval 的缺口是接线而非框架。** fixture 格式、成功检查、指标、来源元数据在 v0.3.22
   已就绪；缺的只是「真实 Agent Loop × 隔离 Workspace」的执行器。
3. **Repo Intelligence 的底座分散但已在产**：file-mentions/引用收集、项目指令、session
   memory、`lsp_get_diagnostics` 均可用，但**没有符号级索引**，上下文选择没有「来源与理由」
   的结构化输出——这是方向 B 的真实增量。

## 6. 方向 A：Live Coding Eval（P0）

**Source Location：** `scripts/bench/coding-task-eval.ts`（`runCodingTaskEvalV1`:286、
live 抛错 `:315`；fixture 加载 `loadCodingTaskCorpus`；成功检查 `checkOne`/`verifyChecks`）；
`src/runtime/product-orion-runtime.ts`、`src/runtime/agent-loop.ts`；fixtures
`scripts/bench/fixtures/coding-tasks/coding-tasks-v1.json`。

**Technical Proposal（新设计，基于已确认缺口）：**

1. 新增 `LiveTaskExecutor`（`scripts/bench/live-task-executor.ts`）：输入 fixture + 配置
   （model、providerId、effort、contextBudget、seed），在 `mkdtemp` 隔离 workspace 中物化
   `repo.files`，然后驱动**生产 Orion Runtime**（product-orion-runtime 的非交互入口）执行
   `instruction`——模型只通过真实工具（read/write/edit/bash）改动文件；executor 自身不写
   预期文件。
2. 成功判定完全复用既有 `verifyChecks()`（文件状态断言）＋新增两类检查：`command_exit_zero`
   （在 workspace 内跑测试命令）与 `invariant`（安全不变量：diff 不触碰 fixture 外路径等）。
3. 运行收据：每任务记录 `outcome: solved | task_failed | provider_failed | timeout |
   permission_denied | false_complete`、模型/Provider/版本/seed/budget、原始消息数与
   token 用量（来自既有 model-request 统计）。**模型自述成功不作为判定。**
4. A/B 报告器：`compare-receipts.ts` 读两份 run 收据，输出 solvedRate、falseCompletionRate、
   tokensPerSolvedTask、modelRequestsPerTask、toolCallsPerTask、P50/P95、retryCount、
   costPerSolvedTask，保留原始样本与样本数（≥3 轮/版本），不报最好一次。
5. fake 模式与 `harness-eval.ts` 保持原样（确定性回归不动）。

**Dependencies：** 无（本方向是 B/C 的前置）。
**Risks：** 模型凭证与费用（live 轮次须显式授权）；Runtime 非交互驱动面可能需要小改
（待验证：product-orion-runtime 是否已有可编程 entry；若无需加 `--eval-task` 入口而非新链路）；
Provider 429 需沿用 request-gate 而非 eval 内自造重试。
**Test Strategy：** executor 单测（隔离 workspace、超时、denied、provider 失败五分类）；
fake 模式对照（同 fixture 两模式跑同一检查集）；1 个真实模型冒烟 fixture（显式授权后）。
**Acceptance Criteria：** `--mode live` 对 12 fixture 完成一次全量跑并产出收据；五分类可
区分；A/B 报告可对比两份收据；`npm run eval:fake` 回归不变。

## 7. 方向 B：Repo Intelligence（P1，本版主要能力建设）

**Source Location：** 新增 `src/services/repo-intelligence/`（symbol-index.ts、
incremental-index.ts、recall.ts）；复用 `src/services/file-context.ts`、
`src/runtime/long-tail-tools/descriptors.ts:350`（`lsp_get_diagnostics`）、
`src/services/project-instructions.ts`、`src/services/session-memory/`、
`src/harness/assembler.ts`（预算内选择）、`src/harness/capsule.ts`/`ledger.ts`（来源记录）。

**Technical Proposal：**

- **B1 轻量符号索引**：优先用 TS 编译器 API（`typescript` 已是依赖）对 TS/JS 建符号表
  （函数/类/导出/导入边），语言接口留扩展位；**不新建语言服务器**，诊断继续走
  `lsp_get_diagnostics`。索引产物：`{symbol, kind, file, line, exportsTo[], importsFrom[]}`。
- **B2 增量维护**：以文件 mtime+size 摘要与 git status（untracked/modified）判断失效文件，
  只重建失效子集；索引任务可取消（AbortSignal）、有目录项/时长预算；索引损坏时降级为
  「无索引召回」并自愈重建。
- **B3 相关性召回**：输入（用户 intent、当前文件、最近修改、测试关联、最近工具证据）→
  候选打分（直接提及 > 符号命中 > import 邻接 > 测试配对 > 近期修改）→ 输出
  `{path, score, reasons[]}`——**来源与理由必须随上下文进入 Harness ledger**（复用
  capsule/ledger 的证据通道）。
- **B4 预算选择**：在 assembler 的 Context Budget 分档内做去重（同文件去重、低分截断），
  保留用户显式引用文件（file-context 的 mentions 为最高优先）与 project-instructions。
- **B5 召回质量评测**：为 fixture 任务标注 expected-relevant 文件集合；指标
  RelevantFile/Symbol Recall@K、无关上下文比例、首次有效定位工具调用数、Context Tokens、
  solvedRate。**必须同时证明「更少」与「不漏」。**

**安全约束：** 索引与召回只经现有安全读取通道；默认排除 `.env`、密钥文件、二进制、
`node_modules`/构建产物与 workspace 外路径（沿用 workspace discovery 的忽略表）。

**Dependencies：** 无硬依赖；与 A 并行；C 的「变更感知」复用 B3 的测试关联。
**Risks：** TS 编译器 API 在大型 repo 的成本（用增量+预算兜底）；monorepo 多 tsconfig
（首版只支持单根）；召回打分是启发式——必须由 B5 验证而非宣称。
**Test Strategy：** 索引器单测（fixture repo 的符号/导入断言）；增量更新单测（改一个文件只
重建一个文件）；召回评测任务集 + Recall@K 报告；预算选择单测（显式引用必保留）。
**Acceptance Criteria：** 12 fixture 的 expected-relevant 标注完成；Recall@5 ≥ 既有
file-mentions 基线且 solvedRate 不降（live eval 实测）；同一任务上下文 token 不增。

## 8. 方向 C：Autonomous Verification & Repair（P1）

**Source Location：** 孤儿能力来源 `src/services/auto-fix/autoFixRunner.ts:43`、
`autoFixHook.ts:53`、`src/services/verification-profile.ts:38/109/185`；并入目标
`src/harness/context-harness.ts`（HarnessKernel 完成审计 `:491-498`）、
`src/runtime/task-context-service.ts`；复用 `src/harness/stop-controller.ts:12`、
`progress-controller.ts:101`、`src/runtime/thread-event-store.ts`（恢复/审计语义）、
`src/runtime/long-tail-tools/descriptors.ts:350`（诊断）。

**Technical Proposal：**

- **C1 变更感知验证**：以 `git diff --name-only` + B3 的测试关联选择验证命令；先快后全
  （类型/单测 → 关联集成 → 全量）；验证命令跑在 ToolGateway 内（权限与收据不变）。
- **C2 结构化失败归因**：新增 `failure-attribution.ts`——把 TypeScript 诊断
  （`lsp_get_diagnostics`）、lint/build/test 输出解析为
  `{kind, files[], symbols[], firstError, structuredDigest}` 证据条目（进 Harness ledger），
  而非把整段日志回灌模型。
- **C3 有界修复循环**：并入孤儿 `AutoFixRunner` 的 maxAttempts 语义到 HarnessKernel 的
  turn 循环：每轮 {失败目标 → 最小修复 → 再验证}，配 `StopController`（预算/无进展判定，
  复用 ProgressController）与用户中断；轮间比较（修复 diff 与错误数变化）——无进展即停。
- **C4 防错误修复**：完成审计新增守则断言（从孤儿 `classifyCommandSafety` 移植命令风险
  分类）：禁止删除/跳过失败测试、降低断言、大范围删除、改验收标准、环境失败伪装修复；
  违规即 terminal=failed（走既有 turn.terminal，不改协议）。
- **C5 完成验证**：完成审计输出五态 `completed / failed / blocked / cancelled /
  unverified`；`unverified` = 无可信验证证据（复用 `isTrustedEvidence`）且未声明无法验证的
  原因。孤儿 `shouldGateCompletion`/`formatVerificationGateNotice` 的门禁提示逻辑并入此处。
- **处置孤儿**：上述并入完成后，`services/auto-fix/` 与 `services/verification-profile.ts`
  的独有逻辑迁入新家，文件删除（git 历史可溯），**消除双栈**。

**Dependencies：** C1 依赖 B3（测试关联，可先用 git diff 近似版先行）；C5 依赖 A（live eval
提供度量）。
**Risks：** 修复循环与 Goal 生命周期的状态机交互（先只在 build 模式启用，feature flag）；
错误归因解析的覆盖面（首版只解析 TS 诊断 + jest/vitest 输出结构）；防止「修复」变成无限
Token 消耗（硬预算 + 无进展即停）。
**Test Strategy：** 归因解析单测（真实 TS 错误/jest 失败样本）；有界循环单测（maxAttempts、
无进展停、用户中断）；防作弊回归（删测试/改断言 → failed）；live eval 对照（修复策略开/关
的 solvedRate 与 falseComplete）。
**Acceptance Criteria：** live eval 上 falseComplete=0；自动修复成功率与轮数有数据；无未
终止的修复循环；协议零变更。

| 安全回归 | 索引不越 workspace；敏感文件排除；修复循环全程走 ToolGateway；防作弊断言 |
| 发行 | 既有 release:check + 三轮连跑 + critical ×3 维持 |

## 12. Evaluation Metrics

A：solvedRate、falseCompletionRate、tokensPerSolvedTask、modelRequestsPerTask、
toolCallsPerTask、P50/P95 Duration、retryCount、costPerSolvedTask。
B：Relevant File/Symbol Recall@K、无关上下文比例、首次有效定位工具调用数、Context Tokens。
C：首次测试通过率、自动修复成功率、平均修复轮数、归因准确率、无效修复率、False Completion。

## 13. Performance Budgets

- 符号索引：单文件重建 ≤ 50ms（目标值，非实测）；全量索引 ≤ 5s（中型 repo fixture）。
- 召回查询 ≤ 100ms；索引不阻塞 Turn 主路径（异步 + AbortSignal）。
- 修复循环：默认 maxAttempts ≤ 3（沿用孤儿栈语义）；单任务修复 token ≤ 该任务基线 × 2。
- Live eval 单任务超时默认 10 分钟（可配）。
以上均为**设计目标**，未实测；以 PR 对应 evidence 为准。

## 14. Risk Assessment

## 15. Acceptance Criteria

1. `--mode live` 全量 12 fixture 产出收据，五分类可区分，模型自述不作为判定。
2. fake 回归 12/12 不变；A/B 报告含原始数据与样本数。
3. Recall@K ≥ 基线且 live solvedRate 不降、上下文 token 不增。
4. 完成审计五态落地；falseComplete=0；防作弊回归全绿；双验证栈消除。

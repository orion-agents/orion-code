# v0.3.0 Session 与 Web Runtime 性能修复方案

状态：本地 v0.3.0 候选已完成，待发布门禁
版本：v0.3.0
范围：Session 列表/恢复、ThreadEventStore、Web 流式输出、工作详情抽屉

## 1. 问题基线

在包含 453 个 Session、99 个项目和 11 个 v2 Thread 日志的真实本地数据上：

- `GET /api/v1/workspaces` 首字节为 19.59 秒；
- `GET /api/v1/sessions` 首字节为 3.90 秒；
- 最大 Thread 日志为 12,864,719 字节、6,727 个事件；
- 同一大 Thread 上 `getCursor()` 每次约 171.7 ms；
- Web 首次加载会等待工作区、Session、诊断、Skills、MCP 和工具详情全部完成，慢请求会让页面看起来为空白；
- CLI `/resume <ref>` 会先构造完整列表，再 lookup 时再次构造列表，然后分别加载 history、transcript、legacy messages 和 compact 状态。

这些数据说明瓶颈不是浏览器、npm 安装或偶发慢盘，而是读模型和权威事件日志的职责混淆。

## 2. 根因

### 2.1 列表接口错误地恢复权威 Thread

`SessionCatalog` 已经保存列表需要的名称、项目、更新时间、消息数和历史大小，但
`listSessions()` / `listProjectSessions()` 对每个 Session 再调用 Thread summary。所谓 summary
会解析 hash-chained event log、重建 projection，并物化 transcript；工作区列表随后又按每个项目重复这一过程。
这本质上是列表读路径中的 N+1 全量事件重放。

### 2.2 ThreadEventStore 没有进程内已验证 head

同一 `ThreadEventStore` 的 `appendDurableBatch()`、`getCursor()`、`replay()`、
`loadProjection()` 和 compact 读取都会重新读取、解析、校验完整 JSONL。流式 `item.delta`
为了取得 cursor 也会调用 `getCursor()`，所以一个模型响应的每个增量都可能重扫数 MB 日志。

### 2.3 Resume 不是一个存储事务视图

CLI 恢复分别请求 provider history、UI transcript、legacy raw messages 和 compact checkpoint；v2
Session 因而对同一 Thread 做多次独立重放。Web 激活 Session 还会重新加载全局工作区列表，放大了同一问题。

### 2.4 UI dock 与 modal drawer 使用同一个状态

当前 `inspectorOpen` 同时控制窄屏遮罩、背景 `inert` 和 Inspector 可见性，无法正确表达桌面常驻栏的
展开偏好。直接增加一个折叠按钮会把桌面 dock 错当成 modal，并破坏焦点与无障碍语义。

### 2.5 Web Composer 在 Session transition 中出现“看似可输入、实际丢提交”

创建或切换 Session 后，客户端会先重置投影，再等待 Session 列表和 snapshot。旧实现只禁用了发送按钮，
textarea 仍可输入；Enter 被 `preventDefault()`，而提交函数检测到 `pendingAction` 后直接返回。因此用户看到的是
“对话无输出”，实际 provider 和 `/commands` 都从未收到请求。这不是模型流式协议问题，而是 UI readiness
没有形成单一状态机。

### 2.6 Web 把历史恢复和 live event 混在同一通道

Session 激活时，Thread observer 和 UI adapter 都从 cursor 0 重放历史；Web snapshot 又顺序拉取全部 transcript
分页。每个历史 fact 都会被 sanitize、复制、序列化并放进内存 SSE retention，长会话会同时放大 CPU、网络和
浏览器 reducer 成本，并可能挤掉真正需要的 reconnect window。

## 3. 目标架构

### 3.1 权威日志、Projection 与列表读模型分层

- Thread JSONL 继续是唯一权威事实源；
- Projection 是可重建、带 digest 的运行时状态缓存；
- SessionCatalog 是列表/选择器专用读模型，不允许在列表请求里恢复 Thread；
- Runtime 启动和 durable turn commit 后，将 projection 派生的 `messageCount`、`historySizeBytes`
  与 `updatedAt` 写回 SessionCatalog；历史数据在被打开时自愈，不阻塞全量列表；
- 工作区计数只对 SessionCatalog 做一次分组，不按项目重复读取 Thread。

### 3.2 ThreadEventStore verified-head cache

每个 Store 实例缓存最近一次完整校验得到的：

- log fingerprint（device/inode/size/mtime/ctime）；
- 已验证 records/events；
- projection 与 projection-file fingerprint。

只要日志 fingerprint 未变化，cursor/replay/projection 使用同一已验证 head；durable append 在文件锁内从
当前 projection 增量应用新事件。若日志被其他进程写入、截断或修改，fingerprint 变化会强制完整扫描；
partial tail、hash mismatch 和 projection ahead 仍按现有规则 fail closed。任何 crash boundary 之前都不发布
新的 cache head。

### 3.3 单次 Session restore bundle

恢复 API 返回同一稳定捕获中的：

- provider-safe model history；
- transcript messages；
- recovery diagnostics；
- summary/compact 展示信息；
- Session metadata。

legacy Session 仍走旧文件锁和 checkpoint 校验；v2 Session 只捕获一次 Thread。命令层不再组合四个会重复
读取存储的 API。

为避免“消息数为 0”的旧索引永久隐藏后来已经提交的 Thread，v2 catalog read model 绑定
`threadId + cursor + projectionDigest + cutoverGeneration + lastRecordHash + log identity`。只有绑定的日志
identity 仍完全一致时，零消息才可判定为真正 empty；若 durable append 后进程在 catalog refresh 前崩溃，
identity 漂移会把目标降为 `unknown`，选中时只修复该目标，不扫描全库。

### 3.4 Web 工作详情双状态

- 桌面：`expanded | collapsed` dock preference；折叠后保留 44–48px 竖状状态栏；
- 窄屏：独立 `overlayOpen` modal drawer；只有它启用 scrim、背景 `inert`、焦点约束和 Escape；
- Session/工作区切换只关闭 overlay，不重置桌面偏好或当前详情 tab；
- 折叠内容必须从可访问性树和 Tab 顺序中移除。

### 3.5 Snapshot 负责历史，SSE 只负责 captured edge 之后的新增事实

- 激活 Session 时先取得 Thread projection edge；observer 只发布该 edge 之后提交的事件；
- 所有 renderer 的 Runtime adapter 都从 captured edge 开始，历史不再经 `RuntimeEvent` 重放；
- Web 从 cursor-bound snapshot 恢复最近 50 条；TUI/经典终端通过 `transcript_replace` 恢复最近 50 条，
  同时设置 256 KiB 总预算与 64 KiB 单条预算；非交互 print 只报告恢复摘要，不回显旧 transcript；
- provider-safe model history 与 UI transcript window 分离：前者完整恢复，后者有界展示，二者不能互相覆盖；
- 历史 transcript、Goal 和 Plan 权威全部来自同一个 cursor-bound snapshot；
- `turn.committed` 历史 receipt 不再整批复制给 Web，snapshot 只读取 latest commit 和 latest plan commit；
- Session view cache 按近似字节数限制，而不是按“若干个完整历史对象”限制。

### 3.6 Transcript 使用 tail-first 分页

产品首屏只返回最近 50 条消息（协议仍允许单页最多 100 条），`nextCursor` 指向更早的稳定边界；用户显式
“加载更早记录”时向前分页，并要求
`sessionId/threadId/threadCursor/projectionDigest` 与当前 snapshot 完全一致。服务端先 slice 再映射，浏览器
不再自动收集全部页。这一版仍从 verified projection 构造 Session view；未来若单 Session 投影超过内存预算，
再将 transcript archive 拆成不可变 page index，而不能恢复到逐页重建全投影。

### 3.7 Composer readiness 是单一门闩

textarea、模式选择、发送按钮和提交函数统一使用
`active Session + configured + connection open + no pending transition`。Session transition 期间明确显示
“正在完成会话切换”，输入控件不可交互；ready 后第一次 Enter 必须产生且只产生一个 `/commands` mutation。

## 4. 一致性与迁移

- SessionCatalog 是派生读模型，永远不能反向覆盖 Thread 权威状态；
- catalog 更新发生在 durable fact fsync 之后；失败只造成列表暂时陈旧，不得回滚已提交的 Thread；
- Runtime 打开 Session 时用已验证 projection 修复该 Session 的 catalog 行；
- read model 与 log identity 必须由 `ThreadEventStore.captureReadModelHead()` 在同一 Thread 锁内捕获，禁止把
  projection、cursor 和 `stat()` 的不同时间点结果拼成一个“伪原子”索引；
- 旧 catalog 不做阻塞式全库迁移；随着 Session 被打开逐项修复；
- 外部日志变化、projection 损坏和 crash tail 必须触发重扫/重建，缓存不能掩盖损坏；
- legacy 到 v2 的 cutover receipt 仍验证导入前缀，性能优化不得改变 generation authority。

## 5. 验收门槛

### 自动化不变量

1. Store 第一次读取完成后，100 个 ephemeral delta 不产生额外完整日志扫描；
2. 同一 Store 的正常 durable append 不产生额外完整日志扫描；
3. 外部改写日志后下一次读必须重扫，内部 hash 损坏仍被拒绝；
4. projection 文件超前/损坏仍从权威日志重建；
5. Session 列表与工作区计数测试不得打开或 replay ThreadEventStore；
6. `/resume` 对 v2 Session 只构造一个稳定 Thread restore view；
7. 流式 delta、最终 assistant 内容和 durable transcript 在 CLI/Web 三处一致。
8. durable append 与 catalog refresh 之间模拟崩溃后，目标仍可被 `/resume --last` 发现并只修复该 Session；
9. Web 激活历史 Session 时 `historicalEventsPublished = 0`，live SSE 只含 edge 后事件；
10. 205 条以上 transcript 产品首屏只传最近 50 条，协议 100 条边界与向前分页均无重复、无跳项；
11. Session transition 期间 Composer 不可交互，ready 后第一次 Enter 恰好产生一个命令和一个 provider 请求。
12. CLI/TUI 恢复不得从 cursor 0 投影历史；80 条模型上下文恢复后 UI 最多 50 条、最多 256 KiB，
    且 Store 中的模型上下文仍为完整 80 条；print JSON 不包含旧 transcript 正文。

### 真实数据性能

- 当前 453 Session / 99 项目数据：`/workspaces` < 250 ms，`/sessions` < 150 ms；
- 已加载页面切换 Session 后可输入时间 < 1 秒；
- 12 MB 日志上缓存后的 cursor 获取 p95 < 2 ms；
- deterministic provider 释放首个 token 后，浏览器在 500 ms 内看到增量；
- 真实配置模型完成一轮浏览器对话，最终正文、SSE 事件和 Session snapshot 三者一致。

性能记录必须同时包含 fresh-process 冷启动和同进程热路径；不得只凭 OS page cache 报告。v0.3.0 的
catalog/list 路径为 O(Session metadata)，目标 Session 首次打开仍允许一次权威 hash-chain 校验。若冷打开仍
超过 1 秒门槛，下一阶段必须落盘带 CAS 的 Thread head/checkpoint 和不可变 transcript page index，不能通过
延长 timeout 或扩大内存 cache 规避。

### UI 与无障碍

- 1440px 下可折叠为 44–48px 竖栏并从快捷图标恢复对应 tab；
- 390px/320px 下使用 `aria-modal` dialog，Tab/Shift+Tab 不离开抽屉，Escape/遮罩关闭后焦点归还；
- 桌面展开、桌面折叠、窄屏开/关四种状态的 Axe critical/serious 为零。

## 7. 本地候选实测结果

同一台 Apple Silicon macOS、同一份真实 catalog 的修复后结果：

- `GET /api/v1/workspaces`：冷路径 42.2 ms，热路径 24.8–28.9 ms（基线 19.59 s）；
- `GET /api/v1/sessions`：冷路径 28.0 ms，热路径 1.3–2.7 ms（基线 3.90 s）；
- 最终 exact tgz 的浏览器切换 2 条消息 Session：415–444 ms；
- 最终 exact tgz 的浏览器切换 90 条消息 Session：冷路径 1,157 ms、热路径 762 ms；热路径达到
  `< 1 s` 门槛，首次冷开仍超出 157 ms，因此没有把冷路径记为达标；
- CLI fresh process 恢复 90 条消息 Session：1.017–1.044 s，其中约 0.85 s 是 Node/CLI 启动；
  JSON 输出从 613,458 bytes 降至 1,741 bytes，模型上下文仍完整恢复；
- 用户真实模型无工具对话：最终全局安装在 1.466 s 得到精确终态 `ORION_WEB_FINAL4_OK`，snapshot
  与 DOM 一致；
- SHA-256 `8040f841…cd1e` 的 exact tgz Chrome critical journey 5/5 通过；完整 Jest 287/287
  suites、3,586 tests 通过
  （另 5 项按平台条件跳过），TypeScript、ESLint、Web build 均通过。

这里的“完成”指本地 dirty source 构建出的开发候选，不代表 release receipt 已满足 source-clean 或已经发布。

## 8. v0.3.0 实施边界与后续演进

本版本已经落地：无 Thread hydration 的 catalog、原子绑定的 Session read model、单目标 restore bundle、
Store verified-head cache、增量 projection、无历史 SSE、tail-first transcript、统一 Composer readiness，以及
桌面 rail/移动 modal 两套 Inspector 状态。

本版本不宣称 JSONL 已经变成数据库，也不把完整 projection 当成长期分页索引。fresh process 打开一个 v2
Thread 仍会做一次 hash-chain 校验；历史 `TurnCommitV1.history` 和 projection item receipt 的累计体积仍需在
后续存储 schema 中拆成 checkpoint/head + immutable archive。该后续项以冷打开和 projection bytes 门槛触发，
不能回退到列表 N+1、全量 Web rehydrate 或 historical SSE。

触发门槛后应作为一次存储 schema 演进完成，而不是继续增加进程内 cache：

1. 落盘 `ThreadHeadV1`，用 generation、cursor、lastRecordHash、projectionDigest 和日志 identity 做 CAS；
2. 落盘不可变 transcript page manifest，snapshot cursor 绑定 page generation，服务端按页直接读取；
3. `TurnCommit` 活跃 projection 只保留 latest authority pointer，历史完整 receipt 进入 archive；
4. CLI/Web 共用 typed activation bundle，并继续把同一个 verified Store 移交给唯一 Runtime owner；
5. 加入 fresh-process Node 22/24/26 的 scan-count、read-bytes、projection-bytes 和 replay-count 门禁，防止
   OS page cache 或某个 renderer 的局部缓存掩盖结构性回归。

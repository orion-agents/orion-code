# Orion Code v0.3.3 Web 内置「方块工坊」像素主题开发计划

- 版本：v0.3.3
- 状态：Proposed / 待评审
- 日期：2026-08-31
- 范围：Web Workbench 内置主题、视觉组件、主题设置、真实浏览器验收与发布证据
- 评审输入：`exec-26786286-3ce7-41b9-876b-d56108c3e540.png`（任务附件，仅作为视觉方向，不作为运行时依赖或像素级验收基线）
- 产品名称：`方块工坊 / Orion Blocksmith`
- 内置视觉风格 ID：`orion-blocksmith`

## 0. 决策摘要

v0.3.3 只交付一个由 Orion Code 随包提供的 Web 内置像素主题，不建设插件系统、主题市场或第三方主题加载器：

1. 新增内置视觉风格 `orion-blocksmith`，视觉语言采用原创的方块工坊、物品槽、石材、木材和像素硬边设计；
2. 附图只提供构图、密度、材质和色彩方向。不得复制 Minecraft 或其他游戏的商标、名称、字体、纹理、图标、音效、角色、文案或界面切片；
3. 保留 `appearance.theme=system|light|dark` 作为明暗模式，新增 `appearance.style=classic|orion-blocksmith` 作为视觉风格；`orion-blocksmith` 是未显式配置 style 时的默认，已有 theme 值不被覆盖；
4. 现有三栏 Workbench、Session、Goal、审批、Tool、终端、文件、Git、设置和 Composer 行为保持不变，主题不得建立第二套产品状态；
5. 主题继续通过 Host Settings 的 CAS、revision、last-good 和只读/无效状态链持久化，并支持无刷新实时切换；
6. 像素感由语义 Token、硬边组件几何和少量第一方像素素材共同实现，正文、代码、CJK 和状态数字不做低分辨率栅格化；
7. 所有素材本地打包，不访问 CDN，不执行主题脚本，不放宽 CSP，不引入安装、卸载、启用或停用生命周期；
8. 完成定义是 exact tarball 中的真实浏览器页面通过主题持久化、功能回归、响应式、无障碍、CSP、资产预算和截图证据门禁，而不是概念图相似或本地 CSS 预览。

### 1.2 当前主题实现

当前 Web 主题不是插件，而是一条固定枚举设置链：

```text
orion.json web.appearance.theme + web.appearance.style
  -> SettingsDocumentRepository strict validation + atomic CAS
  -> SettingsCoordinator effective/explicit/last-good projection
  -> Web protocol and client contract
  -> App sets <html data-theme="..." data-ui-style="...">
  -> bundled CSS variables and component selectors
  -> TerminalPanel reads terminal CSS variables
```

当前 `theme` 只接受 `system | light | dark`，其语义是明暗模式；当前没有独立的视觉 style 字段：

- `src/services/global-config.ts`：全局配置类型、strict validator 和宽容启动清洗；
- `src/services/settings-document-repository.ts`：可写操作枚举、校验和原子持久化；
- `src/services/settings-coordinator.ts`：theme 默认值、来源、scope、live apply 和 last-good view；
- `src/web/protocol.ts`：Web Settings wire 类型和 mutation parser；
- `web/src/settings/`：浏览器 contract、draft、mirror、legacy localStorage 迁移；
- `web/src/components/SettingsDialog.tsx`：主题选择器；
- `web/src/App.tsx`：把 effective theme 写入根节点 `data-theme`；
- `web/src/styles.css`：内置深色/浅色 Token 和全部组件样式；
- `web/src/components/terminal/TerminalPanel.tsx`：从 CSS 自定义属性同步 xterm 色板。

## 3. 视觉方向：方块工坊

### 3.1 设计原则

1. **专业工具优先**：先保证密度、层级和长时间阅读，再加入卡通像素表达；
2. **硬边而非粗糙**：组件遵循 2px/4px 像素网格，但布局、文字和图表仍使用 CSS 像素精确渲染；
3. **材质表达语义**：石材用于容器，木材用于结构，纸张用于内容，彩色珐琅用于主要动作；
4. **状态不靠装饰猜测**：BUILD、ASK、MODEL、CONTEXT、成功、警告和危险保持文字、图标、颜色多重编码；
5. **层次少而稳定**：每个区域最多三层表面，避免边框套边框和背景纹理压过内容；
6. **原创而非复刻**：只借鉴方块构造、物品槽和工坊心智模型，不复制具体游戏界面。

### 3.2 像素几何

- 基础像素单位：`2px`；主要分隔、内阴影和焦点阶梯使用 `2px` 倍数；
- 面板外框：1px 语义边界 + 2px 内高光/暗边，不使用图片九宫格承载基本布局；
- 圆角：内容卡 `0–4px`，主要 Composer `4px`，pill 只保留给真正的短状态，不再普遍使用 `999px`；
- 阴影：使用无模糊或低模糊的阶梯阴影；代码、Diff 和 Terminal 不使用装饰阴影；
- 图标：功能图标继续使用语义 SVG 和可访问名称；主题可用 `shape-rendering`、方形线帽和第一方 16×16 装饰 sprite 增强像素感；
- 图片：仅装饰性纹理使用 `image-rendering: pixelated`，文字和 SVG 不使用该属性。

### 3.4 字体与图标

- 正文和 CJK：沿用系统 sans 字体栈，不使用像素字体；
- 代码和终端：沿用 `SFMono-Regular` / Consolas / Liberation Mono / Menlo；
- 品牌和短标签：v0.3.3 首版使用 system mono、字距和硬边容器表达像素感，不新增远程或未审计字体；

## 4. 外观契约与默认语义

### 4.1 theme/style 双轴合同

当前 `appearance.theme` 是明暗模式，不能直接扩成像素皮肤，否则旧版 strict validator 会把新值判为非法。v0.3.3 保留 theme 枚举，并增加一个封闭的内置 style 轴：

```ts
type WebThemePreferenceV1 = 'system' | 'light' | 'dark';
type WebUiStylePreferenceV1 = 'classic' | 'orion-blocksmith';

interface WebAppearanceConfigV2 {
  theme?: WebThemePreferenceV1;
  style?: WebUiStylePreferenceV1;
  motion?: 'system' | 'reduced';
}
```

DOM 投影为：

```html
<html data-theme="system" data-ui-style="orion-blocksmith"></html>
```

服务端、Web 协议和客户端必须共享两个封闭枚举。任何其他 style 字符串继续 fail closed，不能被解释为文件路径、包名、URL、CSS 或 JavaScript。`classic` 和 `orion-blocksmith` 都是随包编译的核心外观，不具备插件生命周期。

### 4.2 默认、明暗模式和继承

| 配置状态                     | effective style                       | effective theme                                 |
| ---------------------------- | ------------------------------------- | ----------------------------------------------- |
| style/theme 都未设置         | `orion-blocksmith`，source=`internal` | `system`，source=`internal`                     |
| style=`orion-blocksmith`     | 方块工坊几何与材质                    | theme 决定日间/夜间色板                         |
| style=`classic`              | 现有经典几何                          | theme 保持现有 system/light/dark 语义           |
| theme=`system`               | 当前 style 不变                       | 跟随 OS 明暗，切换对应 style 的日/夜 Token      |
| theme=`light`                | 当前 style 不变                       | 固定明亮色板；参考图定义方块工坊 light 主规格   |
| theme=`dark`                 | 当前 style 不变                       | 固定夜间色板；仍属于同一方块工坊内置风格        |
| Settings invalid/unavailable | style/theme 都使用当前 last-good      | 无 last-good 时使用 `orion-blocksmith + system` |

“重置界面风格”只清除显式 style 并恢复 `orion-blocksmith`；“重置明暗模式”只清除 theme 并恢复 `system`。不得在启动时把内部默认强行写入用户配置，也不得覆盖已有显式 theme。

### 4.3 Settings schema 与兼容性

- `appearance` 增加 style 后，Settings view 使用下一个 schemaVersion（当前基线预期为 `2`）；Phase 0 若 v0.3.2 已占用该版本，则顺延而不是复用；
- v0.3.3 client 在滚动恢复期可读取旧 schemaVersion 1，把缺失 style 投影为内部默认；v0.3.3 Host 只发新 schema；
- 仍打开的旧 Web 页面遇到新 schema 时必须停止 mutation，显示“Workbench 已升级，请刷新”，再从同源 Host 加载新 hashed assets；
- Host/Web client 随同一 npm 包原子发布；旧标签页不得用旧 parser 或旧 nonce 保存新 Settings；
- global `orion.json` 中新增的 `web.appearance.style` 必须由旧版宽容 loader 保留并忽略；回滚到 v0.3.1/v0.3.2 后应自动使用 classic + 原 theme，而不是让整个配置无效；
- v0.3.3 strict validator 只接受 `classic|orion-blocksmith`，非法 style 进入现有 invalid/last-good 诊断链；
- legacy localStorage 迁移继续只迁移 `system/light/dark` theme，不伪造 style；
- 从旧版本升级且没有 style 的用户会看到新的方块工坊默认；这是明确的 v0.3.3 产品变更，Settings 提供一键切换 `classic`；
- 实施必须用真实旧版验证 forward-field 保留、rollback、再次升级和旧标签页刷新旅程，不能只依赖静态推断。

## 5. CSS、组件与资产架构

### 5.1 文件组织

避免把主题继续堆进当前单体 `styles.css`：

```text
web/src/
├─ styles.css                         # 基础 reset、布局、经典主题和兼容入口
├─ themes/
│  ├─ contract.ts                    # 封闭 theme/style 枚举、标签、color-scheme/meta 色
│  ├─ orion-blocksmith.tokens.css    # 颜色、边界、阴影、像素尺寸、Terminal token
│  ├─ orion-blocksmith.components.css# 仅主题几何和组件覆盖
│  └─ orion-blocksmith.assets.css    # 本地 sprite/纹理引用；无远程 URL
└─ assets/themes/orion-blocksmith/
   ├─ sprites.webp                   # 可选第一方小型 sprite atlas
   └─ assets.json                    # 名称、用途、尺寸、license、SHA-256
```

如果最终没有必要使用位图，应删除 `assets.css` 和 sprite，优先用 CSS 与现有语义 SVG 完成。`assets.json` 是构建/审计输入，不是运行时插件 manifest。

### 5.2 层级约束

1. 基础布局和组件行为继续由核心 CSS/React 拥有；
2. `orion-blocksmith.tokens.css` 只定义语义 Token；
3. `orion-blocksmith.components.css` 只在 `:root[data-ui-style='orion-blocksmith']` 下覆盖几何和材质，并用 `data-theme`/媒体查询选择日间或夜间 Token；
4. 不使用 `!important` 作为常规覆盖策略；forced-colors 和 reduced-motion 的必要规则除外并需注释；
5. 不复制一整套 React 组件，不用主题条件分支复制业务 JSX；
6. 若某个视觉形态无法通过 Token/CSS 实现，只增加通用、语义化核心 primitive，例如 `pixel-frame`、`action-slot`，不得创建 `MinecraftButton` 等产品外名称；
7. style/theme 切换只影响 presentation，不触发数据获取、Runtime mutation、Context revision、Session 草稿或布局偏好变化。

### 5.3 资产管线

- 所有主题素材必须位于 `web/src/assets/themes/orion-blocksmith/` 并由 Vite 生成内容哈希文件；
- 禁止 data URL 承载大型素材；小于 1 KiB 的纯装饰图是否内联由 Vite 决定；
- CSP 继续保持 `img-src 'self' data:`、`font-src 'self'`、`script-src 'self'`，不得增加网络域名或 `unsafe-inline` script；
- 位图使用整数倍缩放，避免浏览器模糊插值；
- 素材必须有源文件、导出尺寸、用途、版权/许可和 SHA-256；
- exact tarball 测试必须证明 `dist/web-client/assets/` 中包含全部被 CSS 引用的文件，且没有绝对本地路径；
- installed-package probe 必须 digest 整个 `dist/web-client`，解析并请求 HTML/CSS 引用的 JS、CSS、图片和字体，验证 MIME、CSP、缓存头和 404；不能只校验 `index.html`；
- 构建失败、文件缺失或 CSS URL 失效必须是 NO_GO，不能依赖开发目录兜底。

### 5.4 启动与切换

- `App` 从 Settings ready/last-good 同时读取 effective theme/style，并在同一 commit 更新 `data-theme` 与 `data-ui-style`；
- 根节点的 `color-scheme` 由 theme 决定：light 固定亮、dark 固定暗、system 跟随 OS；方块工坊为同一 style 提供日间和夜间 Token；
- `<meta name="theme-color">` 由 theme/style 组合及 system 媒体查询同步，使浏览器窗口装饰与主题头部颜色一致；
- `TerminalPanel` 保持读取 CSS 自定义属性，MutationObserver 同时监听 `data-theme` 和 `data-ui-style`，外观切换后更新现有 xterm，不销毁 PTY；
- 默认 HTML/CSS 使用 `data-ui-style="orion-blocksmith" data-theme="system"` 的安全首帧基色，Settings ready 后原子覆盖；不得新增 localStorage 外观副本；
- style/theme 切换时禁用非必要过渡，避免整屏颜色动画和 motion sickness；
- 切换过程中焦点、selection、scroll、Terminal buffer、Composer 草稿和打开的 dialog 保持不变。

## 6. 设置界面与交互

### 6.1 Settings 外观项

设置页把外观拆成两个原生 `<select>`，避免 style 和明暗模式串线：

**界面风格**

- `方块工坊（内置，默认）` → `orion-blocksmith`；
- `经典工作台（内置）` → `classic`。

**明暗模式**

- `跟随系统` → `system`；
- `深色` → `dark`；
- `浅色` → `light`。

旁边显示一个纯 CSS 色板预览和“均为内置外观，不支持安装/卸载”的说明；预览不得改变当前 style/theme，只有原子保存成功后才切换 effective appearance。保存按钮可以一次提交两个 dirty key，任何一步失败都不得产生半提交外观。

### 6.2 保存语义

- 沿用现有 draft、dirty key、expected revision、原子 CAS 和 last-good；
- theme/style 都是 `applies: live`，不需要 Runtime idle，也不触发模型/权限 prepare/commit；
- 保存失败时页面保持 last-good appearance，draft 保留用户选择并提供重试；
- revision conflict 按现有 Settings rebase/refresh 处理，不允许浏览器直接覆盖外部修改；
- read-only/invalid/unavailable 状态下禁用保存，仍可用 last-good 渲染；
- 多窗口通过现有 invalidation/SSE 投影到同一 effective appearance，不增加 BroadcastChannel 或第二套同步协议。

## 7. 组件实施范围

### 7.1 Workbench Shell 和导航

- 为工作台背景、三栏边界、header、brand row、project/session slot、active row、Runtime footer 和 resize handle 增加方块工坊 Token；
- 保留当前列宽、min-width、折叠态、drawer 和 pointer resize 计算，不让装饰边框改变布局尺寸；
- active Session 使用左侧蓝色/绿色双编码和清晰文字，不能只靠纹理或阴影；
- 纹理只出现在空白边缘，不得位于项目名、路径、branch、dirty 状态或搜索输入后方。

### 7.2 Conversation、Markdown 和 Tool

- 对话卡使用纸张/石板层级；用户、Orion、reasoning、Tool、approval 和 error 各自保持现有语义；
- Markdown 标题、列表、表格、引用、链接、inline code 和 code block 必须逐项验证；

- 大输出 128 KiB 以上的分页、滚动和复制性能不因纹理或多层阴影回退。

### 7.3 Composer 和瞬态卡片

- Composer 是连续容器，木质外框、纸张输入区和底部控制槽属于同一组件；
- BUILD、ASK/permission、MODEL、CONTEXT 和 send 使用独立语义色，同时保留文字和图标；
- Stop、Steer、Queue、approval、Plan review、Context tray 和错误提示覆盖完整状态；
- textarea resize、IME、Shift+Enter、slash command、draft 恢复和 focus ring 行为不变；
- 低宽度下控制行按既有响应式规则收敛，不通过缩小到不可读字号维持一行。

### 7.4 Work Panel、Terminal 和 Dialog

- Agent、Review、Terminal、Files、Git 的一级入口保持相同顺序、role、快捷行为和 state；
- 终端使用主题专用 CSS Token，但保持等宽字体、字重、selection、cursor、screen reader mode 和 paste confirmation；
- Diff added/removed、Git dirty/conflict 和安全警告使用固定语义 Token，不由木/石材质替代；
- Dialog、menu、tooltip、select、alertdialog、scrim 和空态全部覆盖主题；
- 所有 modal 继续支持 focus trap、Escape、scrim close、关闭按钮和触发器焦点恢复。

## 8. 响应式、无障碍与动效

### 8.1 响应式

复用当前 `1180px`、`760px`、`480px` 断点及 v0.3.2 最终落地断点，不为主题新增独立布局系统：

| 宽度          | 验收重点                                          |
| ------------- | ------------------------------------------------- |
| `>= 1440px`   | 三栏完整、装饰不产生第四栏或额外占位              |
| `1180–1439px` | Work Panel 收敛/rail 与 Composer 宽度正确         |
| `761–1179px`  | drawer/rail 行为和 tab 可达性保持                 |
| `390–760px`   | 左右 drawer 互斥，Composer 和发送按钮不被边框挤压 |
| `320–389px`   | 设置 select、审批动作和主要导航无水平滚动         |

所有像素边框使用 `box-sizing: border-box`；装饰伪元素不得参与 Grid/Flex 尺寸求解，也不得捕获 pointer events。

### 8.2 无障碍

- HTML role、heading、label、aria-current、aria-selected、aria-live 和 dialog 语义不因主题改变；
- 主题选择器明确朗读“方块工坊，内置，默认”，不出现安装或市场暗示；
- `:focus-visible` 使用至少 2px 高对比焦点环并与像素边框分离；
- active、success、warning、danger 使用文字/图标/形状辅助颜色；
- forced-colors 下移除背景纹理与 box-shadow，使用系统颜色和可见边框；
- 200% 缩放、键盘、VoiceOver/NVDA 基础旅程和 CJK 输入必须验证；
- 装饰 sprite 使用 `aria-hidden`，不占据可访问名称。

### 8.3 动效

- 允许：单次 120–180ms 的按钮按压、进度格更新和 drawer 过渡；
- 禁止：循环火焰、闪烁矿物、持续漂浮粒子、视差背景和整屏材质移动；
- reduced motion 下所有装饰过渡归零，保留必要的状态变化；
- 运行中状态不能只通过动画表达，必须有文本和静态图标。

## 9. 安全、隐私与性能

### 9.1 安全与隐私

- 主题不读取 workspace 文件、Session 内容、凭证、环境变量或用户路径；
- 主题素材不包含真实项目名、用户名、绝对路径、token 或生产截图数据；
- 不增加网络请求、analytics、动态 import URL、CSS `@import`、iframe 或 worker；
- 不放宽现有 loopback Host、Origin、nonce、CSP、CORP、COOP 和 Permissions Policy；
- screenshot evidence 继续脱敏并通过受控 basename、regular-file、PNG bounds 和 digest 绑定检查；
- 主题设置 mutation 继续使用 exact Origin、nonce、JSON、revision 和 secret-free projection。

### 9.2 性能预算

- 新增首屏 CSS gzip 目标不超过 24 KiB；
- 新增图片/字体压缩总量目标不超过 160 KiB；首版不新增字体；
- 单个组件最多两层装饰伪元素，滚动列表项不得逐项创建大纹理或滤镜；
- 禁止在 transcript、Session 列表、文件树和大输出每个 row 上使用 blur、filter 或大面积 box-shadow；
- 主题切换不得重建 transcript、Terminal、文件树或 Git Diff；
- 1440×960、DPR 2 的持续滚动和 resize 目标保持 55–60fps，不出现长于 50ms 的主题相关 long task；
- `content-visibility`、虚拟化和分页行为保持现有实现，不为视觉效果关闭。

## 13. 验收标准

### AC-01 内置主题边界

Given v0.3.3 Web Workbench，When 检查配置、构建产物和网络，Then theme 仍是封闭的 system/light/dark，style 只有 classic/orion-blocksmith 与本地素材；不存在 plugin SDK、marketplace、安装/卸载、目录扫描、远程主题或可执行主题代码。

### AC-02 默认与兼容

Given 没有显式 Web style/theme，When 首次打开或重置 Settings，Then effective appearance 为 `orion-blocksmith + system`；Given 已显式设置 system/light/dark，When 升级，Then theme 原值继续控制新 style 的明暗；选择 classic 可恢复旧几何。

### AC-03 实时切换

Given 活动 Session、已输入草稿和已连接 Terminal，When 原子保存 style/theme，Then 页面无刷新切换，草稿、焦点、scroll、Terminal buffer、PTY、Context 和 Session 均不改变。

### AC-04 视觉一致性

Given 任一主要 Workbench 状态，When 使用方块工坊主题，Then Shell、导航、Conversation、Tool、Composer、Work Panel、Terminal、Dialog 和菜单使用同一 Token/几何系统，没有经典圆润 SaaS 样式残留或边框套娃过载。

### AC-05 可读性与无障碍

Given 键盘、200% zoom、forced-colors 或 reduced-motion，When 完成项目切换、发送、审批、查看 Diff 和打开设置，Then 旅程可完成、focus 可见、语义完整、axe blocking violations=0，颜色/纹理不是唯一状态信号。

### AC-06 响应式

Given 320–1920 CSS px，When 导航和 Work Panel 在 dock/rail/drawer 间切换，Then 像素边框不改变列宽求解，不遮挡 Composer，不产生页面级横向滚动，触发器焦点可恢复。

### AC-07 Terminal 与工程内容

Given 终端、代码、Diff 和 128 KiB Tool 输出，When 主题切换并持续滚动，Then 内容保持等宽、selection/cursor 正确、红绿状态清晰、分页与复制可用，且不重建 PTY。

### AC-08 安全与发布

Given source-clean exact tarball，When clean install 并运行真实 Chrome 门禁，Then CSP 不放宽、资产只来自 self、包内文件完整、截图/manifest/receipt digest 绑定，所有 release gate 为 GO。

### 18.3 问题定义与用户场景

#### 核心用户场景

1. 用户在 Session A 启动长任务后，立即选择 Session B 查看历史或提交另一任务；A 在后台继续运行；
2. Session A 等待工具审批时，用户可以处理 Session B，并能从任何会话看到 A 的待审批标记；
3. 用户在 A、B 之间来回切换时，最近内容应立即出现，不能反复重建 Runtime 或重拉所有目录与历史；
4. 两个浏览器标签页可各自停留在不同 Session；一个标签页的前台选择不能改变另一个标签页；
5. 用户折叠右栏后，中栏保持原位置和全高，48px rail 始终位于右侧，不能掉到页面底部；
6. 用户只在左侧项目栏底部看到一个持久 Settings 按钮；窄屏时先打开左侧 drawer，再从其底部进入。

#### 成功指标

- 同一 Host 内至少支持 3 个 Session turn 并行执行；第 4 个请求进入可见、可取消的等待队列，而不是
  阻止用户切换或静默丢弃；
- Session A 运行时切换到 B 的成功率 100%，A 的 provider/tool/approval/turn journal 不被停止、重建或
  归属到 B；
- warm Session 选择到缓存内容可交互的 p95 不超过 150ms；cold Session 最新 100 条记录可交互的 p95
  不超过 800ms；
- 一次 Session 选择不得关闭/重连全局 SSE，不得重新请求 Settings、Skills、MCP、Tool catalog 或完整
  workspace list；
- 10,000 条消息的 Session 切换只读取目标页和 cursor 后增量，不扫描/发送全部历史；
- 背景 Session 的状态、审批、完成和错误事件丢失数为 0，跨 Session 错投命令/消息/审批/工具结果为 0；
- 320、390、760、1024、1180、1181、1440、1920px 下，右栏折叠/展开和 drawer 往返均无下沉、重叠、
  页面级横向滚动或焦点丢失；
- 正常已配置页面中，accessible name 为 `打开设置` 的持久按钮恰好 1 个，位于左侧项目栏 footer。

## 19. Track B 目标架构

### 19.1 从“唯一活动 Runtime”改为“Workspace Kernel + Session Actor”

Web Host 增加 `WebSessionRuntimeRegistryV1`，key 为 `{workspaceId, sessionId}`。每个 Session actor 独立
拥有：

- `OrionRuntimeV1` / Thread owner；
- `AgentRuntimeController`、turn/queue/Goal/Plan 状态；
- pending approval、interrupt signal、Session model/effort/permission override；
- Thread observer、durable cursor 和当前投影 revision；
- actor lifecycle：`cold | starting | idle | queued | running | waiting_approval | stopping |
interrupted | failed`。

同一 workspace 的 actors 共享只读或并发安全的 `WorkspaceRuntimeKernelV1`：配置快照、model client pool、
provider request gate、Tool catalog、Skill/MCP descriptors、Settings coordinator 和安全策略。禁止为每个
Session 重复创建 Settings watcher、全局 registry 或无边界 MCP 连接。

旧 `OrionSessionRunnerV1` 不直接扩成一个持有多 Runtime 的巨型类；它继续服务单 Session surface。
Web registry 负责多个 actor 的创建、路由、并发 admission、资源回收和 shutdown。这样可以避免把 Web
并行语义意外带入 TUI。

### 19.2 前台选择只属于浏览器视图

`foregroundSessionId` 是每个浏览器标签页的本地视图状态，不再是 Host 中唯一全局 active Session：

```text
browser tab viewId
  -> foreground { workspaceId, sessionId }
  -> cached SessionProjection
  -> guarded snapshot/delta refresh

Host WebSessionRuntimeRegistry
  -> actor[A] continues running
  -> actor[B] accepts independent command
  -> actor[C] may remain cold/idle
```

- 标签页使用 `sessionStorage` 保存非敏感 `viewId` 和前台选择；它不是认证凭据；
- 浏览器选择 Session 不触发 Host `select_session`、旧 Runtime close/start 或全局 context revision 变化；
- Workspace/Session 资源 API 必须显式携带 identity 和 revision，不能再从 Host 的“当前 Session”推断目标；
- 多标签页选择相互独立；Settings、workspace registry 和 durable Session metadata 仍由 Host 统一管理。

### 19.3 命令、审批和事件合同

v0.3.3 Web protocol 需要新的显式路由合同；最终字段名以 OpenAPI 和 TypeScript 共享类型为准：

```ts
interface WebSessionCommandTargetV2 {
  workspaceId: string;
  sessionId: string;
  expectedWorkspaceRevision: string;
  expectedSessionRuntimeRevision: string;
}

interface WebSessionRuntimeSummaryV1 {
  workspaceId: string;
  sessionId: string;
  runtimeRevision: string;
  phase:
    | 'cold'
    | 'starting'
    | 'idle'
    | 'queued'
    | 'running'
    | 'waiting_approval'
    | 'stopping'
    | 'interrupted'
    | 'failed';
  queuePosition?: number;
  pendingApprovalCount: number;
  updatedAt: string;
}
```

- submit/queue/steer/interrupt/Goal/Plan/permission decision 都绑定 exact Session actor；
- stale workspace/session/runtime revision 返回 409 `session_runtime_revision_conflict`，零 provider 调用、零 Tool
  调用、零 journal append、零文件副作用；客户端先刷新目标 Session，绝不自动重放 submit；
- approval response 同时核对 `sessionId + requestId + invocationId`，不能用前台 Session 的 request map 回答后台
  Session；
- SSE 可以维持单一连接，但所有 Session 事件必须带 `workspaceId/sessionId/threadId/runtimeRevision`；客户端
  只把完整内容投影到对应 Session cache，不能把非前台事件丢弃或写入当前 transcript；
- Runtime summary 在 bootstrap/snapshot 可重建；若某类 live status 不可重放，断线后必须通过 guarded snapshot
  收敛，不能伪装为 durable event；
- foreground selection 不关闭 EventSource；只有 Host restart、协议升级或 replay barrier 才重建连接。

### 19.4 并发预算与同工作树安全

首版默认 `maxRunningSessions=3`、`maxResidentSessionActors=4`，配置允许范围 `1–8`；两个限制必须独立：

- 达到 running 上限时，新 turn 进入 FIFO 队列并显示位置，用户仍可切换、查看、审批和取消；
- running、waiting approval、queued、stopping 的 actor 不得被 LRU 回收；
- idle actor 按最近使用和估算字节回收；回收前关闭 observer/client/Tool scope，但不删除 Session/Thread 数据；
- resident 全为不可回收状态时，允许打开任意 Session 的只读 snapshot，但新 turn 返回明确的
  `session_concurrency_limit`；
- provider 请求继续通过共享 provider gate，不能让三个 actors 绕过账户级 cooldown/429 保护；
- 相同 workspace 的 `write_file`、`edit_file`、潜在写入型 `exec_command` 等经过共享
  `WorkspaceMutationArbiterV1`。LLM 推理和只读工具可并行，变更型工具按 invocation 排队并在 UI 标明等待；
- 不自动合并并发写入。文件基线或 Git revision 变化时 fail closed，要求用户在目标 Session 重新确认；
- 不同 workspace 的变更型工具可以并行，但仍受全局 provider、进程和用户配置预算约束。

### 19.5 Session 切换读模型

Session 选择采用两阶段显示，不等待 Runtime 创建完成才切 UI：

1. **即时阶段**：从浏览器受限 LRU `sessionProjectionById` 显示最近快照、草稿和 Runtime badge，立即更新
   `aria-current`、标题和主区域；
2. **收敛阶段**：请求目标 Session 最新一页（默认 100 条）和 cursor 后增量；若 actor 为 cold，只在用户提交
   新 turn 或需要 live control 时启动 actor；
3. **历史阶段**：更早 transcript 继续显式分页，不因切换自动 drain 所有页面；
4. **恢复阶段**：snapshot revision/cursor 不匹配时，只清理目标 Session cache 并重取该 Session，不重置
   Settings、Workspace、Skills、MCP、Tool catalog 或其他 Session 投影。

服务端需提供可直接分页的 immutable transcript/read-model 索引。每页不得先 materialize 全部 transcript，
不得把全部 `TurnCommit.history` 解析后再 slice。warm actor 和 cold snapshot 都必须记录 scan count、bytes read、
snapshot build time 和 response bytes，以便在真实长 Session 中验证目标。

### 22.2 Given / When / Then

#### AC-B01 运行中切换

Given Session A 的 provider stream 被受控 hold 且 Runtime phase=`running`，When 用户选择 Session B，Then
150ms p95 内显示 B 的缓存内容，A 仍为 running，Host 没有关闭 A Runtime、没有返回 `runtime_busy`，全局 SSE
连接 ID 不变。

#### AC-B02 真正并行

Given running slots 可用，When A 与 B 分别提交确定性任务，Then 两个 turn 可以同时处于 running；每个输出、
Tool receipt、approval、Goal/Plan commit 和 token usage 只出现在其 Session；任一 Session interrupt 不影响另一个。

#### AC-B03 同工作树写入安全

Given A、B 在同一 workspace 请求变更型 Tool，When 两个 invocation 时间重叠，Then workspace arbiter 只允许一个
进入副作用阶段，另一个显示等待；文件基线过期时后者 fail closed，不自动覆盖或合并。

#### AC-B04 切换性能

Given warm Session 和 10,000-message cold Session，When 连续切换 30 次，Then warm p95 ≤150ms、cold p95
≤800ms；每次最多取目标最新页和 cursor delta；Settings/Skills/MCP/Workspace catalogs 请求数为 0，SSE reconnect
和 replay reset 为 0。

#### AC-B05 多标签与恢复

Given两个标签页分别选择 A、B，When 任一标签页切换或提交，Then 另一标签页前台不变；stale actor revision
返回 409 且 provider/tool/journal/file/approval 五类副作用都为 0；刷新后从 guarded snapshot 收敛。

#### AC-B06 右栏位置

Given Work Panel 展开，When 折叠并依次跨越 1920→1440→1181→1180→1024→760→390→320→1440，
Then desktop rail 始终位于右侧且高等于 shell，drawer 不占 Grid 行列，中栏 `top/bottom` 不变，无页面级横向滚动，
回到 1440 后恢复用户桌面偏好。

#### AC-B07 Settings 唯一入口

Given 正常已配置 Workbench，When 检查 expanded left rail、collapsed rail 和 mobile drawer，Then 只有左侧底部
存在 `打开设置` 持久按钮；中栏和右栏 header 不存在 Settings icon；打开/关闭 dialog 后焦点正确恢复。

#### AC-B08 关闭与崩溃语义

Given多个 actor 处于 running/queued/waiting approval，When Host graceful shutdown 或被终止后重启，Then graceful
路径逐 actor abort/close 并无 orphan；崩溃路径从 durable facts 标记 interrupted，pending approval fail closed，任何
started invocation 不被自动重放。

### 22.3 发布门禁补充

- Track B unit/integration tests 在 Node 22.12、受支持的 24 和 26 通过；
- exact tarball 的 primary Chrome 至少 3 个 fresh run，runtime matrix 每个 Node major 至少 1 个 critical run；
- WEB33 receipt catalog 同时要求 Track A `01..12` 与 Track B `16..24` 的 P0 场景；缺失、skip、expected-fail、
  screenshot/fact 缺失或 artifact digest 不一致均 NO_GO；
- 并行测试必须使用真实 `OrionRuntimeV1`、ToolGateway、durable Thread journal 和确定性 loopback provider；fake
  runtime 只能做 unit，不可作为 release proof；
- raw trace/video/network body 仅落受控 ignored evidence 目录；receipt 只保存脱敏 facts、相对证据路径和 digest；
- 在 source-clean commit 生成一次 tarball，所有 Node/Chrome 运行复用同一 SHA，不得用 source Host 截图替代安装包。

## 23. Track B 风险、决策门与 Definition of Done

### 23.1 主要风险

| 风险                         | 影响                                              | 缓解                                                                 |
| ---------------------------- | ------------------------------------------------- | -------------------------------------------------------------------- |
| 直接放开切换按钮             | 正在运行的旧 Runtime 被关闭或命令落入错误 Session | actor registry 完成前保持 fail closed；先做 integration failure test |
| 多 actor 复制 workspace 服务 | watcher/MCP/provider/Settings 重复、内存失控      | shared kernel + session-owned actor，按资源 scope 评审               |
| 同工作树并行写               | 文件覆盖、命令相互污染                            | workspace mutation arbiter、基线 revision、无自动合并                |
| 全局 SSE 被背景流量挤满      | reconnect gap、前台事件丢失                       | session-tagged budget、snapshot recovery、事件/字节压力门禁          |
| 浏览器缓存无限增长           | 长会话拖慢或崩溃                                  | per-Session byte-bounded LRU，只缓存最新页和必要状态                 |
| 布局仅靠 z-index 修补        | 另一断点再次下沉/遮挡                             | explicit grid areas、单 solver、geometry matrix                      |
| Settings 删除后窄屏不可达    | 用户找不到配置                                    | left drawer footer 保留、真实鼠标/键盘/focus 旅程                    |
| Track A/B 同改 Shell         | CSS 冲突、截图基线反复变化                        | B3 先合并；A 只在稳定 DOM/layout 上加 Token/主题                     |

### 23.2 决策门

1. **Gate B0 — 根因**：四项失败均可复现，网络与 geometry 证据齐全；
2. **Gate B1 — 所有权**：两个真实 Session actor 同时运行且无跨 Session 污染；
3. **Gate B2 — 性能**：切换不再 close/start、pause SSE 或 load full baseline，p95 达标；
4. **Gate B3 — Shell**：右栏全断点 geometry 和单 Settings 入口通过；
5. **Gate B4 — 发布**：Track A/B exact-tarball receipts 全部 GO。

任一 Gate 未通过时，不得只把 UI 按钮改为 enabled，也不得宣称“已支持并行”。

### 23.3 Definition of Done

- [ ] Web 不再由一组全局 active Runtime/Controller 代表所有 Session；
- [ ] A running/waiting approval 时可选择并运行 B，A 不被停止或重建；

- [ ] 3 running / 4 resident 默认预算、FIFO、LRU、shutdown 和 interrupted recovery 有确定测试；
- [ ] 同 workspace 变更型 Tool 有共享仲裁，跨 Session 权限和副作用为 0；
- [ ] Session switch 不 pause SSE、不 load global baseline、不全量读取 transcript；
- [ ] warm/cold/10k history p95、bytes、scan、request count 达到预算；
- [ ] 背景 Session badge、approval、completion、error 与 active transcript 均正确；
- [ ] 右栏折叠后在所有目标宽度保持右侧全高 rail，drawer/desktop preference 往返正确；

- [ ] Track A 主题在 Track B 稳定 Shell 上重新截图并通过全部既有门禁；
- [ ] 在实现、测试和 exact-tarball 门禁完成前，v0.3.3 状态保持 `Proposed / 待评审`。

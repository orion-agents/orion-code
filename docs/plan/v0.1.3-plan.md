# Orion Code v0.1.3 开发计划（模型配置、运行时可靠性与 TUI 体验）

> 本文同时作为 v0.1.3 的 Technical Book。`HEAD`、工作树候选和发布产物必须分开记录；未提交代码、临时 dist 或局部测试不能直接作为发布证据。

## 1. 问题定位（当前状态）

你本机的 `~/.orion-code/orion.json` 内容表明当前默认模型是 `ark-code-latest`，且上下文窗口为 `1024000`，所以配置读取链路本身是对的。  
但 `/model` 命令当时仍有两处来自“静态 catalog / legacy 语义”的展示偏差（该历史问题已由 §6 的 `/models` 重构收敛）：

- `/model list` 直接读取 `listModelCatalogEntries()`（静态目录），不是当前生效的 `providers/models` 配置；
- `resolveModelContext()` 没有在 CLI 显示层优先使用 `ModelRegistry` 的已解析 `resolvedContextWindow`；
- `/model <alias>` 只走静态 `resolveModelAlias`，没有优先使用配置中的 profile alias / id 映射；
- `/model info` 对 `currentModel` 的展示信息与 `store.currentModel`、`llm.getModel()` 的语义存在偏差风险。

此外，当前代码中还有一处可确认的结构性冗余：

- `src/runtime/model-coordinator.ts` 已有完整的注册表切换能力，但 `src/cli.ts` 创建后未在命令层接入；
- CLI 仍以“字符串替换模型”方式切换，未将 registry profile 的 `provider/model` 绑定能力上抬到 `/model` 命令流程。

## 2. v0.1.3 目标

做到 `/model` 命令显示与实际运行一致（single source of truth = `modelRegistry`）：

- `/model` 当前模型信息与 `/models` 候选列表以 `ModelRegistry.enabledProfiles` 为主；
- Context/Output 来源显示为 `resolvedContextWindow` / `resolvedMaxOutputTokens`；
- 切换命令优先解析 registry selector（id/alias/prefix）；
- 帮助、picker 和迁移提示同步展示 registry alias，避免文案误导。

## 3. 变更范围（建议落地顺序）

### 3.1 代码改动（P0）

1. `src/commands/index.ts`
   - `handleModel()`：
     - 当前模型信息优先从 `ctx.config.modelRegistry` 匹配 profile；
     - `/models` 从 `modelRegistry.enabledProfiles` 构建列表（fallback 到 catalog）。
     - `/model <name|alias>` 先尝试 `lookupProfile(config.modelRegistry, selector)`；
     - 切换成功后 `llm.setModel()` 写入 profile 的实际 `model`，`store.currentModel` 记录 profile id。
     - 帮助 alias 合并 catalog + registry aliases。
2. `src/services/model-catalog.ts`（可选）
   - 保持静态 catalog 作为 metadata/legacy 来源，不参与“可切换模型集合”判定。

### 3.2 回归与新增测试（P0）

1. `tests/status-command.test.ts`
   - 覆盖：
     - `~/.orion-code` 风格 registry 的 `/model list` 仅展示已启用 profile；
     - `/model` 信息显示使用 profile context；
     - registry alias 切换行为验证（`ark` -> `ark-code-latest`）；
     - `/model help` 中 alias 列表包含 registry alias。

### 3.3 边界修正（P1）

- 评估并串联 `ModelCoordinator`：把 profile 切换、provider 选择、client 检查、compact 前置判断、模型变更事件统一到命令流程，避免继续“字符串切换”与 runtime client 不一致。
- 若未在本次发布内完成，上述点需写入 v0.1.3 release note 的延期项。

## 4. 验收标准（DoD）

- `/models` 中的 `ark-code-latest` 显示 `1.0M ctx`（来源 profile），不再依赖 catalog 假阳性项；
- `/model` info 的 Context/Output 与 `model-registry` 解析值一致；
- registry alias 切换测试通过，且 `store.currentModel` 为 profile id；

## 6. 模型命令重构（model-command-refactor）

> 在 §1–§5 的「模型配置一致性」基础上，进一步重构模型相关命令的**用户交互面**与**内置目录**，使模型切换更直观、上下文兜底更完整。

### 6.1 命令面变更

| 命令 | 行为 | 说明 |
| --- | --- | --- |
| `/model` | 仅展示**当前模型信息** | `''` / `info` / `?` 等价；显示 Model / Alias / Provider / Context / Output / Source / Compact |
| `/model <selector>` | 切换模型 | `selector` = id / alias / 唯一前缀；解析顺序 `lookupProfile` → `resolveModelAlias`；切换后 `llm.setModel(profile.model)` + `store.currentModel = profile.id` |
| `/models` | **交互式选择切换** | 交互式渲染器返回 `modelPicker` 结构化请求（渲染器弹出选择层，选中即 `/model <id>`）；非交互式渲染器打印候选列表并提示 `Use /model <id> to switch` |
| ~~`/model list`~~ | **删除** | 能力迁移到 `/models` |
| ~~`/model help`~~ | **删除** | alias 信息与切换用法并入 `/models` 列表与 `/model` 信息输出 |

- 切换逻辑（`/model <selector>` 的 switch 分支）保持不变，并被 `/models` 选择回调复用（选中即等价于执行 `/model <id>`）。
- 命令注册：保留 `model`；新增 `models`（category `model`，priority 10，argHint 空，execution `builtin`）。

### 6.2 内置目录（catalog）补全

目标：当**已配置的模型未显式写 context 上下文长度**时，自动回退到内置目录的真实值（例如 `glm-5.2` → 1M / 128K）。

目录现状（共两处，需统一补全）：

- `src/services/model-context.ts` 的 `BUILTIN_MODELS` —— 带 `provider` + `contextWindow` + `maxOutputTokens`，由 `resolveModelContext` / `getModelContextWindow` 广泛使用（legacy 路径、compact、diagnostics）。
- `src/services/model-registry.ts` 的 `BUILTIN_CATALOG` —— 仅 6 个模型，由 `resolveModelProfile` 的 `builtin` 兜底使用（registry 路径，即 `/model info` 与 `/models` 选择列表的来源）。
- `src/services/model-catalog.ts` 的 `MODEL_CATALOG` —— 仅 `name/alias/provider`，无 context，用作 alias / provider 展示元数据。

变更：

1. **补全 `BUILTIN_MODELS`（model-context.ts）** 为完整常用模型目录：新增本机配置涉及的 `glm-5.2`(1M/128K)、`kimi-k2.7-code`(256K/32K)、`deepseek-v4-pro`(1M/384K)、`ark-code-latest`(1M/128K)，并补齐 `qwen-long` 等已有条目缺失的上下文；保持现有 `provider` 归属（anthropic / openai / qwen / glm / moonshot / minimax / deepseek / astroncodingplan）。
2. **补全 `BUILTIN_CATALOG`（model-registry.ts）**：新增上述 API 模型 id 的 `contextWindow`/`maxOutputTokens`，使 registry 路径的 `builtin` 兜底可用；并让 `resolveModelProfile` 的 `builtin` 分支**优先查询 `BUILTIN_MODELS`**，未命中再回退 `BUILTIN_CATALOG`，未命中才用 `DEFAULT_*`。
3. **补全 `MODEL_CATALOG`（model-catalog.ts）**：新增上述模型并补齐 `provider`，为 alias / 选择列表展示提供一致的供应商信息；`ModelCatalogEntry` 增加可选 `contextWindow`/`maxOutputTokens`（取自 `BUILTIN_MODELS`），供未配置模型在选择列表中显示上下文。

解析优先级保持不变：`config > discovery > builtin > default`；「builtin」层同时覆盖 `BUILTIN_MODELS` 与 `BUILTIN_CATALOG`。

### 6.3 交互式选择机制（复用 sessionPicker 管线）

`/models` 的交互式选择与 `/resume` 的会话选择走同一套渲染器管线：

1. `CommandResult` 增加 `modelPicker?: ModelPickerRequest`（与 `sessionPicker` 平级）。
2. `src/runtime/chat-controller.ts`：`if (result.modelPicker) { this.events.showModelPicker(result.modelPicker); return; }`。
3. `src/runtime/ui-events.ts`：新增 `ModelPickerRequest`（`{ models: ModelPickerCandidate[]; currentModel?; title?; maxVisibleItems? }`，复用 `createModelPickerState` 形态）与 `UiEventSink.showModelPicker`。
4. **TUI**（`tui-ui/`）：
   - `state.ts` 增加 overlay 类型 `model`（`{ type: 'model'; request: ModelPickerRequest; selectedIndex: number }`），处理 `showModelPicker` action。
   - `layout.ts` 增加 `state.overlay.type === 'model'` 渲染分支（列表形式，标记 `isCurrent`）。
   - `runner.ts`：选择（Enter / 数字）回调 `submit(`/model ${id}`)`，复用既有切换逻辑。
   - `launch.ts`：`consumeModelPickerSelection` 把选择翻译为 `/model <id>` 文本提交（与 `consumeSessionPickerSelection` 对称）。
5. **terminal-ui**（`terminal-ui/launch.ts`）：镜像 `pendingPicker`/`showSessionPicker` 实现 `pendingModelPicker`/`showModelPicker` + `resolveTerminalModelPickerInput`，分页与取消逻辑一致；选中提交 `/model <id>`。

非交互式渲染器（`structuredPickers: false`）下，`/models` 直接打印候选列表（复用既有 `createModelPickerState` + 列表渲染），不进入结构化选择。

### 6.4 测试与验收（DoD）

- `tests/status-command.test.ts`：
  - 原 `/model list` 两个用例 → 改为 `/models`：交互式渲染器断言 `result.modelPicker` 存在且含候选；非交互式渲染器断言打印 `Available Models` 列表。
  - 原 `/model help` 用例 → 改为断言 `/model help` 已移除（等价于当前模型信息输出），并新增 `/models` 结构化请求断言。
  - 保留 `/model` 当前信息、`/model <alias>` 切换、`/model <id>` 切换等用例。
- 新增：configured 模型未配 context 时（`glm-5.2`）解析为 catalog 兜底值（1M/128K）的断言（registry 路径 + legacy 路径各一）。
- `tsc --noEmit` 通过；`npm test -- --runInBand tests/status-command.test.ts` 全部通过；`npm run build` 成功。

## 7. TUI 权限级别交互（toolConfirmation 实时切换）

> 背景：v0.1.2 bug-hunt 期间发现全局配置 `toolConfirmation` 被设为 `deny`（~/.orion-code/orion.json:78），
> 导致 `git config` 等"需确认"命令被无提示拒绝（tool-scheduler.ts:325-337，source=config_deny）。
> 已临时改为 `allow`。本章把"切换权限级别"做成 TUI 原生能力，且**即时改写内存、立刻生效，并在状态栏展示当前级别**。

### 7.1 目标与用户面

- 新增 TUI 命令 `/permissions`：
  - `/permissions` （无参）→ 弹出单选浮层，列出 `allow` / `ask` / `deny`，当前值高亮，方向键移动、Enter 确认、Esc 取消。
  - `/permissions <allow|ask|deny>` （带参）→ 直接设置，不走浮层（headless/快速切换用）。
- 选中后立即：
  1. 落盘：`updateGlobalConfig({ toolConfirmation: value })` → 写入 `~/.orion-code/orion.json`；
  2. 即时生效：改写运行时内存 `this.runtime.config.toolConfirmation = value`，后续工具调用立刻用新值（无需重启）；
  3. 状态栏实时显示 `perm:<level>`；
  4. 在会话里追加一条系统消息确认（如 `Tool confirmation → ask`）。
- 错误输入（`/permissions foo`）→ 清晰报错并提示合法取值。

### 7.3 关键实现细节

- **即时生效的正确性**：调度器在每次工具调用时实时读取 `toolConfirmation`——
  `chat-controller.ts:2170` 传入 `this.runtime.config.toolConfirmation`，`tool-scheduler.ts:293` 取 `confirmation = toolConfirmation ?? 'ask'`。
  因此只要改写 `this.runtime.config.toolConfirmation`（与 2170 读取的是同一对象），下一刀工具调用立即生效。
  ⚠️ 必须在控制器里核对 `this.runtime.config` 即 2170 所用的那个对象（而非某份启动拷贝）；若为拷贝则需同时改写 2170 的来源字段。实现后用一个单测断言：change 后 `runtime.config.toolConfirmation === value`。
- **`permission` vs `toolConfirmation` 浮层**：已有 `overlay.type==='permission'` 是"单工具确认弹窗"（runner.ts:475/661，`answerPermission`），**不要复用**，本次用新类型 `toolConfirmation`，职责分离。
- **状态栏初值**：runner 构造时把当前 `runtime.config.toolConfirmation` 作为 `state.permissionMode` 初值，保证状态栏一开始显示真实级别（当前磁盘为 `allow`）。
- **`blocked` 级不受影响**：无论切到 `allow`/`ask`/`deny`，`tool-scheduler.ts:280` 对 `permission.behavior==='deny'`（如 `rm -rf`）始终拦截，安全网不变。
- **非 TUI 兜底**：`/permissions` 仅注册 `rendererScope:['tui']`；terminal-ui 下不提供。若想在 CLI 也快速切，可后续把"扩展 `/config set`"（Option A）作为独立小增量的 follow-up，本计划不强制包含。

## 8. 运行中增量输入（Incremental Steering）：即时回显 + 上下文累积

### 8.1 现象与问题定位（代码实测）

用户场景：agent 运行中（`grep`/`exec_command` 多工具并发，状态栏 `[tools:2 perm:allow]`），用户补充输入意图纠正方向（如把"讯飞模型在 a2a-python"纠正为"实际在 `~/.orion-code/orion.json`"）。终端出现 `Revision received. Interrupting current response...`，但用户感知"响应很慢、看不到自己输入"。

顺代码链路定位（均为当前 `v0.1.2`/HEAD 实况）：

1. **运行中提交不即时回显（核心"慢"根因）**
   - `submit()` 在 `turnController.hasActiveTurn()` 为真时（agent-runtime-controller.ts:497-532）只做 `emitStatus('Revision received...')`（529-531）+ `turnController.requestRevision(submitted)`（528），**不把用户输入写进 transcript**。
   - 用户文本真正回显发生在**下一轮开始时**：run-loop 内 `if (echoSubmittedInput ?? true && request.echoToTranscript) emitAppend(submittedEntry(nextInput))`（1089-1090）。即必须等当前轮**完整 abort** 后才出现。
   - 结果：在 abort 窗口（多工具仍在跑、`[tools:2]`）里，用户只看到一行状态文案，自己打的字不在记录里 → 体感"慢/没反应"。

2. **多次增量被覆盖（违背"增量"语义）**
   - `turn-controller.ts:61-69` `requestRevision`：`this.pendingRevision = input`（64 行**赋值覆盖**）。运行中连补两条，只有最后一条进 `pendingRevision`，前面全部丢失。
   - 而目标模式下 `submit()` 已对每条调用 `gc.addConstraint(submitted)`（509-525）做**累积**，两套语义不一致。

3. **下一轮是"替换"而非"叠加"上下文**
   - abort 后 run-loop 用 `pendingRevision` 重建 request：`inputKind:'revision', text: revision`（1161-1165），整轮输入被替换为最后一条增量。普通对话模式靠对话历史保留原意，但"最新 user message"只是增量片段，模型需自行从历史拼回原目标；若多条增量被覆盖（见 2），上下文已失真。

4. **状态文案不表达"已接收/等待/调整"**
   - `revisionStatus` 默认 `'Revision received. Interrupting current response...'`（530）、`restartingStatus` 默认 `'Restarting with latest instruction...'`（1159）只说"打断/重启"，不告诉用户"你的补充已记录、下一轮据此调整方向"。

### 8.2 设计目标（对齐用户意见）

> 用户意见：输入要**展示到记录**出来 → **等待下一轮增量处理** → **根据上下文调整方向**。

- **G1 即时回显**：运行中提交的增量输入，在 `submit()` 当下就写入 transcript（不等 abort）。
- **G2 累积不丢**：运行中连续多条增量应**追加累积**（换行连接），而非覆盖最后一条。
- **G3 上下文调整而非丢失**：下一轮把"原始目标 + 累积增量"一并交给模型做方向调整（普通对话模式复用历史 + 把累积增量作为 steering 文本；目标模式沿用 `addConstraint` 累积 + 下一轮 prompt 也带累积增量）。
- **G4 状态可见**：状态条/状态栏明确表达"已接收补充 → 正在中断当前轮 → 下一轮据此调整"。

### 8.3 改动方案（按 file:line）

**Step 1 — 即时回显（G1）**
`submit()` 的 `hasActiveTurn()` 分支（agent-runtime-controller.ts:527-532），在 `requestRevision` 之后、保留 `emitStatus` 的同时，立即回显：
```ts
this.turnController.clearExitIntent();
this.turnController.requestRevision(submitted);
// G1: 立刻把增量写进记录，不等 abort
this.emitAppend(submittedEntry(submitted));   // 复用既有 submittedEntry（user/command 角色自动判定）
this.markRevisionEchoed();                     // 防下一轮重复回显（见 Step 2）
this.emitStatus(this.options.revisionStatus ?? '已接收补充，正在中断当前轮…');
return { type: 'revision_requested' };
```
- 命令型输入仍走"忽略"分支（499-504），不回显（保持现有行为）。
- `submittedEntry` 形如 `{role:'user'|'command', title:'you'|'command', content}`（133-140），增量天然以用户消息落记录，无需新类型。

**Step 2 — 防重复回显（G1 配套）**
- 新增控制器字段 `private revisionEchoed = false;` + `markRevisionEchoed()`；在 `beginTurn`/新轮开始时复位。
- run-loop 回显门（1089）改为：
  ```ts
  if ((this.options.echoSubmittedInput ?? true) && request.echoToTranscript && !this.revisionEchoed) {
    this.emitAppend(submittedEntry(nextInput));
  }
  ```
  即"运行中已即时回显过的增量，下一轮不再重复 echo"。`revisionEchoed` 在 `beginTurn`(line 40) 或 run-loop 每轮开头复位。

**Step 3 — 增量累积（G2）**
`turn-controller.ts:61-69` `requestRevision`：把覆盖赋值改为追加（带分隔）：
```ts
requestRevision(input: string): boolean {
  if (!this.activeTurn) return false;
  this.pendingRevision = this.pendingRevision
    ? `${this.pendingRevision}\n${input}`   // 累积，不丢
    : input;
  this.status = 'aborting';
  if (!this.activeTurn.abortController.signal.aborted) this.activeTurn.abortController.abort();
  return true;
}
```
- 目标模式侧：现有 `gc.addConstraint(submitted)`（513）逐条累积已正确；保持一致即可（无需改）。但注意：目标模式下的 `pendingRevision` 现在也会累积，run-loop 重建 request 时 `text` 即为累积文本 → 下一轮 prompt 同时含多条增量（G3 普通模式同理）。

**Step 4 — 状态文案（G4）**
- `revisionStatus` 默认改为 `'已接收补充，正在中断当前轮…'`；
- `restartingStatus` 默认改为 `'根据补充调整方向中…'`（1159）；
- 可选增强：状态栏 `activity` 数组（layout.ts renderStatus，§7.3 已加 `perm:` 芯片的位置）在 `turnController.getSnapshot().pendingRevision` 存在时追加 `steering` 芯片，让"正在吸收补充"在状态栏可见。

**Step 5（可选/深层）— 加快中断响应**
- 中断实际延迟来自在跑工具未及时检查 `abortSignal`。`requestRevision` 已 `abortController.abort()`（67），但 `tools/bash.ts`/`grep` 等若不在循环/分块处轮询 `abortSignal.aborted`，则要等工具自然结束。可作为独立 follow-up：审计 `src/tools/bash.ts`、`src/tools/grep.ts` 的工具循环 abort 检查频率，让中断更快收敛（属性能优化，不在本章阻塞）。

### 8.4 关键风险与回滚

- **重复回显**：Step 2 的 `revisionEchoed` 门缺失会导致同一增量出现两次（submit 一次 + 下一轮一次）。单测覆盖（见 8.5）。
- **命令型增量**：命令在运行中本就被忽略（499-504），Step 1 的回显只在 `!parsed.isCommand` 后执行，避免把 `/xxx` 当补充回显。
- **历史 vs 增量**：普通模式下一轮 `text` 改为累积增量，模型仍拥有完整历史，方向调整基于"原目标(历史)+增量(最新)"，符合 G3；若担心"替换感"，可在累积文本前加前缀 `（补充指令，请结合上文调整方向）`——作为可选项，默认不加以免噪声。
- **回滚**：仅回滚 agent-runtime-controller.ts（submit/run-loop 两段）、turn-controller.ts（requestRevision）两处；不影响 `addConstraint`、权限（§7）、模型（§1-6）等其它功能。

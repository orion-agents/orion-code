## 1. 为什么是这件事（基线事实，2026-09-21 采）

| 作业 | 结果 |

| **Web E2E full suite three consecutive runs** | 红（45m） |

| Aggregate release / Web E2E receipt ×2 | skipping（长期未产出） |

全量套件（21 个 spec，`workers: 1`，约 30 分钟）：**29 failed / 55 passed**。

根因分四类，其中只有一类是产品缺陷：

### 1.1 真产品缺陷：`aria-orientation` 放在 `<nav>` 上（1 行代码，连坐多处断言）

`web/src/layout/WorkPanelDock.tsx:247`：

```tsx
<nav
  className={overlay ? 'work-panel-rail work-panel-rail-overlay' : 'work-panel-rail'}
  aria-label="工作面板快捷入口"
  aria-orientation={overlay ? 'horizontal' : 'vertical'}   // ← axe critical
>
```

axe 规则 `aria-allowed-attr`（impact **critical**，tags `cat.aria / wcag2a / wcag412`）判定
`role=navigation` 不允许 `aria-orientation`。这是 v0.3.11 把停靠栏从 tab 条改成 rail 时引入的。

连带失败面：
- `scripts/smoke/web-workbench-browser.ts` 的「零 critical/serious 违规」断言 —— 这就是 **`Node 22 verification` 的失败点**（日志停在 `web-workbench-browser.ts:74`，期望 `[]` 实得 `aria-allowed-attr`）。
- 各 spec 里的 axe 断言：`web-v032-accessibility`、`web-v031-foundation-accessibility`（WEB31-P0-12）、`web-security-accessibility`（E2E-P0-08）、`web-v036-keyboard-and-shell`（WEB36-P1-03）。

**反向约束**：`aria-orientation` 在 `web/src/layout/PanelResizeHandle.tsx:197` 是**合法**的（`role=separator`）。全库仅此两处，不要一起改。

**修复的连带面（重要）**：`tests/e2e/web-rail-panel.spec.ts:24` 当前断言 `rail` 有
`aria-orientation="vertical"`。删掉属性后这条断言必须改成**用几何判定垂直**（rail 的高度 > 宽度、
按钮纵向堆叠），而不是换一个 ARIA 属性——否则就是把违规从产品挪进测试。这不是「放宽断言」，是断言从错误契约迁移到真实契约，必须在 PR 里写明。

### 1.2 断言漂移：`role="tab"` → rail 按钮（30 处）

`getByRole('tab')` 分布：

| spec | 处数 |
| --- | --- |
| `web-v031-terminal.spec.ts` | 15 |
| `web-v031-foundation-accessibility.spec.ts` | 7 |
| `web-v033-theme.spec.ts` | 4 |
| `web-security-accessibility.spec.ts` | 2 |
| `web-v033-shell-regression.spec.ts` | 1 |
| `web-v031-context-resources.spec.ts` | 1 |

v0.3.11 把停靠栏的 `role="tab"` 条换成 rail 按钮（选中态 `aria-current="page"` 而非
`aria-selected`），并把面板开关移出 `<main>`。

**必须逐处判定，不能批量替换**：`web/src` 里仍有**合法**的 `role="tab"` ——
`components/Inspector.tsx:66`、`components/terminal/TerminalPanel.tsx:426`、
`components/git/DiffViewer.tsx:72`。终端的 shell tab 与 Diff 的 hunk tab 是货真价实的 tab，
它们的失败另有原因，归 1.3。

rail 的稳定标记：`#work-panel nav.work-panel-rail` 内的
`[data-work-panel-id="<id>"]`，id ∈ `agent｜review｜terminal｜files｜git`（`PANEL_META`，共 5 个按钮）；
详情面板是 `#work-panel-detail`。

## 2. 目标与非目标

### 目标（可验收）

1. `Web E2E full suite three consecutive runs` **连续三轮全绿**。验收标准本身就是「连跑 3 轮」，所以 flake 不能只是被掩盖，必须根除或被显式登记。
2. `Node 22 / 24 / 26 verification` 绿（含 `test:web-browser`）。
3. `TypeScript type-check` 绿。
4. `Dependency security audit` 绿。
5. 所有 axe 断言在修复后**仍断言零违规**：不允许通过 ignore / 放宽规则 / 去掉断言来变绿。
6. 每个修复都能回答「这是产品缺陷还是断言过期」，证据落盘。
7. **S0/S3 判定为产品缺陷的项，修产品代码到功能行为正确**（不是把断言改成迁就现状）。范围含 terminal / 布局等被判定为真实缺陷的产品代码。

### 非目标

- 不做 Git 工作栏新功能（0.3.17 S5/S6 不在本轮）。
- 不重构 CI 作业结构，只修收据管道。
- 不为通过而删除测试、放宽断言、或加无理由 skip。确实无法在环境内验证的用例，走 §7.2 的显式 skip + 登记流程。
- **不把「修到功能正确」扩张成重构**：只修被判定为缺陷的具体行为，不在本轮顺手动结构。

## 3. 阶段拆分

### S0 — 只读分类（先分类，再动手）

产出 `docs/plan/evidence/v0.3.20-e2e/baseline.md`：29 个失败逐个归入「产品缺陷 / 断言漂移 / 环境限制」，每个都附判定证据（失败首行 + 根因 `文件:行`）。

方法：`npx playwright test tests/e2e/<spec>.spec.ts --reporter=line` **定向单 spec 复现**，不要靠 30 分钟整跑试错。

分类口径：
- **产品缺陷**：能指出产品源码的具体位置，行为不满足已声明的契约。
- **断言漂移**：断言引用的标记 / 文案 / 交互已按新契约改名，且新契约是有意的。
- **环境限制**：在 CI 上也不成立，且有替代验证手段。

**风险（v0.3.19 的教训）**：上一轮的经验是「断言欠账」下面藏着 3 个真 bug。所以分类必须带证据，不能靠「看起来像」。

### S1 — 修产品缺陷（先 a11y）

P0：`WorkPanelDock.tsx:247`。两个处置选项：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **(a) 推荐** | 删掉 `aria-orientation`（`role=navigation` 靠 `aria-label` + DOM 顺序已表达方向） | 需同步改 `web-rail-panel.spec.ts:24` 为几何判定 |
| (b) | 保留方向语义 → 把 rail 改成 `role="toolbar"` + `aria-orientation` | 改变可访问性树与既有断言，回归面更大；`toolbar` 要求方向键漫游，涉及键盘行为 |

选 (a)。完成后做一次**全库 ARIA 合法性扫描**（`grep -rn "aria-" web/src/` 对照 axe 规则），确认无同类问题再进 S2。

### S2 — 修断言漂移（30 处，逐处判定）

三类处置：
1. **目标是停靠栏 rail** → 改用 `[data-work-panel-id="<id>"][aria-current="page"]`；开关用 `ui.inspectorButton`（已加 `#work-panel` 兜底）。
2. **目标是终端 tab / hunk tab**（`role="tab"` 仍合法）→ 断言保持不变，失败另有原因，退回 S3 判定。
3. **目标是旧文案**（如 `实时连接正常`）→ 改为稳定契约标记，不要改回文案。

证据：每个 spec 修完定向跑绿，记录前后对照。

### S3 — 长耗时 / 超时组判定与缺陷修复

清单（各 2–5 分钟，占整跑时长的大头）：

| spec | 用例 | 耗时 |
| --- | --- | --- |
| `web-v031-terminal.spec.ts` | WEB31-P0-08 / 09 / 10 | 2m / 3m / 3m |
| `web-v032-layout.spec.ts` | WEB32-P0-01 / 02 / 03 | 2m / 17s / 17s |
| `web-v033-shell-regression.spec.ts` | WEB33-P0-23 / 24 | 各 2m |
| `web-v0314-files-editor.spec.ts` | WEB33-P0-34 | 5m |
| `web-v0312-conversation.spec.ts` | WEB33-P0-15 | — |

判定三分：
- **产品缺陷 → 修产品代码**（本轮范围，见 §7.1）。验收是该行为在 CI 上按契约通过，而不是断言改成迁就现状。
- **断言漂移 → 改断言**（同 S2 口径）。
- **环境限制 → 显式 skip + 登记**（见 §7.2）：带 reason 的 `test.skip`，并在 `baseline.md` 写明「为什么不成立」与「替代证据是什么」。

**前置声明的沙箱限制**：本机 `tests/web-server.test.ts` 的真实 PTY 用例在沙箱必然失败且会留下挂起子进程，因此 terminal 的三个用例大概率**只能在 CI 日志上判定**。这类情况要在证据里写明「判定依据 = CI 日志，非本机复现」，不能含糊成「已确认」。

**代价声明**：本阶段是本轮唯一可能改到非测试产品代码的阶段，也是唯一可能"发现新缺陷→扩大范围"的阶段。每个产品缺陷修复都要单独 commit 并说明「哪条断言因此从红转绿」，避免把它混进测试改动里。

### S4 — 静态类型 + 依赖 + 收据管道

- 12 处 type-check：box 可能为 null 的，先 `expect(box).not.toBeNull()` 再取（既有 spec 已有此写法）；`WorkspaceFixture.displayName` 改成实际字段名。
- `js-yaml` 升级：先 `npm ls js-yaml` 定位宿主（多半是传递依赖），再决定 `overrides` 还是升级宿主；升级后跑受影响的解析类套件。
- 收据管道：让测试失败时也产出 `.release/full-tests.json`，证据留得住，`if-no-files-found: error` 不再二次报错。

### S5 — 收尾与验收

- CI 上 `Web E2E full suite three consecutive runs` 三轮全绿。
- 本地 `release:check`、`format:check`、`lint`、`tsc --noEmit`、`tsc -p web/tsconfig.json`、`typecheck:e2e` 全绿。
- CHANGELOG 0.3.20 段落从 candidate 翻到真实交付状态（受门禁约束：**分支必须叫 `codex/v0.3.20` 且 package = 0.3.20**，否则 `Version consistency` 直接红；无 tag 时不得写 published）。

## 5. 风险与约束

1. **迭代成本**：整跑 30 分钟、连跑 3 轮 1.5 小时 → S0 必须定向单 spec，不要整跑试错。
2. **沙箱**：PTY 挂起子进程、每轮删除配额、无法 `launchctl bootstrap` → 部分用例只能以 CI 日志为判据。
3. **「环境限制」最容易被滥用**：每次此类判定都要写明「为什么不成立」与「替代证据是什么」。
4. **依赖升级的连带面**：js-yaml 可能被多处传递依赖，升级后需跑受影响的解析类套件。
5. **分支名即期望版本**：分支必须是 `codex/v0.3.20`。

## 7. 决策记录（2026-09-21 用户确认）

### 7.1 范围：连产品缺陷一并修到功能正确 ✅

本轮不只让套件变绿：S0/S3 判定为**产品缺陷**的项，修产品代码到功能行为正确。含义与边界：

- 范围含 terminal、布局等被判定为真实缺陷的产品代码。
- 不含 Git 工作栏新功能（S5/S6 仍不做）。
- **不等于放开重构**：只修被判定为缺陷的具体行为。
- 因此验收口径 #1（套件全绿）不足以单独证明质量——每个产品缺陷修复都要额外说明「原先错在哪、现在按什么契约对」，而不只是「断言过了」。

### 7.2 无法在环境内验证的用例：显式 skip + 登记理由 ✅

判定为「本机与 CI 都做不到」的用例走 `test.skip` 并在 `baseline.md` 登记：

- 必须写 reason（指向证据小节），不接受裸 skip。
- 必须写明替代证据（例如「判定依据 = CI 日志 job 链接 + 失败首行」）。
- skip 是**待办**不是**结案**：在 CHANGELOG 与证据里列为已知缺口，下一轮可重新评估。

理由：长期红会让门禁失去表达力；带理由的 skip 至少让门禁重新说明「其余部分是可信的」。

## 1. #269 (Bug) — Git conflict view fails after editing a conflicted file before staging

**Reported symptom**: after a normal merge conflict, editing the conflicted file before
staging makes `GET /api/v1/git/conflict` fail with
`git_command_failed: fatal: git cat-file: could not get object info`, instead of showing
base / ours / theirs alongside the current working file.

**Source-confirmed root cause** — `src/web/git-version-service.ts`, `conflict()`:
the working-tree version is read through

```
git hash-object --path=<path> -- <path>   (no -w)
```

and the resulting OID is then fed to `git cat-file -s` / `git cat-file blob`
(`readVersion`). `hash-object` without `-w` only *computes* an OID — it does not write
the object. For an unmodified checkout the computed OID happens to equal the known index
blob, so `cat-file` succeeds by coincidence. The moment the user edits the file, the
content no longer exists in the object database and `cat-file` fails, failing the whole
conflict response. The index stages themselves (`git ls-files -u`) are read correctly.

**Fix**: read the working-tree version from the filesystem, not from the object
database. `GitVersionReaderOptions` gains an optional
`readWorktreeFile(relativePath) => Promise<Buffer | null>`; `conflict()` uses it for the
`worktree` label (exists = buffer returned; the same MAX_VERSION_BYTES truncation,
binary probe and LFS-pointer probe as `readVersion`, refactored into a shared
byte-decoding tail). The wired implementation in
`GitReadModelServiceV1.versionReader()` resolves the repository root via
`requireRepositoryRoot()` and enforces real-path containment (the file cannot escape the
repository) before reading; sensitive-path and relative-path guards already run earlier
in `conflict()`. The stage reads (`ls-files -u` OIDs) are untouched — those blobs exist.
The `hash-object` call is removed from the read path entirely, keeping reads read-only.

**Tests** (`tests/web-git-versions.test.ts`): build a real merge conflict; read the
conflict (passes today); edit the working file; read again and assert every version
still resolves with the edited worktree content (throws today). Also cover: missing
worktree file (delete shape), binary worktree edit, and root-escape rejection.

## 2. #270 (Bug) — File history ignores the requested revision and returns HEAD history

**Reported symptom**: `GET /api/v1/git/file-history?path=...&rev=...` validates `rev`
but always walks the checked-out `HEAD`.

**Source-confirmed root cause** — `src/web/git-history-service.ts`, `fileHistory()`:
`const target = rev ?? 'HEAD'` is used only for the `git rev-parse --verify` existence
check; the subsequent `git log --follow -- <path>` never includes the revision, so the
query always walks HEAD.

**Fix**: pass the validated target to the log command:
`git log --max-count=<n> --format=<fmt> --follow <target> -- <path>` (positional rev
before the `--` separator). No protocol change — the endpoint already accepts `rev`.

**Tests** (`tests/web-git-versions.test.ts`, alongside the existing file-history
coverage): two branches with divergent histories for one path; `rev=<branch>` returns
that branch's commits (returns HEAD's today); an unknown rev still yields the empty
page (unchanged behavior); the default HEAD query is unchanged.

## 3. #271 (Bug) — Model switching skips compact preflight when the output reserve shrinks the input budget

**Reported symptom**: switching to a profile with the same or larger raw context window
but a smaller effective input budget (larger `maxOutputTokens` reserve) reports
`compactRequired=false` / `compactPreflight=not_required` and persists the target even
though the unchanged history already exceeds the target's safe input budget. Concretely:
100,000-token window, source reserve 4,000 (budget ≈ 94,000), target reserve 48,000
(budget ≈ 50,000), history ≈ 62,680 tokens — fits the source, exceeds the target.

**Source-confirmed root cause** — `src/runtime/model-coordinator.ts`,
`commitSwitch()`: the preflight trigger is
`target.resolvedContextWindow < prev.resolvedContextWindow` — a comparison of *raw*
context windows. The safe input budget already exists right below it
(`resolveProfileSafeInputBudget(profile)` = window − reserved output (capped at 50% of
the window) − 2% safety margin), but it is only consulted after the raw-window gate
lets a switch through. The deferred path in `src/runtime/session-composer-control.ts`
(`runtimeIdle() === false`) repeats the same raw-window comparison
(`profile.resolvedContextWindow < this.project(session, true).model.contextWindow`).

**Fix**: gate the preflight on the *effective input budgets*:
`resolveProfileSafeInputBudget(target) < resolveProfileSafeInputBudget(prev)` in
`commitSwitch()`. In the deferred path, resolve the current session's profile through
the registry and compare the same budgets. The preflight body itself (budget, target
tokens at 65%, receipt validation) is unchanged.

**Tests** (`tests/model-coordinator.test.ts`, `tests/session-composer-control.test.ts`):
the issue's exact scenario — same window, larger output reserve, history between the
two budgets → `compactRequired=true`, preflight invoked, receipt honored; a genuinely
larger target budget still skips the preflight; the deferred path mirrors both. Existing
smaller-window cases keep passing.

## 4. #272 (Feature) — Keep left project navigation order stable when activating sessions

**Reported symptom**: activating a session in another project promotes that project to
the top of the unpinned ("RECENT") group in the left navigation, reshuffling the tree on
every switch and moving expanded session groups.

**Source-confirmed root cause** — two layers sort unpinned projects by
`lastActivatedAt` DESC:
- `src/services/workspace-registry.ts` `compareEntries()` (also used by
  `writeDocument`, so the persisted array order itself is recency-ordered), and
- `web/src/components/projects/ProjectNavigator.tsx` `compareProjects()`.

Every session/project activation stamps `lastActivatedAt`, so normal navigation
continuously rearranges the tree. There is no durable registration-order field today.

**Fix** (stable default order, per the issue's acceptance criteria):
- `WorkspaceRegistryEntryV1` gains a persisted `registeredAt` (set on first
  registration, preserved on every update; documents without it are backfilled from
  `lastActivatedAt` on parse and persisted on the next write — deterministic
  migration-on-next-write).
- `compareEntries()`: pinned first (unchanged), then `registeredAt` ASC (registration
  order), then label/id tiebreaks. `lastActivatedAt` no longer participates in ordering.
- Protocol `WebWorkspaceSummaryV1` gains an additive optional `registeredAt`, populated
  by `workbench-controller.listWorkspaces()`.
- `ProjectNavigator.compareProjects()`: pinned first (unchanged); unpinned sorted by
  `registeredAt` ASC when present, falling back to the previous recency order for
  summaries without the field (older Host compatibility). Activation still updates the
  selected row, session data and the active marker — it just no longer reorders groups.
  Scroll anchoring follows for free from the stable order.

The explicit recent-activity sort toggle suggested by the issue is recorded as a
follow-up (non-goal for this cycle): the acceptance criteria are met by the stable
default, and a sort preference adds UI surface that deserves its own review.

**Tests** (`tests/workspace-registry.test.ts` + ProjectNavigator render assertions):
registration order is persisted and survives activation churn; activation stamps
`lastActivatedAt` but does not reorder; documents without `registeredAt` migrate
deterministically; the UI comparator keeps pinned groups first and orders unpinned
groups by `registeredAt` with a legacy fallback.

web), build, `release:check`. CI: critical journey ×3, three-consecutive-runs 3×105,

## Risks

1. **#269 reads the worktree from disk** on a previously git-only read path — mitigated
   by real-path containment inside the repository root and the existing
   sensitive/relative-path guards; no object-store writes.
2. **#271 behavior change**: switches that previously skipped preflight now run it —
   the deterministic fallback (no bridge wired) reports `unavailable` instead of a false
   `not_required`; that is the honest state, and the bridge path compacts when needed.
3. **#272 reorders existing users' navigation** (recency → registration order) —
   intentional per the issue; pinned users see no change; the migration backfill keeps
   existing relative order deterministic.

## Non-goals

No Thread/Turn/Step protocol changes beyond the additive `WebWorkspaceSummaryV1
.registeredAt`; no ToolGateway permission changes; no explicit sort-preference UI
(follow-up); no new agent capabilities.

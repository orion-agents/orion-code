## 1. 已知事实（运行时证据，非推测）

1. v0.3.52 新增的到达摘要在 main run 41930947053 的失败里给出：

   **从未到达**。可排除「发出了但载荷不含关键字」分支。

   `command.contextReceipt.manifestDigest` 为 64 hex、`referenceCount === 5`

3. 失败只出现在三连跑的**后段 run**（v0.3.52 观察：run-1 GO / run-2 或 run-3 红），
   run-1 从未失败；同一 job 内 119 个场景全跑，`WEB32-P0-08` 是第 58 个。

## 3. 本轮任务分解

### S1 测试插桩：让静默丢弃自我声明 — `tests/e2e/web-v032-context-plan-queue-recovery.spec.ts`

- WEB32-P0-08 在 `contextReceipt` 断言之后、等待 provider 请求之前，检查
  `/api/v1/commands` 响应体的 `result` 字段：host 对 submit 的处置真实写在这里
  （`src/web/workbench-controller.ts:2119-2125` `result: admission.accepted.type`；
  排队分支为 `:2107-2116` 的 `session_turn_queued`；静默丢弃分支为
  `agent-runtime-controller.ts:703-704` 的 `command_ignored`）。
- 断言形式：`expect(['started', 'session_turn_queued']).toContain(command.result)`。
  只放行这两种「turn 会被执行」的处置，命中 `command_ignored` 等静默丢弃时**立刻**
  以 `result`/`detail` 具名失败，而不是再空等 45s。
- 之所以不把 `session_turn_queued` 也判失败：合法排队后请求仍会发出，判失败会引入
  新的假红；本轮目标是「不掩盖 + 具名」，不是收紧语义。

### S2 版本与记录

- CHANGELOG：0.3.52 `candidate` → `published`（PR #312、merge `a054c44`、tag
  `v0.3.52`、npm `2026-11-04T23:09:25.161Z`、GitHub Release 链接），并追加**范围纠正**
  （v0.3.52 的条款 B 修复只覆盖 `WEB32-P0-09`，`WEB32-P0-08` 仍在）。
- 新增 0.3.53 `candidate` 条目，条目首句即写明 **release withheld**：不打 tag、
  不 publish、不建 Release，下一轮修好红灯后**直接发布 0.3.53**（不跳版）。
- **为何仍要 bump**：release gate 会把 `package.json` 版本钉到
  `codex/vX.Y.Z` 分支名（`scripts/release/release-check.js:234-262`），且只做
  「发布后状态翻转」会被判 `Release ref` / `README release state` / `Version
consistency` 三项红（本地实测见 §5）。这正是项目记忆里记过的
  「release-gate 逼占版本号」机制。因此六处 bump 到 0.3.53（`package.json`、
  `npm-shrinkwrap.json` 顶层 + `packages[""]`、`CHANGELOG.md`、`README.md`、
  `README.zh-CN.md`）+ `tests/coding-task-eval.test.ts` pin，**但发布动作整体扣住**。
  0.3.53 处于交付状态图例里的 `Merged`（已合入默认分支、尚不可从 npm 安装）状态，
  不是伪造 `Published`。
- README / README.zh-CN：首部摘要 + install pin 至 0.3.53，摘要首句声明
  「release withheld by clause B」。

### S3 证据文件 — `docs/plan/evidence/v0.3.53/investigation-and-audit.md`

- 0.3.50–0.3.52 三版交付状态审计（tag peel ↔ main 合并提交、npm 存在性、
  `dist-tags.latest`）。
- 本轮运行时事实、静态排查表（含被证伪的假设与判据行号）、以及「为何本轮不发布」
  的判定依据。

### S4 聚合收据可诊断化（2026-11-05 续轮新增）— `scripts/e2e/assemble-web-e2e-receipt.ts` + `src/runtime/release-receipts.ts`

- **动机**：`browser_evidence_clean` 只报 `primaryN=GO …` 加一个布尔
  `cleanEvidence`，不说是**哪个场景的哪个计数器**脏；计数器明细只在每次 run 的
  per-scenario manifest 里，而 `web-e2e-primary` artifact 有 184 MB、本机到 GitHub
  约 20 KB/s（≈2.5 小时）实际取不到。v0.3.49 首轮（primary1）与本轮 PR #313 首轮
  （primary2）都是「6 个 run 全 GO、仅一个 run 证据不干净」→ NO_GO，属会反复掐住
  每次发布的第三类红灯，却无法从 CI 输出定位。
- **改动**：装配脚本按场景计算 `uncleanEvidence: string[]`
  （`scenarioId/status/计数器名=值`，最多 6 条），`cleanEvidence` 由其是否为空推出
  （判定式与原先等价）；`WebE2ERunEvidenceV1` 增加可选字段 `uncleanEvidence?`；
  失败时把不干净 run 的摘要追加进 `browser_evidence_clean` 的 `detail`（截断 500 字符）。
- **判定强度不变**：什么算脏、哪些检查会 NO_GO 一概未改，只是让红灯可定位。

## 5. 验收标准

1. `npm run build` 绿；`npx tsc --noEmit` 0 错；改动文件 `prettier --check` 干净。
2. `tests/coding-task-eval.test.ts` 5/5 绿（未 bump 版本，pin 仍为 0.3.52 应仍通过）。
3. `npm run release:check`：六处 bump 后 `Version consistency (package 0.3.53)`、
   `CHANGELOG.md entry`、`README release state`、`Release ref` 应通过；仍会因
   本机已知 better-sqlite3 ABI 与 PTY 环境家族在 `Jest suite` 项失败（以 CI 同名
   job 为准）。**实测对照**：在只做状态翻转、不 bump 的情况下，同一门禁报
   `Version consistency` ❌、`README release state` ❌、`Release ref (refs/tags/v0.3.52)`
   ❌（「tagged CHANGELOG is stale …current-tree CHANGELOG carries the post-publish
   evidence」），据此确认必须按门禁的分支↔版本钉定规则 bump。
4. CI：`Web E2E critical journey ×3`、Node 矩阵、audit、release gate 等作业结论
   如实记录；`Web E2E full suite` 若再次红，失败信息应具名为 host 的 submit 处置或
   继续给出到达摘要，两者都算本轮目标达成（机制可观测）。CI 全绿则允许合入
   （合入 ≠ 发布）；若因残留 flake 无法全绿，则按「不得强行合并」停止并报告。
5. **不产生 tag、不发布 npm、不建 GitHub Release**（条款 B）。
6. 汇报中明确写出：目标版本 v0.3.53 与实际推进（未发布）不一致，及原因。

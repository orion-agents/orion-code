# Orion Code v0.1.8 Plan

> 状态：Implementation complete; release candidate verification in progress
> 基线：`v0.1.8` / `52b6fc23c6ae`
> 规划日期：2026-08-14
> 版本定位：v0.1.x 稳定性、仓库治理与问题收敛版本

## 1. 版本目标

v0.1.8 聚焦两条主线：

1. 整理仓库目录与 npm 发布内容，删除已经被替代、没有运行时引用或不应进入发布包的内容。
2. 对 GitHub 当前 open issues 做逐项验收；修复 bug，并只开发具备明确用户价值和验收指标的 feature 建议。

本版本不是一次大规模架构迁移。所有清理必须可证明、可回滚，并与 bug 修复分批交付，避免目录移动掩盖行为变化。

## 3. 范围与非目标

### 3.1 本版本范围

- npm 发布白名单与包体积治理。
- 无引用目录、资产和过期手工脚本的安全删除。
- UI/runtime 目录边界文档化与小步收敛。
- 33 个 open issues 的逐项分类、修复、验收或产品决策。
- 对当前 feature 建议做问题定义、兼容性与验收指标补全，并开发被纳入 v0.1.8 的小范围优化。
- Node 20、22、24 的构建、安装、CLI 和 native dependency 验证。

### 3.2 非目标

- 不提前实现 v0.2.0 的 Verified Project Agent：Project Goal、Task Graph、Isolated Agents、Mission Control、Evidence Gate、Stable Exec 仍由 v0.2.0 计划管理。
- 不在 v0.1.8 删除仍可通过 `--ui ink` 使用的 `src/ink-ui/`。
- 不一次性移动 `src/framework/` 或改变现有公共导出；package 目前没有严格 `exports` 边界，激进移动可能破坏 deep imports。
- 不为了“目录整齐”进行无行为收益的大规模 rename。
- 不在计划执行过程中自动发布 npm、创建 tag 或修改 dist-tag；release promotion 需要单独确认。

目录迁移规则：

- `src/ui/` 中 renderer-neutral 的逻辑迁入 `tui-core/` 或 `runtime/`，TUI 专用逻辑迁入 `tui-ui/`；只有目录为空后才删除。

- `src/ink/` 与 `src/ink-ui/` 分开处理：前者是未引用旧 helper，后者是仍受支持的弃用兼容 renderer。
- `tests/` 与 `scripts/` 只对本版本触及的文件逐步分层，避免数百文件的机械移动制造 merge 噪声。
- 历史 release evidence 迁入 archive 并保留索引，不删除不可再生成的发布凭据。

## 6. Workstream B：open issues 修复与 feature 优化

### B0. Issue 处理契约

每个 issue 必须按以下链路处理：

1. 在当前 `v0.1.8` HEAD 上复现，或记录为何无法复现。
2. 将 issue acceptance criteria 转为 focused regression test。
3. 审查候选修复是否覆盖错误路径、并发路径、跨进程路径和 renderer parity。
4. 运行 focused tests、相关回归、build、lint、full suite。
5. 在 issue 留下 commit/PR、测试命令和结果，再关闭或重新分类。

禁止仅凭 `rg` 命中、代码 diff 或“测试通过”就批量关闭 issue。

### B2. 尚未完成的 issue

#### `#203`：数值型工具参数必须在执行前验证（P0 bug）

当前 `exec_command.timeout`、`exec_command.maxOutputBytes` 和 `list_files.maxDepth` 仍可能接受字符串、负数、小数、`NaN`、`Infinity` 或极大值。

实施：

- 建立共享 finite safe integer validator，并在 schema/coercion 后、权限与执行前调用。
- 为每个参数定义并文档化边界：
  - `timeout`: `1..600000` ms。
  - `maxOutputBytes`: `1024..10485760` bytes。
  - `maxDepth`: `0..8`。
- 错误必须包含参数名、收到的安全表示和允许范围；禁止进入 scheduler 或 shell。
- 添加 table-driven unit tests、tool integration tests 与恶意 JSON 输入回归。

#### `#204`：Agent loop budget 停止提示不可操作（P1 UX/feature）

源码已有 continuation hint，但实际 TUI 中用户只看到冷冰冰的停止文本或提示被折叠，因此不能把现状视为已解决。

实施：

- 引入 renderer-neutral 的 `budget_stop` 结构化 view model。
- 展示停止原因、当前/最大 turns 与 tokens、最后完成位置，以及明确的下一步：`继续`、`/loop-stats`、调整预算。
- TUI 使用固定可见的操作提示；terminal/print/JSON 保持信息等价。
- 中文和英文都使用面向用户的文案；collapsed details 不能隐藏唯一的恢复动作。
- 增加窄终端、NO_COLOR、长输出和 continuation 的 PTY 回归。

### B3. 需要集成或产品决策的 issue

#### `#179`：renderer scope

- 不重复开发；审查现有 [PR #201](https://github.com/orion-agents/orion-code/pull/201)。
- 验证命令执行前 scope enforcement、TUI/terminal/print parity 和兼容性。
- 通过后合入并关闭 issue；不通过则在原 PR 补修，不另开竞争实现。

#### `#175`：AUTO 模式网络权限语义

该建议与当前已采用的产品契约冲突：AUTO 是非交互、完整代理执行模式，仍受 hard deny 与项目安全边界约束，但不逐次询问权限。

v0.1.8 不静默恢复确认弹窗。先完成产品决策：

- 保持 AUTO 非交互执行。
- 在状态栏和 tool event 中明确显示网络 capability 与命中策略。
- 支持项目级显式 deny/policy，但不把它伪装成 AUTO 的逐次确认。
- 同步用户文档和 contract tests 后，决定关闭 `#175` 为 product-contract mismatch，或拆出独立的 capability-policy feature。

#### `#161`：npm stable promotion

这是 release operation，不是普通代码 bug。

- 重新查询 npm dist-tags；规划时快照为 `latest=0.1.4`、`next=0.1.7`。
- 只在 exact tag、exact tarball、Node matrix、release ledger 与 GitHub Release 全部匹配时，提交 stable promotion 建议。
- 修改 `latest`、创建 `v0.1.8` tag 和 `npm publish` 均需发布授权，不能作为普通实现步骤自动执行。

### B4. Feature 建议进入 v0.1.8 的准入标准

当前没有 open issue 使用 `enhancement` label。v0.1.8 不凭空扩展功能，建议先补齐 issue 模板：

- 用户旅程与真实痛点。
- 当前行为和可复现证据。
- 建议行为、兼容性和迁移影响。
- 可量化 acceptance criteria。
- 安全/权限影响、测试策略和 non-goals。

本版本允许的优化只有：

1. `#204` 的 budget-stop 恢复体验。
2. npm package hygiene 与可观测的包预算。
3. `#175` 决策后可能产生的 network capability 可见性，但不改变 AUTO 已确定的非交互契约。
4. 为已修 bug 必需的小范围性能、错误信息和 renderer parity 改进。

超出这些边界的产品 feature 进入 v0.1.9 或 v0.2.0 backlog。

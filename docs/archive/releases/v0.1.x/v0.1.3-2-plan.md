# Orion Code v0.1.3-2 计划（审查修正版）

> 审查日期：2026-08-04
> 计划状态：**GO WITH CONDITIONS**——仅对下方收敛后的 v0.1.x 范围进入实现；原始市场能力大包不得直接开工。
> 目标：在项目级 Goal 的约束下，关闭当前版本的安全、Goal 数据完整性、运行时交互和发布可追溯缺口。
> 权威顺序：`docs/goals/orion-code-项目级目标.md` > 当前代码与测试 > `docs/archive/releases/v0.1.x/v0.1.3-plan.md` > 市场对标笔记。

## 0. 审查结论

原计划有价值，但不能按原样实施。它把三类内容混在一起：已经从代码确认的问题、工作树候选改动，以及未经来源证明的竞品/市场判断；同时把项目级 Goal 明确放到 v0.2/v0.3 的能力提前塞进 v0.1.3-2。

本次修正结论：

- 保留并提高优先级：权限模式绕过、SSRF 重定向、API key 前缀泄露、无界响应读取、Goal sidecar 覆盖风险、运行中增量输入候选状态。
- 保留但收窄：沙箱、allowlist、Git 工具、发布追踪；先完成契约、POC 和只读/本地安全路径，不自动扩大到远程发布。
- 已有实现不再重复规划：项目指令文件、model registry 列表/别名/context、provider fallback 主链路。
- 延后到 v0.2 或单独技术书：可写/后台子代理、多 Goal/跨 Session/unattended、远程 MCP/OAuth/Tool Search、自定义工具 API、私有化部署和 Ink 物理删除。
- 所有“完成”必须绑定到当前 source、测试、真实 PTY、tarball 或外部状态证据；局部测试、未提交代码和临时 `dist/` 都不是发布证据。

## 2. 与项目级 Goal 的对齐

本计划服务于 Goal 的 G1/G2/G3/G4/G6：目标状态可靠、安全可控、TUI/terminal/Print 共享 runtime、终端原生体验和可恢复存储。v0.1.x 的主线是可靠性与语义收敛，不是把所有竞品能力一次性补齐。

### 2.1 本版本目标

- 所有 permission mode 对 `ask`、`deny`、read-only、state-write、destructive、external publish 的行为有一致且可测试的契约。
- SSRF、响应体大小、凭据展示和 Goal sidecar 写入路径 fail closed。
- 运行中增量输入候选改动在 TUI、terminal-ui、Print 和共享 runtime 上语义一致，不重复、不丢失。
- Git 首先提供受控的只读观察能力；任何 commit/stage/push 都必须有独立风险门和精确边界。
- 发布流程可追溯、可回滚，但不自动替用户执行 tag、push、PR、merge 或 npm publish。

### 2.2 明确非目标

以下内容不得作为 v0.1.3-2 的完成条件：

- 可写子代理、后台 agent、跨 Session 调度、unattended daemon、多 Goal/DAG/团队协作；这些属于 Goal 阶段 B 或后续技术书。
- 通用 HTTP/SSE MCP、OAuth、Tool Search、远程工具市场和私有化部署；先另立威胁模型与 POC。
- 用户自定义工具注册、远程动态 model catalog、插件市场和大规模命令插件化。
- 删除 Ink。项目 Goal 规定 Ink 进入迁移窗口后再删除，本版只禁止新增 Ink 产品能力。
- 以“竞品已有”“公开服务器数量”“中文准确率”等没有逐条来源的市场数字作为验收依据。

## 4. 收敛后的工作包

### P0-A：权限契约与 plan mode fail-closed

涉及：`src/framework/tool-scheduler.ts`、工具 `checkPermissions/isReadOnly/isDestructive` 契约、共享 runtime 调用方及 renderer confirmation 路径。

设计约束：

- `plan`：read-only 工具可执行；state-write、destructive、external publish 工具必须拒绝，不得因为没有 confirmation callback 而落入 `exec()`。
- `default`：safe/read-only 可自动执行；caution 需要确认；destructive/external 按现有风险策略显式确认或 deny，不能由全局 `toolConfirmation=allow` 越过风险上限。
- `acceptEdits`：只允许定义清晰的工作区编辑范围；网络、凭据、提交、推送、发布和破坏性动作仍走更高风险门。
- `auto`：只能放宽已被风险策略允许的动作；不能成为所有 `ask` 工具的隐式 allow。
- `toolConfirmation` 是配置 fallback，不替代 mode 和 tool risk metadata；缺少 metadata 的工具默认按更高风险处理。

验收：新增 scheduler matrix，至少覆盖四种 mode × safe/caution/state-write/destructive × `ask/allow/deny`，并验证 deny/error transcript 可读；TUI、terminal-ui、Print 走同一 runtime decision。

### P0-B：SSRF、响应体和凭据展示

- 将自动跟随重定向改为逐跳策略：每个 Location 都重新做 URL/地址安全检查；不能只检查初始 URL 或最终 `response.url`。
- 对无 `Content-Length` 的 chunked/流式响应设置硬字节上限，并在超限时中止读取；保留超时和 abort 行为。
- config/doctor/command/trace 输出不显示 key 前缀；统一复用 redaction，测试 `apiKey`、Authorization、query 参数和错误信息。
- 补 IPv4、IPv6、localhost、link-local、RFC1918、DNS/重定向链和安全外网用例；不把单次字符串正则检查写成完整 SSRF 防护。

### P0-C：Goal sidecar 覆盖保护

在 `src/services/goal-storage.ts` 的 sidecar lock 内：

1. `expectedRevision` 缺失时重新读取 sidecar；只有 `not_found` 或明确允许替换的 terminal Goal 才能创建新 Goal。
2. active/non-terminal、corrupt、metadata mismatch、IO error 和无法确认状态时 fail closed，原始 sidecar bytes/hash 不得改变。
3. `coordinator.load()` 失败后禁止 `/target create`/`replace` 绕过恢复门；用户必须先修复存储、明确清理或恢复，再创建新 Goal。

验收：模拟“内存有 active Goal → reload 失败 → create/replace”，断言原 sidecar 内容、Goal id、revision 和 evidence 未被覆盖；并覆盖并发 lock、corrupt sidecar、terminal replace、resume/clear 恢复路径。

### P1-A：运行中增量输入 candidate 收口

以 `docs/archive/releases/v0.1.x/v0.1.3-plan.md` §8 的工作树 candidate 为输入，不假设它已进入 HEAD：

- 多条 revision 必须累积而非覆盖；
- 即时回显与下一轮重建不能重复写入 transcript（`alreadyEchoed` 或等价契约）；
- 当前轮被 abort 时，已经产生的 assistant/tool transcript 和 accounting 不得丢失或重复计费；
- Goal 模式的 `addConstraint`、普通对话历史、pending revision 和 restart/resume 必须保持一致；
- command input 仍按“运行中命令拒绝/先中断”的既有契约处理，不把 slash command 当普通 steering 文本。

验收：controller 单测、目标生命周期测试、至少一个 TUI/terminal PTY 场景和 Print/JSON 事件 parity；如果最终设计改为真正队列注入，需另补取消边界、消息顺序和 provider 计费设计。

### P1-B：沙箱与 allowlist 先做安全 POC

现有 `SandboxOptions` 是 `none/docker/bubblewrap`，不要直接把它改写成没有能力证明的 `none/read-only/workspace-write`。POC 必须先回答：

- 当前支持的 OS/runtime 和缺失依赖如何报告；不支持时是否 fail closed；
- workspace root、cwd、symlink、临时文件、网络和子进程边界如何约束；
- shell quoting、timeout、abort 和错误输出如何保留；
- `allowedTools` 是项目级还是全局级，匹配的是工具名、参数摘要还是命令 AST；规则冲突时 deny/ask/allow 的优先级是什么。

POC 通过后再接入 `exec_command`，并将 allowlist 作为更窄的放行条件，不能绕过 destructive/external 风险门。验收包含 macOS/Linux capability matrix、越权写盘/网络 negative tests 和默认配置兼容测试。

### P1-C：Git 只读工具与安全边界

第一阶段只新增或增强：`git_diff`、`git_log`、`git_branch --list`、`git_status` 的 ahead/behind 和明确结构化输出。所有路径必须是仓库内、无 glob/pathspec 越界，输出做 secret/redaction 处理。

commit/stage/branch switch/push 分开设计：

- commit/stage 属于 state-write，必须精确文件 allowlist、index snapshot/rollback 和用户可见 preview；
- branch switch、push、PR/release 属于外部或高风险动作，不作为本版自动完成条件；
- 不新增不存在的 `/git commit` 契约；若需要 slash command，单独注册、测试和 renderer parity。

### P1-D：已存在能力的加固与小型正确性修复

- 项目指令：补充 precedence、刷新、截断、不可读文件和 prompt 注入测试；不重复实现 loader。
- Model registry：保持 `enabledProfiles`、resolved context/output 和 alias 为 `/model`/`/models` 的 source of truth；静态 catalog 只作为 legacy metadata fallback。
- Provider resilience：核验并修复 `fallback_once` 的实际 model switch、诊断和 usage；不引入远程 catalog 更新。
- 同步审查 bug report 中与本版本直接相关的无界 web read、usage 字段、web-search response id mismatch 等问题；其余 P2 记录到 backlog，不扩大本轮范围。

### P1-E：配置、迁移与兼容契约

任何新增或启用的 `sandbox`、`allowedTools`、权限或 hook 配置都必须先写清楚：字段归属（GlobalConfig 还是 ProjectConfig）、schema/version、默认值、旧配置读取、未知字段处理、降级策略、敏感字段 redaction 和回滚方式。当前 `allowedTools` 是 `ProjectConfig` 字段，不得按全局字段迁移；当前项目指令实际使用 `.orion-code/instructions.md`、`AGENTS.md` 等候选文件，不得写成未实现的 `.orion/instructions.md`。

迁移验收至少包括旧配置 fixture、升级后读取、损坏/部分字段恢复、回滚到旧版本读取，以及项目作用域隔离。OpenHorse 项目的 `--include-project-files` 迁移路径若被本版本触及，必须单独验证主命令确实调用项目文件迁移；不能只因参数已解析就宣称迁移完成。

### P2：发布可追溯与局部架构清理

- 增加人工维护的 `CHANGELOG.md` 或等价 release note，并补 v0.1.3 已确认的用户可见变更；“candidate/已合并/已发布”分开写。
- 可增加只读 `release:check`：版本/identity 一致性、`git diff --check`、build/lint/test、package dry-run、文档链接和 dirty-worktree 检查。
- `README.md`、中文 README、帮助、Banner、package/package-lock 和 release note 必须使用同一版本；当前 package 已是 `0.1.3` 时，README 仍写 `0.1.2` 就是 No-Go。
- 不让脚本默认执行 tag、push、PR、merge、npm publish；这些仍是独立授权状态。
- 架构清理只接受 import graph、测试和回滚证据；不以文件行数或历史 warning 数量作为 DoD；不在本版删除 Ink 或所有 `src/agents`。

## 5. 延后路线

### v0.2 技术书候选

可写/后台子代理、子代理 task/artifact 图、多 Goal、跨 Session 调度、unattended daemon、跨客户端一致性，以及在统一权限/预算/审计下的 provider/model 选择。

### v0.3+ 或独立技术书候选

通用 Streamable HTTP/SSE MCP、OAuth、Tool Search、远程工具市场、插件 API、私有化部署和 Desktop/IDE/App Server 客户端。每项都必须先有威胁模型、数据流、凭据生命周期、SSRF/权限边界、兼容/回滚设计和最小 POC。

## 6. 测试与验收矩阵

### 6.1 聚焦回归

- 权限：新增/更新 `tool-scheduler`、permission mode、TUI confirmation 和 renderer parity 测试。
- Web 安全：SSRF redirect、内网地址、响应体上限、redaction 和 abort 测试。
- Goal：sidecar CAS/lock/quarantine、reload failure、create/replace、resume/clear 和证据保留测试。
- 增量：`agent-runtime-controller`、`turn-controller`、Goal continuation、duplicate echo、multi-revision 和 cancellation 测试。
- Git：工具 schema、路径边界、结构化输出和只读行为测试。
- Model/instructions/fallback：已有 `status-command`、`project-instructions`、registry/provider resilience 相关套件；只补实际缺口，避免重复测试已覆盖的 registry 列表。

每项验收都要形成 `Requirement → Code → Test → Evidence` 映射，最小矩阵如下：

| Requirement            | Code boundary                                      | Test/evidence                                                   | Pass condition                              |
| ---------------------- | -------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------- |
| Permission fail-closed | scheduler + shared runtime + renderer confirmation | mode/risk matrix、TUI/terminal/Print parity                     | 无 mode 会静默执行被拒绝的变更类工具        |
| Web safety             | `web.ts` + redaction/config display                | redirect、IPv4/IPv6/private、body-limit、secret tests           | 每跳重检、超限中止、无 key 明文             |
| Goal preservation      | goal coordinator/storage                           | reload-failure/create/replace、lock、corrupt、terminal fixtures | active/non-terminal sidecar bytes/hash 不变 |
| Incremental steering   | controller + turn controller                       | multi-revision、alreadyEchoed、cancel、PTY                      | 不重复、不丢 transcript、accounting 可解释  |
| Git boundary           | git tools + path guard                             | schema、path negative、read-only renderer calls                 | 只读路径无副作用，写操作单独确认            |
| Config/migration       | config types/loaders/migration                     | old/new/corrupt/rollback fixtures                               | 旧配置可读、失败不覆盖用户数据              |
| Package identity       | package/README/bin/dist                            | version cross-check、tarball clean install                      | source/package/runtime 版本一致             |
| Release readiness      | release note/check script/CI                       | owner checklist + immutable artifact record                     | 每个外部状态独立标记，不把本地绿灯当发布    |

### 6.2 发布门

按最终 source/候选 commit 重新执行并记录结果：

```text
git diff --check
npm run build
npm run lint
npm test -- --runInBand
npm test -- --runInBand --coverage
npm pack --dry-run
```

适用时再执行：

- `scripts/*-pty-smoke.py` 的 TUI、terminal-ui、target、Goal lifecycle、Print smoke；
- 真实 macOS Terminal、用户 login-shell PATH、`orion --version`/`--help`；
- 支持 Node 20/22/24 的矩阵；
- 生成 tarball 的 clean-prefix 安装与运行，而不是直接读取工作树 `src`/临时 `dist`；
- 对兼容 fixture、迁移输入、配置路径和 package identity 做 hash/内容核对。
- 当前 CI 的 Node 20/22/24、lint、build、Jest 绿灯不覆盖 pack/install、迁移、回滚、真实 PTY 或 registry；这些缺口必须在 evidence ledger 中标为 `not_run`，不能默认为 `met`。
- Coverage 结果要记录 scope、denominator、threshold/waiver owner；不要用测试总数替代未覆盖的安全、PTY、迁移和安装场景。

### 6.3 证据状态定义

每个目标只能标记为 `met`、`partial`、`unmet` 或 `not_run`，并附具体命令/输出/文件/人工签名。以下状态必须分开：

1. 本地检查；
2. staged/commit source；
3. push；
4. CI/review；
5. merge/tag/GitHub Release；
6. npm publish；
7. 发布后 registry install。

前一状态通过不能替代后一状态。

## 7. Rollout、回滚与 Go/No-Go

推荐顺序：安全 POC → P0 安全/Goal 修复 → 聚焦回归 → 全量 gate → 真实 PTY/Terminal → tarball clean install → 文档/版本审计 → 人工 Go/No-Go → 经授权的外部发布。

回滚要求：

- permission/sandbox/allowlist：按 feature flag/config compatibility 回退，保留 deny/审计输出，不回退到静默执行；
- Goal storage：保留原 sidecar、临时文件和 deletion fence；失败时只暂停/阻塞，不删除或重写原证据；
- 增量输入：回退 controller/turn-controller candidate，不丢已有 transcript；
- Git/release：不自动撤销用户 commit 或远程历史；只恢复本轮明确拥有的 index/候选文件。

### Go 条件

- P0 安全和 Goal 覆盖 negative tests 全部通过；
- build/lint/全量测试和适用 PTY 有可追溯结果；
- 工作树所有权、最终 diff、版本 identity 和 package 内容已确认；
- 没有把 deferred 能力写入当前版本的稳定承诺；
- 发布/回滚步骤由用户或 release owner 明确授权。

### No-Go 条件

- 任一 P0 仍会静默执行、泄露凭据、绕过 SSRF 或覆盖 active Goal；
- 只有未提交工作树、局部测试或旧快照证据；
- dirty-worktree 所有权未解决；
- 真实 PTY、clean install、CI/review 或外部发布状态被混为同一“通过”；
- 需要通过自动 tag/push/publish 才能证明计划成立。

## 8. 风险与开放问题

- `toolConfirmation` 的历史默认值为 `allow`；需要在实现前确认用户可见语义和 risk metadata 上限，避免安全修复与 v0.1.3 §7 TUI 文案冲突。
- `wrapForSandbox()` 当前以 shell 字符串包裹命令，不能在没有跨平台 POC 的情况下声称提供强隔离。
- 增量输入是“abort 后重启”还是“真正队列注入”会改变 accounting、message ordering 和 provider 成本；两者不能在计划中混写。
- 通用 MCP 的 HTTP/OAuth 设计会扩大网络和密钥攻击面；web-search 的专用 HTTP 实现不能直接作为通用能力证明。
- 旧 bug report 中部分 P2 来自 v0.1.2 快照；实现前必须重新确认 HEAD、候选 diff 和当前测试，避免修复已经改变的行号或重复已完成工作。

## 9. 决策

当前版本对 **P0-A、P0-B、P0-C、P1-A、P1-B、P1-C、P1-D、P2 release-check** 可进入“逐包设计/POC”阶段；对第 2.2 节的 deferred 能力保持 **OUT OF SCOPE**。在用户确认本收敛后的范围并建立干净候选边界前，不进入跨模块大规模实现，也不执行任何外部发布动作。

本计划是技术书/验收合同，不是市场能力清单；外部市场调研只能作为选题输入，不能替代仓库证据、项目 Goal 或发布门。

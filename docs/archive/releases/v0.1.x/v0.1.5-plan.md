## 1. 版本结论

### 1.1 一句话目标

先把 v0.1.4 发布线和 `main` 之间的修复收敛为可安装、可回滚的前置基线，再将当前
“功能已多、控制面分散”的 46 个 canonical command、21 个 alias（合计 67 个可调用名称）
收敛为 TUI 优先、运行时共享、可发现、可迁移的命令系统，并实现 provider-aware 的
`/effort`：用户能看到当前模型支持什么、设置什么、请求实际发送什么，以及不支持或
fallback 时发生了什么。

ACP 是本版的**条件性 P1 薄适配层**：实现稳定 ACP v1 服务端并复用同一 runtime；只有
协议、权限、取消、恢复、包分发和真实客户端证据全部通过时才提交 ACP Registry。若此门
未关闭，ACP 从 v0.1.5 稳定发布拆出，不阻断命令/effort P0（详见第 12 章）。

### 1.2 为什么 v0.1.5 优先做这些

项目 Goal 的当前阶段要求“公开能力与真实行为一致”。现状中三条关键链路仍未闭合：

1. **可安装产物与 main 不一致。** npm 稳定 `latest` 仍是 `0.1.4`，`next` 是 `0.1.4-2`；
   `main` 又有配置目录并发、native SQLite ABI 和 session 容量锁修复没有进入这两个不可变产物。

2. **命令是主要控制面，但还不是单一协议。** Help、palette 和 completion 已读取同一注册表的
   一部分信息，业务 handler 仍大量直接写 `console.*`，runtime 再通过全局 monkey-patch 捕获 stdout；
   TUI 还有 `/permissions`、`/tool-output`、`/redraw` 私有执行分支。
3. **模型已有 `reasoning?: boolean`，但没有 effort 行为。** 当前请求统一走 OpenAI SDK 的
   `chat.completions.create()`，没有 reasoning/effort 参数、能力级别、作用域、session 恢复、fallback
   解析、reasoning token 记账或 renderer event。

因此，本版不以“再增加若干命令”为成功标准，而以以下闭环为成功标准：

```text
统一 CommandDescriptor
  → TUI palette / help / completion / docs
  → shared runtime invocation
  → structured CommandResult / AgentRuntimeEvent
  → renderer projection

Effort preference
  → model capability resolution
  → immutable logical-request snapshot
  → provider adapter payload
  → usage / fallback / error evidence
  → session resume 与 TUI/Print 可见状态
```

### 3.1 Effort API 对标

- [Codex config reference](https://developers.openai.com/codex/config-reference) 将
  `model_reasoning_effort` 建模为模型相关能力；当前文档明确其对支持的 Responses API 模型生效。
- [OpenAI model guidance](https://developers.openai.com/api/docs/guides/latest-model) 使用
  `reasoning.effort`，并强调 effort 级别取决于模型，不能把最高级别假定为所有模型都支持。
- [Anthropic effort reference](https://platform.claude.com/docs/en/build-with-claude/effort) 使用
  `output_config.effort`；effort 是 request-level 行为信号，不是硬 token 上限，改变它还可能影响 prompt cache。
- [Gemini thinking reference](https://ai.google.dev/gemini-api/docs/generate-content/thinking?hl=en)
  区分 Gemini 3 的 `thinkingLevel` 与 Gemini 2.5 的 `thinkingBudget`，并提供独立的 thinking token 用量字段。

**采用结论：** Orion 对外使用 `/effort`（`/reasoning` 为可发现 alias），内部不建立“一刀切的厂商
参数”。`auto` 只表示使用 active model/provider 的默认值，不表示尚未实现的动态智能路由。

## 4. 当前命令审计与收敛决定

### 4.1 审计规则

每个当前 command 进入以下一种状态：

- **keep**：名称、语义和风险都清晰，继续作为产品入口；
- **merge**：能力保留，但并入一个 domain command/subcommand；
- **advanced**：仍可执行，但退出默认 palette，只在搜索或 `/help --all` 中出现；
- **compat**：从 canonical registry 移除，只保留带期限的解析 shim；
- **add**：存在真实 runtime 能力或本版会闭合完整链路后再新增。

兼容 shim 不计入公开命令数量，也不进入 help、palette、completion 或生成文档；精确调用时必须发出
结构化 deprecation warning。既有 `removeIn: v0.3.0` 不在 v0.1.5 偷跑删除。

| `/doctor`                             | keep                 | read-only 默认；任何 `--fix` 后续必须 preview/confirm，不在本版暗中增加                                                            |
| `/usage`、`/loop-stats`、`/cost`      | merge/compat         | canonical `/usage [session\|lifetime\|loop]`；`/cost` 保持既有 deprecation window；删除其中提示用户使用旧 `/run`/`/chat` 的文案    |
| `/trace`、`/last-tool`、`/artifacts`  | advanced/keep        | `/artifacts` 保留 evidence 入口；trace/last-tool 进入高级诊断，TUI inspector 为首选                                                |
| `/checkpoint`                         | merge                | 新 `/rewind [list\|restore]` 使用现有 checkpoint 能力；恢复文件/会话的实际边界必须在预览中明确                                     |
| `/storage`、`/migrate`                | advanced/conditional | 不进入默认 palette；仅在 storage diagnosis 或 legacy OpenHorse 数据存在时可用；destructive 分支继续强制 preview + confirm          |
| `/agents`                             | compat/internal      | 当前只展示旧 registered agents，不等于 runtime subtask；新增 `/subagents` 后旧入口给出语义迁移提示                                 |
| `/subagents`                          | add                  | 展示当前 session 的 subtask/research timeline；没有 typed runtime 数据时不得伪造“无任务”                                           |
| `/task`、`/run`、`/chat`              | compat               | 删除旧 TaskManager/Agent 私有实现，只保留到 v0.3.0 的薄迁移 shim；普通文本继续走 shared Agent Runtime                              |

### 4.3 本版明确不新增的市场常见命令

以下能力有价值，但本版不应为追赶命令数量而加入：

- `/plan`：必须先有共享、可持久化、可更新的 typed plan artifact；不能把当前 read-only permission
  mode 包装成“计划能力”。`/mode plan` 仅表示受约束的 Agent 工作模式，不创建、读取或冒充 plan artifact。
- `/init`：生成项目指令会写仓库，需单独设计 merge/preview/ownership 合同。
- `/copy`、`/theme`、`/vim`、`/terminal-setup`：属于体验增强，排在命令语义与 effort 可靠性之后。
- `/plugins`、`/hooks`：需稳定的扩展生命周期、信任和审计协议，不在 v0.1.5 扩大安全面。
- `/background`、`/batch`、`/worktree`、定时任务：属于 v0.2 多目标/跨 Session runtime。
- `!` shell mode：直接执行 shell 会扩大绕过 tool permission/sandbox 的风险；本版拒绝。

### 4.4 v0.1.5 目标命令面与 surface budget

命令数量不是 KPI。目标是让 root command 表示稳定 domain，高频动作可以保留快捷入口，低频动作
进入 subcommand，内部/兼容入口不污染默认 palette。实现完成后的 canonical root 规划如下：

| Domain             | Canonical roots                                                                              | 默认 `/` surface                                      |
| ------------------ | -------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Goal / workflow    | `/goal`、`/diff`、`/review`、`/security`、`/test-gen`、`/research`、`/commit-plan`、`/todos` | Goal、diff、review；其余按能力/最近使用进入搜索结果   |
| Session / context  | `/session`、`/resume`、`/context`、`/compact`、`/rewind`                                     | resume、context、compact；rewind 仅在 checkpoint 可用 |
| Agent / model      | `/mode`、`/permissions`、`/model`、`/effort`                                                 | 全部 primary；各自只控制一个状态轴                    |
| Extension / tools  | `/skills`、`/skill`、`/tools`、`/mcp`                                                        | skills、mcp；动态项必须显示 source/trust              |
| Observe / maintain | `/status`、`/usage`、`/doctor`、`/artifacts`、`/config`                                      | status；其余 searchable primary/advanced              |
| Renderer / system  | `/help`、`/clear`、`/exit`、`/tool-output`                                                   | help；renderer capability 决定其余入口                |

Surface budget：

1. 空 `/` 首屏最多展示 12 个 primary root（实际可见行仍受 §5.2 的 10 行/终端高度约束），按当前状态、
   capability 与稳定优先级决定，不靠硬编码数组；输入搜索后可以发现全部 available primary。
2. `advanced` 只在精确搜索或 `/help --all` 出现；`compatibility`、`internal` 永不进入空 `/`、普通 help
   或 completion。
3. 一个 domain 只保留一个 canonical root；复数/单数、横线变体只能是带生命周期的 alias 或 subcommand，
   不能成为第二套状态/handler。
4. `/goal`、`/mode`、`/permissions`、`/model`、`/effort` 分别控制 Goal、Agent mode、tool policy、model、
   reasoning effort；任何实现都不得把这些轴重新压成一个 `mode` 字符串或布尔值。

## 5. 目标命令平台设计

### 5.1 单一 CommandDescriptor

注册表从“带 execute 函数的展示数组”升级为可生成 UI、协议、测试和文档的合同：

```ts
type CommandAudience = 'primary' | 'advanced' | 'compatibility' | 'internal';
type CommandExecution = 'runtime' | 'agent-workflow' | 'renderer-view';
type CommandBusyPolicy = 'immediate' | 'queue-next' | 'reject-busy';
type CommandSourceKind = 'builtin' | 'skill' | 'mcp-prompt' | 'plugin';

interface CommandAlias {
  name: string;
  since?: string;
  deprecatedSince?: string;
  removeIn?: string;
  replacement?: string;
}

interface CommandDescriptor {
  id: string;
  name: string;
  aliases: CommandAlias[];
  source: { kind: CommandSourceKind; id: string; trust: 'core' | 'user' | 'project' | 'remote' };
  title: string;
  description: string;
  category: CommandCategory;
  audience: CommandAudience;
  execution: CommandExecution;
  busyPolicy: CommandBusyPolicy;
  risk: CommandRisk;
  arguments: CommandArgumentSpec[];
  subcommands?: CommandSubcommandSpec[];
  defaultAction: 'show' | 'list' | 'picker' | 'execute';
  rendererCapabilities?: string[];
  requiredCapabilities?: string[];
  sideEffects: CommandSideEffect[];
  lifecycle: { since: string; deprecatedSince?: string; removeIn?: string };
  handlerId: string;
}
```

约束：

1. built-in descriptor 不允许缺失 execution、risk、audience、sideEffects 或 lifecycle。
2. alias 与 subcommand 也有独立 deprecation/usage，不再只能给整个 command 标 deprecated。
3. availability 由可序列化 capability key + runtime resolver 共同决定，不能只存在无法生成文档的闭包。
4. workflow、skill、MCP prompt 可以扩展 registry，但必须声明 source、risk、作用域和命名冲突策略。
5. destructive command 不得作为空 `/` 的默认首屏项；搜索到时显示风险和确认要求。
6. `id` 是事件、日志、ACP 和兼容映射使用的稳定机器标识；公开 name 改名不能改变 `id`。
7. 每个 command 必须声明 busy policy 和无参 default action；无参默认不得产生 destructive side effect。
8. built-in canonical name 属于保留命名空间，skill/MCP/plugin 不得 shadow；冲突项必须使用带 source 的
   qualified display name，并在 palette 显示来源与 trust。
9. availability resolver 只做本地、确定、无副作用检查；不得为了渲染 `/` palette 发起 provider/network 请求。

### 5.2 Typed 参数与 palette

TUI `/` palette 在 v0.1.5 必须支持：

- 空 `/`：按 category 展示 primary command，最多 10 行，支持 PageUp/PageDown；
- 输入命令：name、alias、description、category 的 token/fuzzy 匹配，不只做 prefix；
- 输入空格后：切换到 subcommand/argument suggestion，不再继续展示整条 command 列表；
- enum、model、effort、session、path 等参数使用 typed candidate provider；
- unavailable item 保留可发现性但 disabled，并显示原因；internal/compat 不进入普通 palette；
- destructive、deprecated、scope、provider/extension source 使用简短 badge；
- Enter 只执行完整且可用的 invocation；缺参时补全或显示 usage，不靠 command-name 正则特判；
- fuzzy/unique-prefix 只用于排序与建议，永不直接执行；执行必须命中 canonical、exact alias 或明确选中的 item；
- Esc 关闭、Tab 补全、上下键导航、resize、CJK 光标与 paste 行为保持稳定。

TUI 可提供丰富 picker；terminal-ui 只实现同一 descriptor 的基础 completion/smoke；Print/Text 和
Print/JSON 对需要 picker 的 command 返回候选与 machine-readable next action，不等待交互输入。

### 5.3 Structured CommandResult

本版移除 `captureConsoleOutput()` 的产品依赖，不再在并发 runtime 中改写全局 `console`：

```ts
interface CommandResult {
  status: 'ok' | 'error' | 'cancelled';
  summary?: string;
  blocks: CommandResultBlock[];
  warnings?: CommandWarning[];
  picker?: CommandPickerRequest;
  effect?: CommandEffect;
  nextActions?: CommandNextAction[];
}
```

- handler 返回纯数据；format/color/layout 由 renderer 完成；
- runtime 发出 `command_started`、`command_completed`、`command_failed`、`command_deprecated` 等事件；
- command output 是否写 transcript 由 protocol policy 决定，不能由 `console.log` 的存在与否决定；
- error、cancel、unavailable 和 confirmation-required 是不同状态；
- 为外部客户端预留 command descriptor snapshot，但本版不承诺稳定 SDK。

允许按 slice 迁移 handler，但 **v0.1.5 GO 前所有 primary command 必须脱离全局 console capture**；
advanced/compat handler 若暂时保留 adapter，必须列入有 owner 和 v0.2 删除期限的例外清单。

### 5.4 Invocation grammar 与命名规范

Slash command 是 CLI 公共 API，不是自由文本触发器。v0.1.5 固定以下语法：

```text
invocation  := "/" command *(SP token) [SP "--" SP opaque-tail]
command     := lower-kebab-name | exact-versioned-alias
token       := subcommand | option | typed-argument
```

规范：

1. canonical root 仅使用小写 ASCII kebab-case；domain 优先用稳定名词（`model`、`session`、`context`），
   高频状态动作可使用清晰动词（`resume`、`rewind`、`compact`）。禁止同时出现无合同的单复数 root。
2. command 仅在 trim 后输入的第一个 token 以 `/` 开头时识别；路径、Markdown、URL 和消息中段的 `/`
   仍按普通输入处理。command/subcommand/enum 可大小写无关解析，path、prompt、session name 等 opaque value
   必须保留原始 Unicode、空格和大小写。
3. `argumentHint` 只用于展示，不能参与执行。parser 必须产出 typed `CommandInvocation`，包含 command id、
   canonical name、alias used、subcommand、options、typed args、raw tail、source 和 validation result。
4. `--` 终止 option parsing；引号/转义只做参数分组，不做 shell expansion、变量替换或 command substitution。
5. 无参调用必须是 show/list/picker 或明确 usage；destructive action 必须具名 subcommand、精确 target、preview
   和显式确认，不能由 fuzzy match、默认值或 alias 推断。
6. unknown、ambiguous、unavailable、invalid-argument、confirmation-required、busy 和 cancelled 使用不同错误码，
   同时提供 `usage`、候选和 machine-readable `nextActions`。

### 5.5 运行中调度、扩展来源与冲突

一流 Agent 允许用户在 turn 运行时检查状态或排队调整，但不能让 command 与 provider/tool 状态发生竞态：

| Busy policy   | 适用示例                                                    | 合同                                                                            |
| ------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `immediate`   | `/status`、`/usage`、`/help`、只读 inspector                | 使用一致性 snapshot，不能修改 active logical request，也不能抢占 transcript     |
| `queue-next`  | `/model`、`/effort`、`/mode`、`/permissions`                | 写入 typed queued control input；只影响下一个 logical request，并显示待生效状态 |
| `reject-busy` | `/session` 切换、`/rewind restore`、destructive maintenance | 返回结构化 busy 原因；不得静默排队，也不得部分执行                              |

`/goal pause`、interrupt 等少数控制动作若需要立即影响 active turn，必须定义独立 runtime control event 和
幂等状态机，不通过普通 `immediate` handler 偷改共享状态。

扩展 registry 规则：built-in stable id/name 优先且不可被覆盖；project/user skill、MCP prompt、plugin 以
明确 source id 注册，unqualified name 只有在全局无冲突时可用。冲突时 palette 显示 qualified name、来源、
trust 和 risk；Print/ACP 必须使用 stable id 调用，不能依赖当前排序后的 display name。

### 5.6 非功能目标与成功指标

- metadata coverage 100%：canonical、alias、subcommand 都有 source、audience、risk、side effect、availability、
  busy policy、lifecycle、typed argument 和测试 owner；不允许 built-in fallback 默认值掩盖缺字段。
- 在 200 个 descriptor（含动态扩展）的基准下，palette/filter 本地计算 p95 < 50 ms、无 I/O/network；resize
  或输入一个字符不重建 runtime/provider。
- 空 `/` 首屏不超过 12 个 primary root；advanced/compat/internal 泄漏数为 0；同一 domain 的重复 canonical
  root 为 0。
- parser 通过 property/fuzz corpus：CJK、emoji、组合字符、引号、反斜杠、路径、URL、超长输入和控制字符
  均不误执行、不丢原始参数、不产生 shell expansion。
- TUI、terminal-ui、Print/Text、Print/JSON、ACP 对同一 invocation 产生相同 command id、validation、result
  status 和事件顺序；仅 renderer-view block 的呈现允许差异。

## 6. Effort 能力设计

### 6.1 用户合同

```text
/effort
/effort status
/effort <auto|none|minimal|low|medium|high|xhigh|max>
/effort <level> --project
/effort <level> --global
```

- `/effort`：TUI 打开 active model 实际支持级别的 picker；非交互 renderer 输出状态和合法值。
- 默认作用域是当前 session；`--project` 和 `--global` 是显式持久化写入。
- `/reasoning` 是 active alias，不复制实现。
- `auto` 表示删除该作用域 override，回到下一级配置或 model/provider default。
- `max` 是行为信号，不是“无限 token”；Goal budget、loop budget、max output 和安全权限仍独立生效。
- active model 不支持 effort 时 command 为 unavailable，必须说明 provider/protocol/model 和恢复路径。

### 6.2 公共类型

```ts
type EffortLevel = 'none' | 'minimal' | 'low' | 'medium' | 'high' | 'xhigh' | 'max';
type EffortPreference = 'auto' | EffortLevel;

interface ReasoningCapability {
  kind: 'effort-level' | 'thinking-level' | 'thinking-budget';
  supportedLevels: EffortLevel[];
  defaultLevel?: EffortLevel;
  adapter: EffortAdapterId;
  source: 'config' | 'discovery' | 'builtin';
}

interface ResolvedEffort {
  requested: EffortPreference;
  effective?: EffortLevel;
  source: 'request' | 'session' | 'project' | 'global' | 'model-default' | 'provider-default';
  capabilitySource?: ReasoningCapability['source'];
  supported: boolean;
  warning?: string;
}
```

迁移 `ModelProfile.reasoning?: boolean` 时保持向后读取：

- `false/undefined` 不推断支持；
- legacy `true` 只表示“可能支持 reasoning”，不能自动选择 wire parameter；`/effort` 显示为
  `unavailable: capability levels/adapter not configured`；
- 新 `reasoningCapability` 优先级遵循 config > discovery > builtin；不能仅凭模型名称 fuzzy 猜测。

### 6.3 配置与作用域

建议优先级（高到低）：

1. 当前 logical request 的显式 override（Print/SDK 边界，交互 CLI 暂不暴露）；
2. session `/effort` 或启动参数 `--effort`；
3. `ProjectConfig.defaultEffort`；
4. `GlobalConfig.defaultEffort`；
5. model profile / provider default，即 `auto`。

持久化字段均为可选：

- `GlobalConfig.defaultEffort?: EffortPreference`；
- `ProjectConfig.defaultEffort?: EffortPreference`；
- `SessionMeta.effortPreference?: EffortPreference`；
- runtime/store 保存 `requested` 与 `effective`，但不持久化厂商 wire payload。

旧 config/session 无字段时行为与 v0.1.4 完全一致：不发送 effort 参数。sanitize、schema、示例和
doctor 必须同时更新；未知/非法值 fail closed，并给出精确路径。

### 6.4 Provider adapter

当前公共 `ProviderProtocol` 只有 `openai-completions` 与 `anthropic-messages`；不能把计划中的
`openai-responses` 当成既有能力。本版先增加 immutable `ProviderRequestContext` 与协议 adapter：

| Adapter                   | v0.1.5 状态         | Wire contract                                                                                   |
| ------------------------- | ------------------- | ----------------------------------------------------------------------------------------------- |
| `anthropic-messages`      | P0 stable candidate | 只在 SDK/provider 当前合同与 live characterization 均证明后写 `output_config.effort`            |
| `openai-completions`      | P0 profile-explicit | 默认 unsupported；Huoshan/other gateway 只在 profile 显式声明 wire field 且脱敏 live 验证后发送 |
| `openai-responses`        | P1 conditional      | 新增 protocol 时必须闭合非流式、流式、tool call、abort、retry、usage，不做 effort-only 特例     |
| `google-generate-content` | deferred            | 当前没有该 `ProviderProtocol`；不在 v0.1.5 为了对标新增第二个协议扩张面                         |

每次 logical request 创建后冻结 model/provider/effort/max-output/tool schema；retry 必须复用同一
snapshot，避免用户在重试间改变 payload。`/effort` 在 active turn 中可以被 shared controller 接受，
但只对**下一个 logical request**生效，不改变已发出的请求或其 retry。

### 6.5 Model switch、fallback 与错误

1. `/model` 切换后重新 resolve effort；若 session override 不被新模型支持，显示 structured warning，
   effective 回到 `auto`，requested 值保留供用户选择，不得静默声称仍为 high。
2. 自动 provider/model fallback 也必须用 fallback profile 重新解析；event 同时记录 requested/effective、
   source 和 downgrade reason。
3. 用户显式指定的 effort 被 provider 以 unsupported/invalid parameter 拒绝时，不自动删除参数重试；
   返回 `unsupported_effort`，提示 `/effort auto` 或支持级别。
4. `auto` 默认不发送 provider 参数；provider 自己的实际默认未知时显示 `provider default`，不能猜成
   medium/high。
5. effort 变更可能降低 prompt cache 命中；TUI 在持久 session 中首次切换时给一次非阻塞提示，usage
   记录 cache token 变化但不夸大因果。

### 6.6 用量、状态和事件

扩展 `LLMUsage` / usage ledger：

- `reasoningTokens?: number`（若 provider 单独报告；它是 completion/output 的子集时不得重复计费）；
- `effortRequested?: EffortPreference`；
- `effortEffective?: EffortLevel`；
- `effortSource?: ResolvedEffort['source']`；
- `providerProtocol?: ProviderProtocol`；
- `latencyMs?: number`。

OpenAI 读取 reasoning token detail，Gemini 读取 `thoughtsTokenCount`，Anthropic 未单独报告时保持
undefined。usage ledger 采用 additive schema migration，v1 记录继续可读，不批量重写历史文件。

新增 shared runtime event：

- `effort_changed`：requested、scope、previous、appliesFrom；
- `effort_resolved`：model/provider、effective、source、supported levels；
- `effort_unavailable`：精确原因和恢复路径；
- provider request/usage trace 增加 effective effort，但不写私有 reasoning 内容。

TUI footer 默认显示 `model=<id> effort=<effective|auto>`；`/status` 和 `/usage` 展示 requested/effective
差异。terminal-ui 与 Print/JSON 使用同一字段；Ink 不新增产品 UI。

出现任一项即停止发布：

- 通过 prompt 文案或静态 boolean 冒充 effort API 已生效；
- unsupported effort 被静默删除、clamp、映射或计为成功；
- command handler 输出串到另一个 session/turn/subagent；
- destructive/配置写入命令绕过 shared preview/confirm；
- TUI、terminal-ui、Print、ACP 对 command 或 effort 产生不同业务结果；
- 旧 command 被提前删除且无 compat window；
- `/mode` 与 `/permissions` 仍共享一个无迁移合同的状态值，或 fuzzy/unique-prefix 能直接执行 command；
- active turn 中 queue-next command 改变当前 logical request，或扩展 command 能 shadow built-in；
- 只有 mock/dirty worktree/local partial tests，没有最终 source、PTY、package 或 live provider 证据。
- v0.1.5 仍基于 `addaa78` 而未纳入 main 后续修复，或发布包缺失 PR #123/#124 行为；
- 仅依靠 rerun 获得绿色 CI，或已知锁/cleanup 残余被写成“已彻底消除”；
- ACP 使用手写 parser/types、experimental v2、stdout 混日志、缺少 permission/cancel/resume 中任一项，
  却仍提交 Registry 或宣称 IDE stable。

### 11.3 回滚

1. effort provider 参数由单一 feature gate 控制；出现 provider 回归时可关闭参数注入，保留 config/session
   字段只读并显示 `temporarily unavailable`，不能假装仍生效。
2. command migration 每个 domain 保留旧名 compat map；回滚新 palette 时不回滚 shared runtime 的安全修复。
3. config/session/usage 都是 additive；旧二进制可忽略新字段，无需破坏性降级脚本。
4. npm 回滚发布前先停止 tag/publish；已发布时发布修复版本，不覆盖 registry 历史版本。

## 12. Zed / ACP v1 薄适配（条件性 Registry 分发）

> 权威依据是 ACP stable v1 schema、官方 `@agentclientprotocol/sdk` 与 Registry 当前 schema/CI。
> `docs/zed-acp-integration.md`（2026-08-08）只作调研背景，其中手写 JSON-RPC、单向方法和分发细节
> 若与官方 SDK/schema 冲突，以锁定版本的官方产物为准。v2 仍是 experimental，不进 v0.1.5。

### 12.1 一句话目标

让 Orion Code 作为 **stable ACP v1 服务器** 被 Zed 等兼容客户端驱动：`orion acp` 使用
官方 TypeScript SDK 的 NDJSON/stdio transport，复用现有 Agent runtime、Goal、session、tool permission 和
`UiEventSink`/`AgentRuntimeEvent`。ACP 实现通过本地客户端契约后只标记 experimental；通过包、认证、
Registry CI 和真实编辑器验收后才标记 stable/listed。

### 12.2 为什么 v0.1.5 做、且只做协议层

Zed 旧的 Agent Server Extension 已被 ACP Registry 取代。Orion 当前全仓无 ACP 代码，但已有
完整 turn runtime 与 npm 分发，因此只允许增加薄适配。这与 Goal 的 v0.3+ 多客户端方向存在
阶段张力：本版可做 POC/conditional delivery，但不得为了 Registry 排期绕过 G2 权限或 G3 单一 runtime。

### 12.3 当前基线与约束

| 项目      | 当前事实                                                                                                   | 对计划的约束                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| ACP 代码  | 全仓零命中；依赖中也没有 ACP SDK                                                                           | 新增 `src/acp/`，并锁定官方 `@agentclientprotocol/sdk` stable v1；禁止 experimental v2                         |
| CLI 形态  | `src/cli.ts` 手写 `process.argv` 分发（`orion` / `-p` / `--ui` / `doctor` / `diff` / `commit`）            | 新增 `acp` 分支，零侵入现有命令                                                                                |
| Turn 入口 | `AgentChatController.runInput(input, options)` 支持 `abortSignal`/`turnId`；`runRequest` 处理 Goal request | `session/prompt` 复用 `runInput`；`session/cancel` 是 notification，它 abort 当前 turn 并最终返回 `stopReason` |
| 事件出口  | `UiEventSink`/`AgentRuntimeEvent` 已有 text、tool、Goal、Research 事件                                     | `AcpEventSink` 将 text 投影为 message chunk，tool 投影为 tool call/update，不把所有事件压成 Markdown           |
| 会话存储  | `createSession`/`readSessionMessages`、Goal sidecar 与 resume 已有                                         | `session/new` 复用既有模型；Registry 前必须闭合 `session/load` 或 `session/resume`，不重放工具副作用           |
| 认证      | 本地 config/env 可检测，但尚无独立、可交互的 `orion setup` 流程                                            | Registry 的 terminal auth 需要真实 setup args/交互入口；仅在 `authenticate` 中读 config 不足以宣称支持         |
| 权限/MCP  | 共享 tool scheduler 已有 risk/confirmation；ACP client 会发 `mcpServers` 并接收 permission request         | 必须把 `session/request_permission` 对接 shared gate；未宣告的 MCP transport 拒绝，不忽略也不绕权限            |
| 分发      | 已发 npm `@orion-agents/orion-code`                                                                        | 优先 `npx` 分发；`orion` bin 软链到该包                                                                        |

### 12.4 协议映射设计

| ACP v1 方法/通知              | Orion 映射                                                                                 | 说明                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `initialize`                  | SDK handler 返回 `protocolVersion:1`、`agentInfo`、真实 `agentCapabilities`、`authMethods` | 能力只宣告已实现部分；Registry 认证门只接受 agent/terminal auth                      |
| `authenticate`                | 根据 `methodId` 确认 setup 后的本地凭据状态；缺凭据返回可操作错误                          | terminal auth 在初始化时提供 `args:['setup']`，需新增真实交互 setup 命令             |
| `logout`                      | 本版默认不宣告；只有安全的凭据撤销/本地语义锁定后才开启                                    | 不得声称 logout 却只清理无关内存态                                                   |
| `session/new`                 | 以请求 `cwd` 为 root，创建 Orion session + headless controller + per-session abort/sink    | 校验 cwd/附加 roots；宣告 MCP transport 时才接收并连接 `mcpServers`                  |
| `session/load`/`resume`       | 复用 session storage/Goal resume，恢复 controller 但不重放 tool 副作用                     | 本地 POC 可先声明 `loadSession:false`；进 Registry 前至少闭合一种可恢复路径          |
| `session/prompt`              | 将 Text/ResourceLink 转为 runtime input，调用 `runInput(..., {abortSignal, turnId})`       | 响应是 `stopReason`，不是 `done:true`；图像/音频只在 capability 开启后接收           |
| `session/cancel` notification | abort 该 session 当前 turn 与待定 permission，然后使原 `session/prompt` 返回 cancelled     | 它不是普通 request，不单独返回 result                                                |
| `session/update` notification | agent→client：text chunk、plan、tool call/update、usage、config update                     | 这不是 client→agent 的配置入口；事件顺序必须保留                                     |
| `session/set_config_option`   | model、effort、permission mode 通过 shared controller 变更，返回完整 config options        | 未知 config ID 返回 invalid params，不忽略；active turn 变更按现有 next-request 语义 |
| `session/request_permission`  | ACP agent 向 client 请求 allow/reject，结果输入 shared tool scheduler                      | 不能绕过 Orion risk metadata，也不能在 ACP 与 runtime 各做一次相互矛盾的确认         |

约束：

1. 传输为官方 SDK `ndJsonStream` 的 stdio JSON-RPC 2.0；**stdout 只允许协议帧**，日志必须进 stderr
   并脱敏。单元测试必须注入 command console 输出，证明不会污染协议流。
2. 固定 stable `protocolVersion:1`，使用 SDK 的 version/capability negotiation；不自定义“不支持时回自身最高”语义。
3. ACP v1 baseline 要求 Text 与 ResourceLink；image/audio/embedded resource 只在 `promptCapabilities` 声明后接受。
4. 每个 ACP session 独立 runtime、event sink、AbortController 与 permission correlation map；不共享当前 turn 状态。
5. SDK 包版本、ACP schema artifact 版本和 wire protocol 版本分开记录；升级 SDK 必须跑官方 schema/contract fixture。

### 12.5 架构与文件

新增 `src/acp/`：

- `src/acp/server.ts`：组装官方 SDK `agent(...).onRequest(...).onNotification(...).connect(ndJsonStream(...))`；
  只做进程生命周期和 stdout/stderr 隔离，不自建 parser/dispatcher。
- `src/acp/protocol.ts`：`initialize`/`authenticate` 与真实 capability 声明；`logout` 未有真实语义时不注册。
- `src/acp/session.ts`：`new|load/resume|prompt|cancel|set_config_option` 与 per-session resource map。
- `src/acp/events.ts`：`AcpEventSink implements UiEventSink`，类型化映射 message/plan/tool/usage/config update。
- `src/acp/permissions.ts`：ACP permission request/response 与 shared tool scheduler 的 correlation/abort 桥。
- `src/acp/auth.ts`：terminal auth 与 setup 状态判定；不记录、返回或透传 API key。
- 协议类型直接来自 `@agentclientprotocol/sdk`；不新增与官方 schema 并行的 `src/acp/types.ts`。

CLI 改动：`src/cli.ts` 在参数分发中增加 `case 'acp':` → `startAcpServer()`（不进入任何 UI 渲染器路径）。

Headless runtime：复用现有 runtime 构建函数，仅替换 event/permission/client-filesystem adapter；不引入
第二套 Agent 引擎。新工厂使用 Orion 命名，不恢复已删除的 OpenHorse 公共类型或 alias。

## 13. Definition of Done

v0.1.5 只有在以下结论都能被证据证明时才算完成：

1. 用户在 TUI 输入 `/` 能快速找到当前真正可用的控制入口，参数、风险、scope 和不可用原因清晰；
2. 过时、重复和误导命令已按迁移表收敛，旧调用有期限但不再污染产品 palette；
3. `/goal`、`/mode`、`/permissions`、`/model`、`/effort` 分轴清晰；canonical/alias/subcommand 命名、
   source/trust、availability 与 lifecycle 全部由同一 descriptor 生成和验证；
4. Help、palette、completion、文档和外部 command snapshot 来自同一 descriptor；fuzzy 只建议不执行，
   empty `/`、advanced、compat 和 internal surface budget 有可重复快照；
5. immediate/queue-next/reject-busy 在 active turn 中行为确定；built-in 不被 skill/MCP/plugin shadow，
   TUI、terminal、Print 和 ACP 使用同一 stable command id、validation、result/event；
6. command 业务处理不直接控制 stdout，所有 renderer 消费同一 runtime result/event；
7. `/effort` 从用户选择贯通到 active provider request，并能用 payload/usage/trace 证明实际 effective 值；
8. model switch、fallback、unsupported、retry、abort、resume 和 config write failure 都有确定行为与测试；
9. effort 不绕过 Goal budget、loop budget、权限、安全确认或完成审计；
10. 最终 clean source 通过质量、PTY、provider、package、发布和回滚 gate，没有把计划、局部实现或本地测试
    误报为已发布能力。
11. v0.1.5 从最终 main 基线交付，PR #123/#124 与 #125～#132 predecessor 的行为在最终 tarball
    和 registry install 中仍可验证；
    Goal evidence 非确定性不靠 rerun 掩盖，已知 stale-lock/cleanup 残余有实现或带 owner/期限的显式处置。
12. ACP 若进 v0.1.5 对外范围，A1～A8 全部有证据，且 npm、Registry、CDN 和真实 client 状态分开记录；
    若任一外部门未关闭，计划必须把 ACP 标记为 deferred/experimental，不能用本地 POC 宣称 Registry/IDE 交付。

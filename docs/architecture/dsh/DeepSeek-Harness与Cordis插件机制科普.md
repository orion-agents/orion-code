# DeepSeek Harness 与 Cordis：一文读懂「一切皆插件」的 Agent 底座

> 基于 2026 年 8 月 DeepSeek 开源事件的深度解读，涵盖插件机制、Cordis 运行时、与 Skill 的区别、以及它对 AGI 的意义。

---

## 引言

2026 年 8 月 13 日，DeepSeek 开源了官方 Agent 框架 **DeepSeek Harness**（CLI 名 `dsh`），MIT 协议，发布 24 小时即获 4.6 万星。它的核心设计只有一句话：

> **Everything is a Plugin —— 一切皆插件。**

模型、工具、技能、会话、沙箱、存储、Agent 循环、UI……所有能力都是可替换的插件，无需改动源码即可自由组合。

更值得关注的是它背后的运行时 **Cordis**——由北京大学与 DeepSeek-AI 联合开发，88 页论文《A Programming Paradigm for Spatiotemporal Composability》同步发布。这篇科普从九个问题入手，把这套体系讲透。

---

## 一、DeepSeek 最新的插件方案是什么？

DeepSeek Harness 基于 **Cordis 插件框架**构建，核心架构分层：

| 层级 | 职责 |
|---|---|
| **Cordis 运行时** | 元框架，只负责插件加载/卸载与依赖管理 |
| **核心层** | 调度、上下文管理、会话生命周期——仅此三件事，无特权核心 |
| **插件层** | 模型适配器、工具注册表、会话日志、Agent Loop、沙箱、审批策略……全部是插件 |
| **模型层** | 与 DeepSeek 深度适配，但架构上可替换（支持 OpenAI/Anthropic 及自定义端点） |

**关键设计：插件系统没有需要打补丁的特权核心——包括 Agent 循环本身都可以从配置层替换。**

### 四种运行模式

| 模式 | 加载内容 | 适用场景 |
|---|---|---|
| 标准模式 | 完整工具集 | 日常 Agent 工作 |
| PTC 模式 | 程序化工具调用——模型生成一段代码编排多轮工具调用 | 复杂多步骤工作流 |
| 极简模式 | 仅 shell + 文件编辑两个工具 | 模型基准测试 |
| 创造模式 | 检查运行时、在内存中试验 Cordis 插件 | 构建测试新插件组合 |

### 组织概念

- **Profile**：命名组合，列出叠加的 Bundle、外部插件与用户 `cordis.patch.yml`；内置 `web` 与 `headless` 两个模板
- **Bundle**：Cordis 配置行 + 挂载代码的分发格式，插入内容可被上层补丁覆盖
- **dsh-base**：所有 Profile 的基础层（模型适配器、工具、持久化、沙箱、审批策略、凭证、遥测）

快速上手：`npx @deepseek-ai/dsh web`，默认监听 `http://127.0.0.1:3080`。

## 二、插件是插到模型上吗？

**不是。插件插到 Harness（运行时）上，模型本身不感知插件。**

一个直观的类比：

> **模型是 CPU，Harness 是主板，插件是插在主板上的显卡/声卡/网卡。** 换 CPU 不需要拔显卡，加网卡也不需要动 CPU。Cordis 就是这块主板的「总线协议」。

实际执行流程：

```
用户输入 → Agent Loop 插件调度
    ↓
模型插件：把上下文发给模型，拿回回复
    ↓
回复含工具调用意图？
  ├─ 是 → 工具插件执行 → 沙箱插件实际执行 → 会话日志记录 → 回到 Loop
  └─ 否 → 输出最终结果
```

模型中整个过程的角色是**「决策者」**：接收上下文、输出下一步动作。换模型 = 换一个模型适配器插件，不影响工具/沙箱/日志。

## 三、Cordis 是什么？

**一句话：一个 TypeScript 元框架，核心理念是「时空可组合性」——让运行中的程序能像换零件一样卸载/替换组件，且不留下任何残留状态。**

论文核心问题：

> **运行中的 Agent 能否「换零件」而不重启？**

传统软件存在「粒度不匹配」：组件组合粒度是函数/模块级，生命周期管理却是进程/容器级。想换一个小模块就得重启整个进程——丢缓存、丢连接、丢正在执行的任务。这在 self-evolving Agent 场景里是致命的：Agent 生成的坏模块甚至可能把「修复自己」的进程一起搞挂。

### 两大核心机制

**1. 时间可组合性（Temporal Composability）——可逆效应**

传统插件系统：`activate` 与 `cleanup` 是分离的两套代码，开发者必须手工保证卸载时一项不漏地撤销。

Cordis 的做法——**每个 effect 同时返回它的 inverse**：

```typescript
ctx.effect(() => {
    registerRoute("/foo")        // 做事
    return () => unregisterRoute("/foo")  // 自动注册撤销
})
```

撤销按 LIFO 执行：`E1 → E2 → E3` 的执行，撤销顺序是 `E3⁻¹ → E2⁻¹ → E1⁻¹`。初始化到一半失败时，Cordis 自动逆序撤销已执行部分，无需手动处理「半初始化」异常路径。

**2. 空间可组合性（Spatial Composability）——依赖驱动生命周期**

组件声明依赖（Coeffect）：

```yaml
inject:
  - database
  - logger
# 只有 database 和 logger 都存在时才运行
```

依赖满足关系驱动组件的激活/停用。例如 `MySQL Provider → User Service → REST API`，MySQL 被卸载时变化反向传播：REST API 先 deactivate → User Service deactivate → MySQL 最后卸载。

最精妙的细节是 **UNLOADING 状态**：provider 卸载时，consumer 的 teardown 可能还需要它（flush 数据、关连接），因此 provider 先停止接收新 consumer，等旧 consumer 全部完成 teardown 后才真正执行自己的 inverse。

### 最核心的保证：Confluence（汇合性）

> 系统经历过怎样的 load/unload/reload 历史不重要，最终稳定后的状态**等价于直接加载最终配置**。

```
启动 A → 启动 B → 删除 A → 装 C → 重装 A → 替换 B → 删 C
最终只剩 A + B' → 状态 = 直接启动 A + B'
```

不会有旧版的 ghost listener、残留的 tool registration、泄漏的 cache entry。这是 Cordis 与所有「尽力而为」插件系统的分水岭。

### 事务性 HMR

传统 HMR 依赖模块作者自己声明接受边界、自己处理旧状态。Cordis 因为 effect 自带 disposer：

```
dispose old fiber → recover effects → reload module → instantiate new fiber
```

新模块 import 失败时自动恢复旧 fiber——**热替换要么成功，要么原样回滚**。

### 存在性证明：Koishi

Cordis 已在 Koishi（聊天机器人框架）上运行多年，社区插件超 **4000 个**，证明这套抽象能支撑真实的大型插件生态。DeepSeek Harness 是它在 AI Agent 领域的新应用。

## 四、它是「Agent + 插件」的概念噱头吗？

**噱头在于包装，不在于内核。**

### 噱头部分

- 「一切皆插件」本身是营销话术——任何框架拆到底都是模块化
- 88 页论文 + 形式化证明，包装感确实有
- v0.1 工程实现远未兑现理论高度：runtime 不验证 inverse 正确性、effect independence 假设较强

### 不是噱头的部分

它解决了一个真实且难的问题——**动态状态管理**：

```
传统插件卸载：开发者手动写 cleanup，忘了 3 个
            → 残留 listener / route / cache
            → 运行越久脏状态越多，最后只能重启

Cordis 卸载：effect 自带 inverse，自动逆序回滚
            → Confluence 保证无残留
            → 最终状态只由当前配置决定
```

这个问题在普通应用里是「烦」，在 **self-evolving Agent** 里是「致命」：Agent 删掉一个有 bug 的工具插件，残留的 event listener 还会触发——行为不可预测，state drift。

### 一句话

> **底层有真东西，但被包装成了「颠覆性范式」来讲，实际成熟度还在早期。**

## 五、Skill 与 Cordis 插件的区别？

| 维度 | Skill | Cordis 插件 |
|---|---|---|
| 作用层 | 模型行为层（prompt + 工具流程） | 运行时基础设施层（状态 + 生命周期） |
| 插拔的是什么 | 知识和流程（「怎么做 PDF」） | 能力和资源（工具注册表、沙箱、模型适配器） |
| 执行者 | 模型自己按指令执行 | 运行时执行确定性代码 |
| 确定性 | 低——同样 skill，不同模型执行质量不同 | 高——同一输入同一输出 |
| 卸载后 | 不加载就完了，无状态问题 | 必须撤销所有 effect、级联处理依赖、保证无残留 |
| 需要 Confluence 保证吗 | 不需要 | 核心卖点 |

**类比：**

```
Skill = 菜谱（告诉模型该怎么做）
零件 = 自动售货机（模型按按钮，机器确定性出货）
```

模型控制使用两者的**机制相同**（都是工具调用），但控制的对象不同：

- **调用零件 = 委托**：模型出意图，代码执行，模型不参与
- **加载 Skill = 指导**：模型拿到指令文本，自己按步骤执行，内部还会调用一堆零件

关键：**Skill 是插件的子集。** 在 Harness 里，Skill 管理本身就是一个 Cordis 插件。Skill 解决「教固定能力换着花样做事」，插件解决「能力本身可以扩展」。

## 六、dsh-plugin 都是些什么？需要很多插件吗？

**插件 ≠ Skill，Skill 只是插件家族的一支。** 插件按用途分六类：

| 类别 | 干什么 | 你感知得到吗 |
|---|---|---|
| 基础设施类 | 模型适配器、沙箱、会话日志、存储、审批策略 | ❌ 看不到但必须有 |
| 工具类 | 读文件、写文件、跑命令、Git | ✅ 日常用的就是这些 |
| 连接器类 | 接入外部系统（MCP server、数据库驱动、API 客户端） | 按需 |
| 能力类 | 视觉/OCR、语音、浏览器自动化 | 按需 |
| 知识/流程类 | 指导模型怎么做——**本质就是 Skill** | 按需 |
| UI 类 | 终端 TUI、Web 面板、任务看板、皮肤 | 你看到的 |

### 你的直觉是对的

如果你只是想要一个「能帮我写代码的 Agent」：

```
基础工具插件（文件读写、命令、Git）
+ 一个模型适配器 + 会话日志
= 够用了
```

**没有任何平台要求你装一堆插件才能用**——默认状态是够用的，插件是**按需添加**的。

### 但生态为什么需要很多？

因为**不同人要做的是完全不同的 Agent**：

| 想造的 Agent | 需要的插件 |
|---|---|
| 代码助手 | 文件读写 + Git + 终端 + LSP |
| 客服机器人 | CRM 连接器 + 工单系统 + 知识库检索 |
| 数据分析师 | 数据库驱动 + 图表生成 |
| 运维 Agent | SSH + 监控 + 日志分析 |
| 视觉 Agent | 截图 + OCR + 图像理解 |

**每个人只需其中一行，但平台必须覆盖所有行。** 这就是长尾逻辑——就像 VS Code 不会因为「我只用 5 个扩展」而砍掉扩展市场。

### 更关键的一点

大部分插件不用自己写。dsh 深度支持 **MCP**——MCP server 生态已有几千个现成连接器，挂载一个 MCP server 就是一个插件。

## 七、一个通用 Agent 加载 skills 集合，不也一样吗？

**大部分知识型场景，确实够了。** 但「效果相似」和「机制相同」是两回事：

```
通用 Agent + skills：能力边界 = 厂商出厂配好的几个工具
                    加载 skill = 换个方式用这些工具
                    → 没法让它突然会连数据库
                    → 没法让它突然拥有视觉

Harness + 插件：能力边界 = 可扩展的
                挂 MCP server → 接入几千个外部系统
                换沙箱 → 获得隔离执行环境
```

**读 1000 本《直升机驾驶手册》，司机开的还是汽车。** 手册改变「怎么开」，不改变「开什么」。

分水岭场景：

| 场景 | 通用 Agent + skills | Harness + 插件 |
|---|---|---|
| 写作/总结/代码生成 | ✅ 够用 | ✅ 够用 |
| 接入外部系统 | ❌ 缺真连接 | ✅ 挂连接器插件 |
| 需要真实执行环境 | ❌ 缺执行后端 | ✅ 换沙箱插件 |
| 运行时切换模型/工具集 | ❌ 厂商固定 | ✅ 热替换 |
| 多 Agent 协作 | ❌ 无此能力 | ✅ 插件提供 |
| Agent 自我进化 | ❌ 手册换不了零件 | ✅ 设计目标 |

**两者是包含关系，不是替代关系：Skill 是插件的一个子集。** 通用 Agent + skills 是「产品逻辑」（一个 Agent 卖天下），Harness + 插件是「平台逻辑」（你们自己造 Agent）——DeepSeek 选的是后者。

## 八、AGI 需要运行态能力吗？插件系统能实现自动进化吗？

### AGI 需要——这是整场讨论的落点

看「学习」的两种形态：

```
当前 LLM 的学习 = 权重更新（离线、缓慢、重训练，改参数不改架构）
AGI 需要的学习 = 组件增删（在线、即时、运行中完成，能力结构可变）
```

人类学开车、学编程、学新语言，本质是「大脑里装进新能力模块」，不需要重启大脑。AGI 要逼近这一点，能力结构就必须运行时可变。

**Cordis 的三个保证恰好对应 AGI 的三个需求：**

| Cordis 机制 | AGI 需求 |
|---|---|
| 可逆效应 | 自我修改必须能回滚——坏工具要能干净卸载 |
| Confluence | 自我进化最怕 state drift——最终状态只由当前配置决定 |
| 依赖驱动生命周期 | 换组件时依赖它的东西自动级联调整——不能因换 memory 就崩溃 |

### 但插件系统做不出自动进化

进化需要三样东西，Cordis 只有一样：

| 要素 | 干什么 | Cordis 提供吗 |
|---|---|---|
| 变异（生成新组件） | 产生新能力 | ⚠️ 部分——架构允许，但 LLM 生成不可靠 |
| 选择（评估优劣） | 判断新组件是否更好 | ❌ 基本没有——最大缺口 |
| 安全承载（可回滚） | 变异失败不污染系统 | ✅ 完整——这就是 Cordis 的全部贡献 |

更深一层：**换零件 ≠ 变聪明**。插件扩展的是「能力结构」（相当于外骨骼），不改变「推理能力」（相当于大脑皮层）——后者发生在模型权重层面，热插拔管不到。

### 结论

> **插件系统是 AGI 自我进化的「允许条件」，不是「引擎」。它解决的是「改坏了怎么办」，不是「该不该改、往哪改」。真正的进化需要可靠的变异（模型写可靠代码）和可靠的选择（自我评估），这两者当前都未解决。Cordis 是在赌一个前提：总有一天模型写代码和评估的能力足够可靠——到那天，它的地基直接派上用场。**

## 九、Cordis 先进在哪里？

**它的概念几乎都有先例，先进在「组合 + 证明」：**

| Cordis 概念 | 先例 | 差异 |
|---|---|---|
| 可逆效应 | 数据库 undo log | undo log 只管数据，Cordis 管任意组件副作用 |
| 依赖注入 | Spring DI | Spring 只管装配，Cordis 用依赖关系驱动生命周期 |
| 热替换 | Webpack HMR / OSGi | 传统靠开发者处理旧状态，Cordis 是事务性的 |
| 动态加载 | 插件系统遍地都是 | 卸载保证无残留（Confluence），不是尽力而为 |

**最贴切的类比：Cordis 想做「动态软件组件的 ACID」。**

- 可逆效应 = 事务 undo log
- Confluence = 事务隔离/提交
- coeffect = 约束
- inverse = 回滚

四个形式化保证（88 页论文、30 页数学证明）：**Preservation**（结构合法性）、**Temporal Composability**（恢复精确性）、**Spatial Composability**（依赖安全性）、**Confluence**（历史无关性）。

### 诚实的边界

| 局限 | 说明 |
|---|---|
| runtime 不验证 inverse 正确性 | 忘了写撤销，检测不到 |
| 只验证了 Koishi 一个生态 | 4000 插件验证「能用」，未验证「普遍适用」 |
| 运行时开销未测 | 论文承认没有 controlled benchmark |
| 依赖循环难解 | A↔B 循环依赖两边都 inactive，最坏 O(n²) 拆件 |

## 十、这个能力能引入 OpenClaw 或 Claude Code 吗？

**分对象看：CC 基本不可行；OpenClaw 可行但要看值不值。**

### Claude Code：几乎不可能

CC 是闭源商业产品，扩展面只有 Skill（模型行为层）、MCP（工具接入层）、CLI 钩子——**摸不到它的工具注册表、生命周期、依赖图**，而这些恰是 Cordis 语义要作用的地方。能做的最多是应用层模拟（skill 记录自己注册了什么、退出时清理），那只是手写 cleanup，不是 Cordis。

### OpenClaw：三条路径

| 路径 | 做法 | 成本 | 收益 |
|---|---|---|---|
| A. 借语义（推荐） | 不引入 Cordis，给现有插件系统加「注册时携带 cleanup + 依赖声明」 | 低 | 获得 70% 的卸载无残留效果 |
| B. 薄适配层 | 写插件注册管理器，统一跟踪注册/注销 | 中 | 类似 A，更系统化 |
| C. 深度集成 | 把 Cordis 作为运行时框架重构核心 | 极高 | 完整语义，但等于重写 |

### 关键判断：值不值？

```
Cordis 解决：运行时动态增删组件的安全性
   —— 组件运行中频繁装卸、卸载无残留

多数 Agent 产品现状：启动时一次性装配
   —— 装好基本不拆，重启才换配置
```

**没有「运行中频繁装卸组件」的场景，Cordis 的核心价值就发挥不出来**——进程退出本身就清理了，Confluence 是为「运行中改一百次不重启」设计的。

### 建议

| 场景 | 建议 |
|---|---|
| 只是想让插件卸载干净 | 路径 A，半天工作量 |
| 想做 Agent 平台的底座 | 考虑路径 C，但这是战略级决策 |
| 想给 CC 加这个能力 | 放弃——在 skill/MCP 层做应用级清理就够 |
| 为 AGI 自我进化做准备 | 不用现在做——等模型能写可靠代码再评估 |

## 总结

整场对话的思考链条：

```
DeepSeek Harness（一切皆插件）
  → Cordis（可逆效应 + Confluence）
  → self-evolving Agent（运行中自我修改）
  → AGI（能力结构可进化）
```

每层都是上一层的必要条件。六个关键结论：

1. **Harness 的插件插在运行时上，不是模型上**——模型只是被 Agent Loop 调用的插件之一
2. **Cordis 的先进是「范式级」的**——把副作用可逆、依赖驱动、历史无关提升为运行时一等语义并数学证明，相当于动态软件的 ACID
3. **Skill 是插件的子集**——Skill 教固定能力换着花样做事，插件让能力本身可扩展
4. **「一切皆插件」有包装成分，但内核是真的**——v0.1 工程实现尚未完全兑现论文承诺
5. **插件系统做不出 AGI 自动进化**——它只是安全承载变异的地基，缺变异可靠性和自我评估两个引擎
6. **对现有 Agent 产品（OpenClaw/CC）**——多数场景取 10% 精华（注册即携带 cleanup）就够，不必全量引入

> **DeepSeek 一个模型厂商，花 88 页论文去证明一个「插件系统」——他们在为 AGI 铺地基，不是在做插件。**

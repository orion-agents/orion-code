## 1. Qualification objective

The release gate must prove a complete user journey, not merely that the browser shell renders.
Starting from one exact npm tarball installed into an empty prefix, a real Chrome browser must drive
the public Web Workbench through HTTP and SSE into the production Web bridge, Orion runtime,
ToolGateway, permission system, filesystem, command runner and durable session state. Refresh,
network loss and process restart must not lose committed state or repeat a side effect.

The only controlled substitute is the external LLM provider boundary. A loopback,
OpenAI-compatible fixture returns deterministic streamed text and tool calls. Orion's product
runtime, permission decisions, tools, persistence and file effects remain real. A live-provider
canary is separate, opt-in and non-blocking because it requires credentials, network access, cost
authority and tolerance for model nondeterminism.

## 2. Starting evidence and known gap

The plan was started after a live repository check on 2026-08-27:

- branch `v0.3.0`, HEAD `40d02f687b70a648b452022ebf0e2f114021ea2e`;
- package version `0.3.0`; the then-current contract covered Node `20.19+`, `22.12+` and `24.x`;
- the default shell used then-unsupported Node `26.5.1`; local Node `22.22.3` and `24.14.1` were
  present, while a conforming Node 20 runtime was not yet present;
- Google Chrome `151.0.7922.174` was present;
- the worktree already contained the v0.3.0 implementation and unrelated user-owned edits. In
  particular, `docs/plan/quality-review-rotation-next-run.md` is out of scope and must not be
  overwritten;
- `npm run test:web-browser` passed against the real loopback Host and Chrome with a real session
  mutation, responsive drawer behavior and zero axe violations;
- the five focused Web contract/Host/event/controller suites passed 16 of 16 tests.

That evidence is only the baseline. The current browser smoke stops after the model-unconfigured
state and therefore does not prove a model turn, ToolGateway approval, filesystem effect, durable
recovery or reconnect idempotency. The existing dependency is `playwright-core`; a durable
Playwright Test runner, fixtures, reports and traces are still required.

## 3. Trust and isolation model

Every run receives a unique root containing:

- a fixture workspace and a second outside directory;
- an isolated `ORION_CODE_CONFIG_DIR` using current `providers` plus `models` configuration;
- a loopback OpenAI-compatible provider with a test-only environment-backed key;
- a loopback MCP server where required;
- an empty package-install prefix containing the exact target tarball;
- a browser profile, downloads and Playwright output;
- a manifest containing only sanitized paths, versions, hashes and test results.

The runner must never read or write the user's normal Orion configuration. It must never use the
DeepSeek Harness checkout. Temporary roots are deleted after success; failed-run evidence is kept
under `tests/tmp/web-e2e/<run-id>/` for diagnosis. No secret or authorization header may enter a
committed report.

The deterministic provider must record a bounded, redacted request summary: scenario, message
roles, selected mode, tool-result receipt and request count. It must not persist system prompts,
raw credentials or unrestricted workspace contents.

## 4. Artifact-first execution model

The authoritative candidate is a tarball plus receipt, not the mutable checkout:

1. Build the server and Web client with a supported Node runtime.
2. Produce one tarball with `release:artifact`; capture its SHA-256, npm integrity, manifest digest,
   source Git SHA and dirty flag.
3. Install that exact tarball into a new prefix.
4. Start the installed `bin/orion web --no-open --port 0 --cwd <fixture>` process.
5. Parse the emitted loopback URL and assert the listener is `127.0.0.1`.
6. Run browser journeys only against that installed process.
7. Reuse the same immutable tarball and receipt for the Node 22, 24 and 26 critical matrix.

Source-mode tests may be used while developing fixtures, but they cannot close a packaged-runtime
criterion.

## 5. Test runner and target layout

The implementation uses Playwright Test, with its version aligned to the existing
`playwright-core` version. The intended layout is:

```text
playwright.config.ts
tests/e2e/
  fixtures/
    artifact.ts
    evidence.ts
    openai-provider.ts
    mcp-server.ts
    orion-host.ts

  web-recovery-idempotency.spec.ts
  web-modes-goal-plan.spec.ts
  web-workspace-settings-catalog.spec.ts
  web-security-accessibility.spec.ts

  run-web-e2e-matrix.ts
```

Selectors in core journeys must use accessible roles, labels and visible product text. CSS or test
IDs are permitted only for non-interactive structural assertions where there is no semantic target.
Direct browser-context `fetch` is reserved for transport/security/idempotency negative cases and
cannot substitute for the core user journey.

The existing `test:web-browser` remains a fast smoke. New target scripts are:

- `test:web-e2e`: full packaged Chrome suite on the primary supported Node runtime;
- `test:web-e2e:critical`: the smallest complete create/turn/approval/effect/recovery journey;
- `test:web-e2e:matrix`: critical journey against one exact tarball on Node 22, 24 and 26;
- `test:web-live-canary`: explicit opt-in live-provider check, never invoked by default CI or
  publication scripts.

## 6. P0 scenario matrix

### E2E-P0-01: packaged bootstrap and public UI

Action:

- install the exact tarball into an empty prefix;
- start the installed CLI with port zero and an isolated workspace/config;
- open the emitted URL in real Chrome;
- create and rename a session through visible controls.

Required proof:

- package identity and SHA match the artifact receipt;
- the Host is `127.0.0.1`, health is ready and Web assets come from the installed package;
- bootstrap/UI report `0.3.0`;
- session creation and rename persist after reload;
- no unexpected page error, console error, unhandled rejection or HTTP 5xx occurs.

### E2E-P0-02: coding turn, denial, approval and exact effect

Action:

- submit a deterministic coding request in BUILD through the composer;
- let the provider request a real read followed by a permission-gated write;
- deny the first write;
- submit the approved variant and select `once`;
- let the provider request a real verification command.

Required proof:

- streaming assistant/tool UI is ordered and reaches a terminal turn state;
- denial produces a durable denied receipt and leaves the target file absent/byte-identical;
- approval uses the same displayed permission request, applies exactly one write and creates the
  exact expected bytes and SHA-256;
- the real verification command exits zero and its result is inspectable in the UI;
- provider observations and durable receipts agree on tool names, call IDs and result order.

### E2E-P0-03: approval ownership and shutdown behavior

Action:

- pause on a pending approval;
- reload, close the page and open a new browser page;
- resolve the restored approval;
- in a separate run, stop the Host while an approval is pending and restart it.

Required proof:

- reload/tab close does not approve or deny and reprojects the same request ID;
- only an explicit browser decision resolves the live request;
- shutdown/forced runtime teardown fails the waiting tool closed;
- restart never executes an orphaned pending tool call.

### E2E-P0-04: SSE replay and no duplicated side effect

Action:

- capture the session snapshot cursor;
- interrupt the browser SSE connection while a deterministic turn produces events;
- restore connectivity and allow the client to replay/recover.

Required proof:

- observed cursors are monotonic after de-duplication;
- every event ID is unique in the final projection;
- a replay reset causes a fresh snapshot rather than silent loss;
- the recovered transcript equals a final server snapshot;
- the write/command receipt count remains one.

### E2E-P0-05: mutation retry and settings CAS

Action:

- allow the Host to commit a mutation, discard the first client response and retry the exact body
  with the same request ID;
- reuse that request ID with a different body;
- open two pages at the same settings revision and submit competing changes.

Required proof:

- the exact retry returns the original response and performs one mutation;
- a body-digest conflict returns HTTP 409;
- the second stale settings update returns HTTP 409 and cannot overwrite the first;
- bootstrap, responses and browser traffic contain no provider key.

### E2E-P0-06: PLAN, Goal and AUTO semantics

Action:

- select PLAN and run the deterministic plan scenario;
- observe its committed receipt and automatic follow-on execution;
- create a durable Goal, advance it across turns, reload and complete it;
- select AUTO and attempt both an authorized edit and a hard-policy escape.

Required proof:

- the Web Plan projection contains exactly `body`, `returnMode` and `digest` semantics; it does not
  synthesize review status or steps;
- planning commits before execution, and execution occurs in a separate logical request;
- Goal restoration is derived from the latest valid TurnCommit and completion has durable evidence;
- AUTO can suppress interactive confirmation only inside configured Authority; workspace escape and
  hard-denied operations remain denied.

### E2E-P0-07: workspace/session isolation and observable catalogs

Action:

- use two isolated workspaces and multiple sessions;
- create, rename, resume and switch sessions;
- inspect Skills, MCP and tool-detail collections;
- explicitly select/call the local MCP fixture;
- generate output larger than 64 KiB and page through its detail.

Required proof:

- a session from another project cannot be activated in the current workspace;
- failed activation does not strand the old runtime;
- Skills/MCP descriptors are safe metadata; MCP remains dormant before selection and runs only for
  the explicit call;
- tool-detail paging is byte-bounded with no gap/overlap and exposes no local backing path;
- large output is not embedded wholesale in SSE.

Tool details are project-scoped in v0.3.0. The test must not claim session ownership that the
artifact metadata cannot prove.

### E2E-P0-08: browser security and accessibility

Action:

- use a hostile-origin browser page and direct browser-context requests for negative cases;
- test missing/wrong Origin, nonce and content type, oversized JSON, encoded traversal and symlink
  boundary behavior;
- exercise desktop and 390 x 844 layouts by keyboard;
- run axe in an isolated audit context.

Required proof:

- Host, Origin, nonce, body and path violations fail closed with the expected 4xx response;
- the normal application runs with real CSP and without `bypassCSP`;
- only the separate axe-injection context may use `bypassCSP`;
- frame embedding is denied, focus is visible/restored and drawers/dialogs close with Escape;
- axe reports zero critical or serious WCAG A/AA/2.1 AA/2.2 AA violations;
- sanitized network/SSE/HTML evidence contains no API key, authorization header or configured
  environment secret.

### E2E-P0-09: supported Node matrix

Action:

- run the critical packaged journey against the exact same tarball/receipt on Node 22.12+, 24.x
  and 26.x.

Required proof:

- each runtime records its exact Node/npm/Chrome/OS identity;
- package install, Host startup, browser task, approval, effect, reload and shutdown pass;
- every matrix record binds to the same tarball SHA-256;
- any unavailable runtime is a failed/missing gate, not a skip represented as pass.

The v0.3.0 Settings extension adds `SET-P0-01..14` from
[`v0.3.0-settings-integration-plan.md`](../plan/v0.3.0-settings-integration-plan.md). Final full
coverage is `E2E-P0-01..08 + SET-P0-01..14` (22 scenarios); final critical coverage is
`E2E-P0-01..04 + SET-P0-01..14` (18 scenarios) on every supported Node major.

## 7. Stability and release decision

The primary full P0 suite must pass three consecutive fresh runs. A retry performed by Playwright is
diagnostic evidence, not a passing first attempt: release evidence records both initial and retry
outcomes. Timeouts are bounded and based on observable state transitions; increasing a timeout or
adding a skip is not an acceptable repair for a race.

The decision is `GO` only when:

- every P0 criterion above has fresh direct evidence;
- no unexplained browser/runtime warning remains;
- there are no page errors, console errors, unhandled rejections, unexpected 5xx responses, event
  gaps, duplicated side effects or secret findings;
- all three consecutive primary runs and all three Node-major matrix runs pass against the one
  artifact;
- focused regressions, build, lint, Web browser smoke and release checks remain green.

Otherwise the decision is `NO-GO`, with exact failed criteria and evidence paths. A live-provider
canary is reported independently as `PASS`, `FAIL` or `NOT RUN` and never changes a deterministic
P0 failure into `GO`.

## 8. Evidence contract

Each run writes a private `manifest.json` with:

- run ID and timestamps;
- source Git SHA and dirty flag;
- package name/version, tarball path, tarball SHA-256 and receipt digest;
- Node, npm, browser, OS and architecture identities;
- sanitized workspace/config roots;
- scenario status/duration and evidence-relative paths;
- before/after file hashes, observed event cursors/IDs and durable receipt digests;
- page/console/request failures and secret-scan results;
- final `GO` or `NO-GO` decision.

Playwright writes JUnit and HTML results, screenshots and trace/video on failure. Network and SSE
capture is a redacted semantic log, not a raw HAR containing headers or bodies. The committed report
contains artifact hashes, command outcomes and relative local evidence paths but no credentials,
absolute personal paths, raw prompts or unrestricted file content.

## 9. Failure handling and cleanup

- On a product failure, preserve the failed evidence root, make the smallest in-scope repair, add a
  regression assertion and rerun the affected scenario plus the full primary suite.
- Never lower a security rule, delete an assertion, broadly mock Orion internals, turn a P0 into a
  skip or hide a failure behind retries.
- On a fixture/runner failure, prove that the product path was not reached before classifying it as
  infrastructure rather than product.
- Terminate provider, MCP, Host and browser process trees in `finally` hooks. Validate every cleanup
  target as a run-owned temporary directory before removal.
- Do not commit, push, tag or publish as part of this Goal.

## 10. Execution record

Append exact commands, artifact identity, failures, repairs, three-run stability results, Node matrix
results and the final decision to `docs/test/v0.3.0-web-e2e-report.md`. Do not edit historical proof
to make a later run appear green.

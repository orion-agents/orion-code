## 一、核心结论（执行摘要）

1. **Orion Code 的内核已经很强。** Agent Loop（生成器式、带预算护栏/并发调度/自动压缩）、多层记忆（文件 + sqlite-vec 向量 + harness 上下文 + 会话）、MCP 一等公民集成、强安全设计（命令分级、SSRF 拦截、轨迹脱敏）、Skills 插件化、受约束只读子代理 —— 这些是扎实的工程能力，与 Codex / WorkBuddy 的水平相当甚至更安全。

2. **但「产品形态」存在结构性代差。** 当前是**纯 CLI + npm library**，没有桌面外壳、没有图形前端框架（React 仅用于已弃用的 Ink TUI）、没有可视化设置/会话/文件管理界面、没有插件市场、没有多 Agent 协作的产品化实现。**"多 Agent" 与 "多模态生成" 两项对外宣称的能力在当前代码中名不副实**（详见 01 文第 5 节，已逐行核实）。

3. **最大技术隐患是原生模块 ABI。** `better-sqlite3` + `sqlite-vec` 是 C++ 原生模块，对 Node ABI 强绑定；一旦打包进 Electron/Tauri 的独立运行时，极易出现 `NODE_MODULE_VERSION` 不匹配 —— 这正是当前测试环境已暴露的 better-sqlite3 ABI 失败的根因。

4. **对标路径清晰。** WorkBuddy 的「Craft / Plan / Ask 三模式 + 三层记忆 + 技能市场 + 多 Agent + 自动化 + 连接器 + 安全沙箱」、Codex 的「统一 App Server 驱动 CLI/桌面/Web + 三种审批模式 + 远程 TUI + 沙箱并行」是可复制的成熟范式。Orion Code 应复用其已验证的 agent 内核，补齐**客户端外壳与产品化交互层**。

## 三、推荐演进路线（摘要，详见 05）

- **M0 准备（2 周）**：统一版本号、收敛 UI 层、为原生模块确定预构建策略（见 04）。
- **M1 桌面外壳（4–6 周）**：Electron/Tauri 外壳 + 本地后端引擎复用（关键决策见 04）。
- **M2 核心交互（4–6 周）**：富文本对话、@引用、三模式、会话/文件管理 UI。
- **M3 协作与生态（5–7 周）**：产品化多 Agent、技能市场、自动化调度。
- **M4 多模态与连接器（4–6 周）**：图像/音视频管线、连接器市场。
- **M5 打磨发布（3–4 周）**：安全沙箱、长对话治理、签名与自动更新。

**总估时：约 22–35 周（单团队 3–5 人），可分阶段独立交付。**

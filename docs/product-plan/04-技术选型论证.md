# 04 · 技术选型论证（客户端版 · Orion Code Desktop）

> 目标：针对「桌面客户端应用」，论证前端框架、后端架构、通信协议、数据存储、部署方案，给出选型理由与对比。
> 约束：**最大化复用 v0.2.19 已验证的 TypeScript 引擎**（`src/` 全部逻辑），仅在"外壳与交互层"做新增；**必须解决原生模块 ABI 隐患**。

---

## 一、客户端形态选型：Electron vs Tauri vs 纯 Web+本地后端

| 维度 | **Electron** ✅推荐 | Tauri | 纯 Web + 本地后端（如本地 Node 服务 + 浏览器） |
|---|---|---|---|
| 技术栈一致性 | 复用现有 Node/TS 引擎与 `better-sqlite3`/`sqlite-vec`（同 V8/Node ABI） | Rust 后端，**原生模块需重新编译到 Tauri 运行时**，ABI 断裂风险最高 | 引擎跑本地 Node 服务，前端走浏览器，需自管进程 |
| 原生模块兼容 | ⭐ 直接复用 `better-sqlite3@12` prebuild（同 Node 版本）→ **ABI 风险最低** | 需 `napi`/Rust 绑定或重新 prebuild | 同 Electron，但分发/体验差 |
| 开发效率 | ⭐ 前端即 Web 技术（React DOM），团队现状可直接上 | 需 Rust 知识，学习曲线陡 | 前端自由，但需额外进程管理/通信 |
| 包体积 | 大（~80–150MB，含 Chromium） | 小（~10–20MB） | 中（依赖本地 Node） |
| 生态/成熟度 | ⭐ 极成熟，MCP/AI 工具链多基于此 | 成长中 | 自研成本高 |
| 安全模型 | 主进程/渲染进程隔离，可禁用 Node 集成 | 更强（Rust 核心） | 依赖自行设计 |

**结论：推荐 Electron（方案 A）。**
- 核心理由：**ABI 兼容性**。Orion Code 的核心资产 `better-sqlite3` + `sqlite-vec` 是 Node 原生模块，Electron 自带 Node 运行时，只要打包时 Node 版本与预编译一致，ABI 风险最低；Tauri 的 Rust 运行时会让这些原生模块**必须重新编译**，正好是现状最大隐患的放大器。
- 开发效率：前端直接用 React DOM（Web 技术），与团队现有 TypeScript 能力无缝衔接；可立即把 `UiEventSink` / `ui-view-model` 适配到 Web 渲染。
- 体积与安全的代价可接受（客户端应用普遍接受 Chromium 体积；主/渲染进程隔离 + 禁用 `nodeIntegration` + `contextIsolation` 可满足安全）。

> 若未来极致体积/安全优先，可在 v2 评估 Tauri + 用 `sql.js`（WASM SQLite）替代 `better-sqlite3` 以规避原生模块 —— 见第六章风险缓解。

## 二、前端框架选型

| 选项 | 说明 | 判定 |
|---|---|---|
| **React 18 + TypeScript + 状态管理（Zustand/Jotai）** ✅ | 把已弃用的 Ink `react@17` 升级为 React DOM；复用 React 心智；`UiEventSink` → React 状态流 | **推荐** |
| Vue 3 | 生态好但需重写现有 React 组件思路 | 不推荐（团队已用 React 范式） |
| Svelte | 体积小但团队无沉淀 | 不推荐 |
| 继续 Ink/终端 | 无法达到竞品图形体验 | ❌ 排除 |

**配套**
- **构建**：Vite（`vite`/`@vitejs/plugin-react`）—— 快、HMR、易打包进 Electron。
- **UI 组件**：自建轻量组件库（对标 Codex/WorkBuddy 简洁风）或 `shadcn/ui`（Radix + Tailwind）以加速。
- **Markdown/代码高亮**：`react-markdown` + `shiki`（对标 Codex 语法高亮 diff）。
- **富文本输入**：`tiptap` 或 `lexical`，支持 `@` 选择器与拖拽。

## 三、通信协议（桌面内 & 远程）

| 场景 | 选型 | 理由 |
|---|---|---|
| 渲染进程 ↔ 主进程（本地） | **Electron IPC**（contextBridge + `ipcRenderer`/`ipcMain`） | 官方标准、类型安全（zod 校验）、低延迟 |
| 主进程内引擎调用 | 直接 `import` 引擎包（同进程或 worker） | 避免序列化开销；重计算放 `worker_threads` |
| 远程 TUI / 多端（对标 Codex app-server） | **WebSocket（wss + TLS）** + JSON-RPC 或自定义事件协议 | 复用现有 `UiEventSink` 事件流模型，天然可序列化推送 |
| 与外部 MCP server | 现状已支持 stdio/sse/http/streamable-http | **直接复用** |

**架构借鉴 Codex 统一 App Server**：一份引擎后端（主进程 + 可选独立 Node 服务）同时驱动 ① 桌面渲染进程 ② CLI（保留）③ 远程 WebSocket TUI ④ 未来 Web。统一事件协议 = 现有 `UiEventSink` 事件的序列化版本。

---

## 四、后端 / 运行时架构

**核心原则：引擎即库，外壳即壳。**
- 将现有 `src/`（agent loop、tools、memory、mcp、skills、security）抽为 **`orion-engine` 包**（npm 内部包 / monorepo workspace）。
- 桌面主进程 `import { bootstrapRuntime, query } from 'orion-engine'`，通过事件接口把进展推给渲染进程。
- 重负载（embedding、向量搜索、文件 IO）放入 `worker_threads` 防阻塞 UI。
- **保留 CLI 入口**（`bin/orion`）作为"高级/终端"通道，与桌面共享引擎 —— 不丢失现有用户。

> Monorepo 建议：`pnpm workspace` 或 `npm workspace`，包结构：
> `packages/engine`（现有 src 重构）、`packages/desktop`（Electron 主+渲染）、`packages/cli`（现有 CLI 适配）。

## 五、数据存储选型

| 数据 | 选型 | 说明 |
|---|---|---|
| **长期记忆 / 向量** | **`better-sqlite3` + `sqlite-vec`（复用）** + **Electron 预构建策略**（见下） | 现状资产，语义检索强；关键是打包时锁定 Node ABI |
| 会话历史 | 复用 JSONL `session-storage`，加 **索引层**（SQLite 表或独立 meta 文件）以支持搜索/标签 | 现状已有 |
| 客户端设置/偏好 | `electron-store`（基于 `electron-store` 或自定义 JSON）或落地 `~/.orion-code/orion.json`（**向后兼容 CLI**） | GUI 为配置的可视化层 |
| 大数据/缓存 | 文件系统 + LRU，避免塞进 SQLite | — |
| （可选）云端同步 | 若走 SaaS，加一个同步服务（对标 WorkBuddy 云端记忆） | P2，v1 可不做 |

**原生模块预构建策略（解决 ABi 隐患，最关键）**
1. 在 `electron-builder`/`electron-rebuild` 中加入 `better-sqlite3` 与 `sqlite-vec` 的 rebuild 步骤，**目标 ABI = 打包 Electron 的 Node 版本**（用 `@electron/rebuild` 或 `electron-builder` 的 `npmRebuild`）。
2. CI 中对 macOS（x64/arm64）、Windows、Linux 分别预构建并校验 `NODE_MODULE_VERSION` 一致。
3. 运行时兜底：若向量库加载失败，**复用现状的 LIKE 降级**（已实现），保证无语义检索也能用。
4. 长线：评估 `sql.js`（纯 WASM，无 ABI 问题）作为 `better-sqlite3` 的替代，彻底消除原生模块风险（v2 候选）。

## 六、部署与分发

| 项 | 选型 | 说明 |
|---|---|---|
| 打包 | **`electron-builder`** | 跨平台（mac/win/linux）、签名、自动更新一体 |
| 签名 | macOS 走 Developer ID + 公证（notarize）；Windows 走代码签名证书 | 避免"未知开发者"拦截 |
| 自动更新 | `electron-updater`（Squirrel/DMG/NSIS） | 增量、签名校验 |
| 分发通道 | 官网下载 + （可选）Microsoft Store / 腾讯软件源 | 对标 WorkBuddy 一键安装 |
| 崩溃上报 | Sentry（脱敏，复用 `redaction`） | — |
| 沙箱（安全） | 高危/Full-Auto 模式默认进 **Docker / E2B** 或等效容器隔离（对标 Codex 网络禁用 + WorkBuddy Docker/E2B） | M-12 |

## 七、选型总表（一图决策）

| 层 | 选型 | 复用/新增 | 关键理由 |
|---|---|---|---|
| 客户端外壳 | **Electron** | 新增 | 原生模块 ABi 兼容最优、TS 一致、生态成熟 |
| 前端框架 | **React 18 DOM + Vite + Tailwind/shadcn** | 新增（替代 Ink） | 团队 React 范式、图形体验达标 |
| 本地通信 | **Electron IPC + contextBridge** | 新增 | 官方标准、类型安全 |
| 远程/多端 | **WebSocket(wss)+TLS**，复用 `UiEventSink` 事件模型 | 新增（协议复用） | 对标 Codex app-server |
| 引擎 | **`orion-engine` 包（重构现有 src）** | 复用 | 不重写已验证内核 |
| 存储（记忆/向量） | **better-sqlite3+sqlite-vec + electron-rebuild 预构建** | 复用 + 预构建 | 现状资产，解决 ABi |
| 设置 | `~/.orion-code/orion.json` + GUI | 复用 + GUI | 向后兼容 CLI |
| MCP / Skills / 安全 | 现状直接复用 | 复用 | 已达竞品同等 |
| 打包/更新 | electron-builder + electron-updater + 签名 | 新增 | 一键安装、自动更新 |

## 八、关键风险与缓解（技术侧）

| 风险 | 影响 | 缓解 |
|---|---|---|
| 原生模块 ABi 不匹配 | 桌面启动即崩溃（现状已暴露） | `electron-rebuild` 锁定 ABI + CI 多平台预构建 + LIKE 降级兜底 |
| 长对话质量衰减（WorkBuddy 痛点） | 复杂任务跑偏 | 强化 auto-compact + harness drift guard / completion gate（现状已有，调优） |
| 复杂任务稳定性（WorkBuddy 卡死） | 用户体验崩 | 重规划/异常重试 + 工具超时/abort（现状 `exec_command` 已有） |
| 多 Agent 协作"信息孤岛"（WorkBuddy 痛点） | 并行质量低 | Supervisor 统一 ledger/轨迹（复用 `runtime/subagents` 约束机制） |
| 体积/启动慢 | 下载转化低 | Vite 拆包 + 懒加载 + worker 预取；v2 评估 Tauri+WASM |

> 产品/功能侧规划见 `03`；排期与里程碑见 `05`。
